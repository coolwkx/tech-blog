# 装饰器与生成器
> **一句话总结**：装饰器是"接收函数、返回新函数"的闭包，用 `@` 语法糖把增强逻辑套在原函数外面；生成器是"用 `yield` 把函数变成惰性产值的状态机"，两者共同的前提都是"函数是对象 + 闭包能保存状态"。
> **前置知识**：函数是一等对象、高阶函数、LEGB 与 `nonlocal`（02 篇）、可变默认参数陷阱（02 篇）、类与 `@property` 的宿主类（03 篇）。

> 1. 独立写出通用装饰器（支持任意参数、保留返回值、加 `functools.wraps`），并推导多个装饰器的执行顺序；
> 2. 写出带参数的装饰器，理解"三层结构"为什么是必需的；
> 3. 用 `yield` 写生成器处理大文件/无限序列，并用 `@property` + `@x.setter` 实现带校验的属性读写。

## 1. 核心概念
### 1.1 从闭包到装饰器
回顾闭包的三个条件：**有嵌套、有引用、有返回**。装饰器在闭包基础上加第四条：**有额外功能**。
```text
def my_decorator(func): # 外层函数：参数是"被装饰的函数"
 def wrapper: # 内层函数：将来真正替代原函数的东西
 print("开始执行...") # 额外功能（前置）
 func # 引用外层变量 func（原函数）
 print("执行完成！") # 额外功能（后置）
 return wrapper # 返回内层函数对象

@my_decorator
def say_hi:
 print("hi")
```
`@my_decorator` 完全等价于：
```text
def say_hi:
 print("hi")
say_hi = my_decorator(say_hi) # 名字被重新绑定到 wrapper
```
**装饰发生在"定义时"**：解释器读到 `@my_decorator` 那一行就立刻调用 `my_decorator(say_hi)`，把结果赋回 `say_hi`。之后每次 `say_hi` 调用的其实都是 `wrapper`。

| 概念 | 含义 |
| --- | --- |
| decorator | 接收一个函数、返回一个函数的高阶函数 |
| `@` 语法糖 | 等价于 `f = decorator(f)`，写在函数定义上一行 |
| wrapper / inner | 包装函数，负责"加料"并调用原函数 |
| 装饰时机 | 模块加载（定义）时执行一次 |
| 调用时机 | 每次调用被装饰的名字时执行 wrapper 体 |

### 1.2 通用装饰器模板（背下来）
原函数可能有参数也可能有返回值，所以 wrapper 必须"透传"：
```python
import functools

def decorator(func):
    @functools.wraps(func) # 保护原函数的元信息
    def wrapper(*args, **kwargs): # 接收任意参数
        # === 前置增强 ===
        result = func(*args, **kwargs) # 调用原函数
        # === 后置增强 ===
        return result # 必须把结果返回出去
    return wrapper
```
| 必须做的三件事 | 漏掉的后果 |
| --- | --- |
| `*args, **kwargs` 透传参数 | 原函数带参时 `TypeError` |
| `return result` | 调用者拿到 `None`，链式调用断裂 |
| `@functools.wraps(func)` | `__name__` 变成 `"wrapper"`、`__doc__` 丢失，日志/调试/框架按名字查找全部失效 |

实测对比：
```text
无 wraps: wrapper None
有 wraps: bar 'bar 的文档'
```
### 1.3 的 timer 装饰器是**错的**
 `python进阶/03-装饰器.py` 的"第 2 节 timer"写法如下：
```text
def timer(func):
 import time
 start = time.time # ❌ 在"装饰阶段"就取时间了
 func # ❌ 在装饰阶段就把原函数执行了
 end = time.time
 print(f"耗时: {end - start} 秒")
 # ❌ 没有 return wrapper

@timer
def say_hello:
 print("Hello!")
```
问题有三层：

1. `func` 在**装饰阶段**（也就是模块导入时）就被执行了，**不是**在调用 `say_hello` 时；
2. `timer` 返回 `None`，所以 `say_hello` 被重新绑定成 `None`；
3. 之后写 `say_hello` 会直接抛 `TypeError: 'NoneType' object is not callable`。

正确写法是把计时逻辑放进 `wrapper` 内部：
```python
import functools
import time

def timer(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        start = time.perf_counter # ✅ 每次调用时取
        result = func(*args, **kwargs)
        print(f"{func.__name__} 耗时 {time.perf_counter - start:.4f}s")
        return result
    return wrapper

@timer
def slow(n):
    return sum(range(n))

slow(200000) # slow 耗时 0.0051s
```
> 顺带一提：计时优先用 `time.perf_counter`（单调时钟，不受系统时间调整影响），而不是 `time.time`。

### 1.4 多个装饰器的执行顺序
```text
@deco_a
@deco_b
def target:
 print(" 原函数执行")
```
**装饰顺序（从下往上）**：
```python
target = deco_a(deco_b(target))
```
所以先由 `deco_b` 包装，再由 `deco_a` 包装原函数。**执行顺序（从上往下）**：最外层的 `deco_a.wrapper` 先跑。实测输出：
```text
A 进入
B 进入
 原函数执行
B 退出
A 退出
```
记忆口诀：**装饰由内到外，执行由外到内**（像剥洋葱/穿衣服：最后穿的最先脱）。

### 1.5 带参数的装饰器：为什么必须三层
```python
def log(level): # 第 1 层：接收装饰器自己的参数
    def decorator(func): # 第 2 层：接收被装饰的函数
        @functools.wraps(func)
        def wrapper(*a, **k): # 第 3 层：接收调用时的实参
            print(f"[{level}] 调用 {func.__name__}")
            return func(*a, **k)
        return wrapper
    return decorator

@log(level="DEBUG")
def add(a, b):
    return a + b
```
`@log(level="DEBUG")` 的求值过程：先算 `log(level="DEBUG")` 得到 `decorator`，再等价于 `add = decorator(add)`。

**为什么不能写成两层 `def decorator(func, level)`？** 因为 `@` 后面的表达式求值结果必须是一个"只接收函数"的可调用对象。Python 只会把被装饰函数作为**唯一**参数传给 `@` 的结果，所以装饰器自己需要的参数必须在更外层先"固化"进闭包。

### 1.6 装饰器的常见实战场景
| 场景 | 关键点 | 标准库支持 |
| --- | --- | --- |
| 计时/性能统计 | `perf_counter`、`functools.wraps` | — |
| 日志记录 | 记录入参、返回值、耗时 | `logging` |
| 结果缓存 | 用参数字典做 memo | `functools.lru_cache` / `cache` |
| 权限校验 | 校验失败抛异常 / 返回错误 | — |
| 参数校验 | 检查类型、范围 | `pydantic` |
| 失败重试 | 捕获指定异常并重试，注意加退避 | `tenacity` |
| 注册路由 | 装饰器把函数登记到全局表 | Flask / FastAPI / pytest fixture |

缓存装饰器实测：
```python
calls = {"n": 0}

@functools.lru_cache(maxsize=None)
def fib(n):
 calls["n"] += 1
 return n if n < 2 else fib(n - 1) + fib(n - 2)

print(fib(30), calls["n"]) # 832040 31
```
不做缓存时 `fib(30)` 需要约 270 万次调用，加了缓存只要 **31 次**，差距是指数级。

### 1.7 生成器：惰性求值的状态机
| 创建方式 | 写法 | 特点 |
| --- | --- | --- |
| 生成器函数 | 函数体里出现 `yield` | 可写复杂逻辑、循环、条件 |
| 生成器表达式 | `(x * 2 for x in range(5))` | 一行写法，等价于列表推导式的"惰性版" |
```python
lst = [x ** 2 for x in range(100000)] # 立即生成全部 → 800984 字节
gen = (x ** 2 for x in range(100000)) # 只保存规则 → 200 字节
```
**内存差 4000 倍**，这就是生成器存在的理由。

`yield` 的语义（强调的两点）：

1. **返回值**：把 `yield` 后面的值交出去；
2. **暂停**：函数在这一行"卡住"，局部变量、指令指针全部保留，下次 `next` 从这里继续。

| 操作 | 行为 |
| --- | --- |
| `next(g)` | 恢复执行到下一个 `yield`，返回其值 |
| `g.send(v)` | 恢复执行，并把 `v` 作为**上一个 `yield` 表达式的值**（第一次必须先 `next(g)` 启动） |
| `for x in g` | 内部自动处理 `StopIteration` |
| 生成器耗尽 | 再 `next` 抛 `StopIteration`；`for` 循环直接结束 |
| `list(g)` 第二次 | 得到 `[]` —— **生成器只能遍历一次** |
```text
第一次: [0, 1, 2] 第二次: []
```
### 1.8 `@property`：把方法伪装成属性
```python
class Person:
    def __init__(self, name, age):
        self.name = name
        self._age = age

        @property
        def age(self): # getter
            return self._age

        @age.setter
        def age(self, value): # setter
            if not 0 <= value <= 150:
                raise ValueError("年龄必须在 0~150 之间")
            self._age = value

            @property
            def is_adult(self): # 只读的派生属性
                return self._age >= 18
```
| 装饰器 | 作用 |
| --- | --- |
| `@property` | 定义 getter，方法变成"只读属性" |
| `@x.setter` | 定义 setter，赋值时做校验 |
| `@x.deleter` | 定义 `del obj.x` 的行为 |

**为什么要用 property 而不是直接暴露属性？**

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 公有属性 `self.age = age` | 简单、快 | 无法校验、无法在未来改成计算属性而不破坏调用方 |
| `get_age` / `set_age` | 可校验 | Java 风格，调用方要改写法 |
| `@property` | 调用写法不变（`p.age`），内部可校验/计算/惰性 | 略有性能开销；容易被误以为"廉价" |

**关键优势**：`p.age` 的调用形式在"直接属性 → property"之间**不变**，所以可以先把属性写成公有的，等需要校验时再升级成 property，调用方代码一行都不用改。

`type(Person.age)` 是 `<class 'property'>` —— 说明 property 是一个**数据描述符**，放在类上拦截了实例属性的读写。

## 2. 最小可运行示例

```text
import functools
import sys
import time

# ---------- 1) 通用装饰器模板：wraps + 透传参数 + 返回结果 ----------
def timer(func):
 @functools.wraps(func) # 保护 __name__ / __doc__
 def wrapper(*args, **kwargs): # 接收任意参数
 start = time.perf_counter # 计时必须在 wrapper 内
 result = func(*args, **kwargs)
 print(f"{func.__name__} 耗时 {time.perf_counter - start:.4f}s")
 return result # 必须把结果返回出去
 return wrapper

@timer
def slow_sum(n):
 return sum(range(n))

print("结果:", slow_sum(200000)) # slow_sum 耗时 0.0050s / 结果: 13800138000

# ---------- 2) 没有 wraps 会怎样 ----------
def plain(func):
 def wrapper(*a, **k):
 return func(*a, **k)
 return wrapper

@plain
def foo:
 """foo 的文档"""

print(foo.__name__, repr(foo.__doc__)) # wrapper None ← 元信息丢了

# ---------- 3) 多个装饰器：装饰由内到外，执行由外到内 ----------
def deco_a(func):
 @functools.wraps(func)
 def wrapper(*a, **k):
 print("A 进入"); r = func(*a, **k); print("A 退出"); return r
 return wrapper

def deco_b(func):
 @functools.wraps(func)
 def wrapper(*a, **k):
 print("B 进入"); r = func(*a, **k); print("B 退出"); return r
 return wrapper

@deco_a
@deco_b
def target:
 print(" 原函数执行")

target # A 进入 → B 进入 → 原函数执行 → B 退出 → A 退出

# ---------- 4) 带参数的装饰器：三层结构 ----------
def log(level): # 第 1 层：接收装饰器参数
 def decorator(func): # 第 2 层：接收被装饰函数
 @functools.wraps(func)
 def wrapper(*a, **k): # 第 3 层：接收调用实参
 print(f"[{level}] 调用 {func.__name__}")
 return func(*a, **k)
 return wrapper
 return decorator

@log(level="DEBUG")
def add(a, b):
 return a + b

print("add:", add(3, 4)) # [DEBUG] 调用 add / add: 7

# ---------- 5) 缓存装饰器：指数级加速 ----------
calls = {"n": 0}

@functools.lru_cache(maxsize=None)
def fib(n):
 calls["n"] += 1
 return n if n < 2 else fib(n - 1) + fib(n - 2)

print("fib(30) =", fib(30), "实际计算次数:", calls["n"]) # 832040 31

# ---------- 6) 生成器：内存对比 + 惰性 + 只能遍历一次 ----------
lst = [x ** 2 for x in range(100000)]
gen = (x ** 2 for x in range(100000))
print("列表内存:", sys.getsizeof(lst), "生成器内存:", sys.getsizeof(gen)) # 800984 200

g2 = (i for i in range(3))
print("第一次:", list(g2), "第二次:", list(g2)) # [0, 1, 2] []

def countdown(n):
 print(" 生成器启动")
 while n > 0:
 yield n # 暂停并返回值，下次从这里继续
 n -= 1
 print(" 生成器结束")

g = countdown(3)
print("next:", next(g)) # 3
print("继续:", next(g), next(g)) # 2 1
try:
 next(g)
except StopIteration:
 print("捕获到 StopIteration")

# ---------- 7) property：带校验的属性读写 ----------
class Person:
 def __init__(self, name, age):
 self.name = name
 self._age = age # 真实数据存在 _age

 @property
 def age(self):
 return self._age

 @age.setter
 def age(self, value):
 if not isinstance(value, int):
 raise TypeError("年龄必须是整数")
 if not 0 <= value <= 150:
 raise ValueError("年龄必须在 0~150 之间")
 self._age = value

 @property
 def is_adult(self):
 return self._age >= 18

p = Person("小明", 20)
print("age:", p.age, "| is_adult:", p.is_adult) # 20 | True
p.age = 25
print("setter 后:", p.age) # 25
for bad in (-5, 200, "x"):
 try:
 p.age = bad
 except (ValueError, TypeError) as e:
 print("拒绝", repr(bad), "->", type(e).__name__, e)
```

**关键点说明**

| 位置 | 关键点 |
| --- | --- |
| `@functools.wraps(func)` | 复制 `__name__` / `__doc__` / `__module__`，否则调试信息全变成 `wrapper` |
| `start` 放在 `wrapper` 内 | 放在外层就是的错误写法，计时的是"装饰过程"而不是"调用过程" |
| `return result` | 漏掉则原函数返回值被吞成 `None` |
| `@deco_a` 在 `@deco_b` 上面 | 先 `deco_b` 包装、后 `deco_a` 包装；执行时 `A` 先跑 |
| `@log(level="DEBUG")` | `log(...)` 先返回 `decorator`，再由 `@` 作用到 `add` |
| `lru_cache` | 用参数做键缓存结果，把 `fib(30)` 从约 270 万次调用降到 **31 次** |
| `sys.getsizeof(gen)` 为 200 | 生成器只保存"规则 + 当前状态"，不保存数据；列表是 800984 字节 |
| `list(g2)` 第二次为 `[]` | 生成器是"一次性的迭代器"，耗尽即空 |
| `p.age = bad` 抛异常 | setter 里做校验，非法赋值不会污染 `_age` |
| `self._age` 而非 `self.age` | property 内部用同名属性会无限递归 → `RecursionError` |

## 3. 常见坑
| 坑 | 现象 | 原因 | 正确做法 |
| --- | --- | --- | --- |
| 装饰器里直接调用原函数 | 函数在"导入时"就执行了，名字变成 `None` | 把 `func` 写在 `decorator` 层而不是 `wrapper` 层 | 所有增强逻辑都放进 `wrapper` |
| 忘记 `return wrapper` | 被装饰的函数变成 `None`，调用报 `TypeError: 'NoneType' object is not callable` | 装饰器必须返回一个可调用对象 | 返回 `wrapper` |
| wrapper 没有 `*args, **kwargs` | 原函数带参时报 `TypeError: wrapper got an unexpected keyword argument` | wrapper 签名必须能接住任何调用 | 用 `def wrapper(*args, **kwargs)` |
| wrapper 忘记 `return` 原函数结果 | 调用者拿到 `None` | 只写了 `func(*args)` 没写 `return` | `return func(*args, **kwargs)` |
| 忘记 `functools.wraps` | `func.__name__` 变成 `"wrapper"`，`__doc__` 变 `None`，日志/框架识别失败 | 装饰器把原函数的元信息覆盖了 | 加 `@functools.wraps(func)` |
| 计时器在装饰阶段取时间 | 第一次运行耗时 0 或异常 | 同第一条 | 时间戳写在 `wrapper` 内部 |
| 用 `time.time` 计时 | 耗时出现负数或跳变 | `time.time` 是墙钟，会被系统时间调整/NTP 同步影响 | 用 `time.perf_counter` |
| 多个装饰器顺序搞反 | 输出顺序和预期相反 | 装饰由内到外（从下往上），执行由外到内（从上往下） | 记住"离函数最近的先装饰" |
| 带参数装饰器写成两层 | `TypeError: decorator missing 1 required positional argument` | `@` 只会把函数作为唯一参数传进去 | 用三层结构，参数放最外层 |
| `lru_cache` 装饰可变参数方法 | 报 `TypeError: unhashable type` | 缓存用参数做字典键，list/dict 不可哈希 | 传 tuple，或改用自定义缓存 |
| `lru_cache` 用在实例方法上 | 缓存永不命中 / 内存泄漏 | `self` 也参与缓存键，且会持有实例引用 | 用 `functools.cached_property` 或类外缓存 |
| 生成器只能遍历一次却被遍历两次 | 第二次得到空结果 | 生成器是迭代器，耗尽后不再产出 | 需要重复遍历就改用 list，或重新创建生成器 |
| `send` 之前没 `next` | `TypeError: can't send non-None value to a just-started generator` | 生成器还没执行到第一个 `yield` | 先 `next(g)`（或 `g.send(None)`）启动 |
| 生成器里忘写循环变量的边界 | 无限循环 + 无限内存增长 | `while True: yield ...` 无终止条件 | 调用方负责 `break`，或加上终止条件 |
| `@property` 与同名实例属性冲突 | `AttributeError: can't set attribute` | `@property` 是数据描述符，且没有 setter 时禁止赋值 | 加 `@x.setter`，内部用 `self._x` 存真实值 |
| property 内部用同名属性名 | `RecursionError: maximum recursion depth exceeded` | `self.age = value` 又触发了 setter | 内部一律操作 `self._age` |
| 在 `__init__` 里给 property 赋值但 setter 校验太严 | 构造对象就抛异常 | `self.age = age` 会走 setter | 校验要覆盖合法的初始值，或 `__init__` 里直接写 `self._age = age` |

## 4. 面试问答
<details>
<summary><strong>Q1：装饰器的本质是什么？`@dec` 到底做了什么？</strong></summary>

本质是**接收函数、返回函数的高阶函数（通常用闭包实现）**。

`@dec` 是语法糖：`@dec` 写在 `def f:` 上面，完全等价于 `f = dec(f)`。解释器在**执行到 `def f` 语句时立刻**做这件事，所以"装饰"发生在定义时而不是调用时。之后调用 `f` 时，实际执行的是 `dec` 内部返回的 `wrapper`，由它决定"在调用原函数前后做什么"。

要写一个正确的通用装饰器，必须满足四点：① 内层 `wrapper` 用 `*args, **kwargs` 接收任意参数；② 用 `return func(*args, **kwargs)` 把结果透传出去；③ 用 `@functools.wraps(func)` 保留原函数的 `__name__` / `__doc__` 等元信息；④ 把计时、日志等副作用放在 `wrapper` 里，而不是装饰器外层。

如果装饰器本身需要参数，就要多加一层：`dec(args)` 返回真正的装饰器，再由 `@` 作用到函数上，这就是三层结构的原因。

</details>

<details>
<summary><strong>Q2：多个装饰器叠加时，装饰顺序和执行顺序分别是什么？</strong></summary>

假设：
```text
@a
@b
@c
def f: ...
```
等价于 `f = a(b(c(f)))`。

- **装饰顺序（由内到外）**：`c` 先包装 `f`，然后 `b` 包装 `c(f)`，最后 `a` 包装 `b(c(f))`。即"离函数最近的装饰器先装饰"。
- **执行顺序（由外到内）**：调用 `f` 时进入最外层的 `a.wrapper` → 再进入 `b.wrapper` → 再进入 `c.wrapper` → 最后执行原函数；**返回时顺序相反**，像栈一样后进先出。

所以输出的"进入"顺序是 `a → b → c`，"退出"顺序是 `c → b → a`。这个模型在权限校验（先校验登录、再校验权限）和缓存（缓存必须最外层才能拦住所有调用）等场景直接影响正确性。

</details>

<details>
<summary><strong>Q3：生成器和迭代器是什么关系？为什么说生成器省内存？</strong></summary>

迭代器是实现了 `__iter__` 和 `__next__` 的对象；生成器是一种**用语法糖自动创建迭代器**的机制 —— 只要函数体里出现 `yield`，这个函数就变成生成器函数，调用它得到的生成器对象自动拥有 `__iter__` / `__next__`。

省内存的原因在于**惰性求值 + 不保存全部数据**：列表推导式会立刻把所有元素算出来存进内存（`[x**2 for x in range(100000)]` 约 800 KB），生成器表达式只保存"产生规则 + 当前状态"（约 200 字节），每次 `next` 才计算一个值。对于 100 万行日志、无限序列、大 CSV 分批读取这类场景，内存差距就是"能不能跑起来"的区别。

代价是：① 只能遍历一次（耗尽即空）；② 不支持随机访问和 `len`；③ 调试时不如列表直观（要看内容得先 `list`）。

</details>

## 5. 自测题
<details>
<summary>1. 下面这个装饰器有什么问题？</summary>

```text
def timer(func):
 import time
 start = time.time
 func
 end = time.time
 print(f"耗时: {end - start} 秒")

@timer
def say_hello:
 print("Hello!")
```
三个问题：① `func` 在装饰阶段就执行了（`say_hello` 被定义时），不是调用时；② 没有返回 `wrapper`，`timer` 返回 `None`，所以 `say_hello` 变成 `None`；③ 因此 `say_hello` 会抛 `TypeError: 'NoneType' object is not callable`，且计时测的是"模块加载"而不是"函数调用"。

正确写法：
```python
import functools, time

def timer(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        start = time.perf_counter
        result = func(*args, **kwargs)
        print(f"{func.__name__} 耗时 {time.perf_counter - start:.4f}s")
        return result
    return wrapper
```

</details>

<details>
<summary>2. 为什么带参数的装饰器需要三层函数？</summary>

因为 `@` 的求值规则是固定的：`@expr` 会把**被装饰的函数作为唯一实参**传给 `expr` 的结果。当装饰器需要自己的参数时，必须先用一次调用把参数"吃掉"并返回一个"只接收函数"的对象。

- 第 1 层 `log(level)`：接收装饰器参数，返回真正的装饰器；
- 第 2 层 `decorator(func)`：接收被装饰的函数，返回 wrapper；
- 第 3 层 `wrapper(*a, **k)`：接收调用时的实参。

如果只有两层写成 `def decorator(func, level)`，那么 `@decorator("DEBUG")` 会先调用 `decorator("DEBUG")`，把字符串当成 `func`，直接出错。

</details>

<details>
<summary>3. `yield` 和 `return` 有什么区别？</summary>

| 维度 | `return` | `yield` |
| --- | --- | --- |
| 函数性质 | 普通函数 | 生成器函数 |
| 执行后 | 函数彻底结束，栈帧销毁，局部变量丢失 | 函数**暂停**，栈帧和局部变量全部保留 |
| 再次调用 | 从函数开头重新执行 | 从暂停处继续执行 |
| 返回值 | 返回给调用者，只能有一次 | 每次 `next` 产出一个值，可以有多次 |
| 结束标志 | `return` | 函数体执行完自动抛 `StopIteration` |

一个函数里只要有 `yield`，它就**不再是普通函数**：调用它不会执行函数体，只是创建生成器对象。要真正开始执行，必须 `next` 或 `for` 迭代。

</details>

<details>
<summary>4. `@property` 相比直接暴露属性和 `get_x` / `set_x` 方法，优势在哪？</summary>

核心优势是**调用形式与公有属性一致**：调用方写 `p.age` 而不是 `p.get_age`，所以"先写公有属性、之后需要校验/计算时再升级为 property"这个重构过程**不会破坏任何调用方代码**。

对比：

- 公有属性：最简单，但无法校验、无法在后续改成派生属性（改了就是 API 破坏）；
- `get_age` / `set_age`：能校验，但调用方写法笨重，且不符合 Python 习惯（Python 里 `len(x)` 而不是 `x.len`）；
- `@property`：写法简洁 + 能校验 + 能计算 + 能只读（只定义 getter 不定义 setter），代价是有一点访问开销，以及容易被误认为"访问属性很便宜"而放进热循环。

注意 property 只应做**轻量**操作；需要查数据库/发网络的"属性"应该显式叫 `fetch_xxx`，避免"看起来像属性实则有 IO"的陷阱。

</details>
