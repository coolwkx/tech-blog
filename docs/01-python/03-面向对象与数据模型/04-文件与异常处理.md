# 04 文件与异常处理
> **一句话总结**：文件操作的核心是"打开—读写—关闭"必须可靠闭环，`with` + 上下文管理器协议就是为此设计的；异常处理的核心是"让错误发生在能被处理的地方"，`try/except/else/finally` 四件套要按语义用而不是随手包一层。
> **前置知识**：函数与作用域（02 篇）、可变/不可变类型（01 篇）、类与魔法方法 `__enter__` / `__exit__`（03 篇）。

> 1. 根据需求正确选择 `r / w / a / x` 与 `b / t` 模式，并解释为什么必须显式写 `encoding="utf-8"`；
> 2. 用 `with` 安全地读写文件，理解 `tell` / `seek` 指针行为，能用逐行方式处理大文件；
> 3. 写出 `try/except/else/finally` 结构，自定义异常并用 `raise ... from ...` 保留异常链，避免裸 `except` 吞异常。

## 1. 核心概念
### 1.1 为什么需要 `with`：从"手动关闭"到"自动释放"
```python
# 方式一：手动关闭 —— 一旦中间出错，close 就不会执行
f = open("1.txt", "w")
f.write("hello world")
f.close # 如果 write 抛异常，这一行永远走不到，文件句柄泄漏
```
文件对象占用**操作系统资源**，而且同一进程能打开的文件数量是有限的（Linux 默认 1024）。所以必须保证"无论是否出错都能关闭"。三种写法对比：

| 写法 | 是否安全 | 代码量 | 说明 |
| --- | --- | --- | --- |
| 手动 `open` + `close` | ❌ | 少 | 中途异常会泄漏句柄 |
| `try ... finally` | ✅ | 多 | 保证关闭，但啰嗦、容易忘 |
| `with open(...) as f` | ✅ | 少 | **推荐**，等价于 try/finally 但由协议自动完成 |

`with` 背后的机制叫**上下文管理器（context manager）**：

> 一个类只要实现了 `__enter__` 和 `__exit__` 两个方法，它的实例就是上下文管理器，可以被 `with` 管理。

执行流程：

1. 计算 `with` 后面的表达式，得到上下文管理器对象；
2. 调用它的 `__enter__`，**返回值绑定到 `as` 后面的名字**；
3. 执行 `with` 语句块；
4. 无论语句块是正常结束、`return`、`break` 还是抛异常，都会调用 `__exit__(exc_type, exc_val, exc_tb)`。

| `__exit__` 返回值 | 效果 |
| --- | --- |
| `None` / `False` | 异常继续向外传播（默认行为，**正确做法**） |
| `True` | **吞掉**异常，外层看不到（只在极特殊场景使用，容易掩盖 bug） |
```python
class MyFile:
    def __init__(self, name, mode):
        self.name, self.mode, self.fp = name, mode, None

        def __enter__(self):
            self.fp = open(self.name, self.mode, encoding="utf-8")
            return self.fp # 返回什么，as 后面就拿到什么

        def __exit__(self, exc_type, exc_val, exc_tb):
            self.fp.close # 一定执行
            return False # 不吞异常
```
> `open` 返回的文件对象本身就是一个上下文管理器，所以 `with open(...) as f` 才能工作。标准库里的 `threading.Lock`、`socket`、`contextlib.suppress` 也都是上下文管理器。

### 1.2 `open` 的模式：一张表说清
| 模式 | 含义 | 文件不存在 | 文件存在 | 可读 | 可写 |
| --- | --- | --- | --- | --- | --- |
| `r` | 只读（默认） | `FileNotFoundError` | 从头读 | ✅ | ❌ |
| `w` | 只写 | 创建 | **清空** | ❌ | ✅ |
| `a` | 追加 | 创建 | 指针移到末尾 | ❌ | ✅ |
| `x` | 独占创建 | 创建 | `FileExistsError` | ❌ | ✅ |
| `r+` | 读写 | `FileNotFoundError` | 不清空 | ✅ | ✅ |
| `w+` | 读写 | 创建 | **清空** | ✅ | ✅ |
| `a+` | 读写 | 创建 | 指针在末尾 | ✅ | ✅ |

在模式字符串后加 `b` 表示**二进制模式**（`rb` / `wb`），加 `t` 是文本模式（默认）。二进制模式下 `read` 返回 `bytes`，且**不能指定 `encoding`**。

| 文本模式 `t` | 二进制模式 `b` |
| --- | --- |
| 读写 `str` | 读写 `bytes` |
| 需要 `encoding` | 禁止 `encoding` |
| 自动处理平台换行符（`\n` ↔ `\r\n`） | 原样读写，不转换 |
| 适合 txt / csv / json | 适合图片、音频、压缩包、pickle |

### 1.3 读写方法对比
| 方法 | 返回 | 内存 | 适用 |
| --- | --- | --- | --- |
| `f.read` | 整个文件内容（str/bytes） | 全量载入 | 小文件 |
| `f.read(n)` | 最多 n 个字符/字节 | 可控 | 分块处理 |
| `f.readline` | 一行（含 `\n`） | 一行 | 逐行 |
| `f.readlines` | 所有行的 list | 全量载入 | 小文件、需要列表 |
| `for line in f:` | 每次一行 | ⭐ 最小 | **大文件首选** |
```python
# 大文件唯一推荐写法：惰性迭代，内存里始终只有一行
with open("big.log", "r", encoding="utf-8") as f:
    for line in f:
        process(line.rstrip("\n")) # 用 rstrip 去掉行尾换行
```
写入方法：

| 方法 | 说明 |
| --- | --- |
| `f.write(s)` | 写入字符串，返回写入的字符数；**不会自动换行** |
| `f.writelines(seq)` | 逐个写入序列中的字符串，**也不会自动加换行** |
| `print(..., file=f)` | 会加换行，适合快速写日志 |

### 1.4 指针：`tell` 与 `seek`
文件对象内部维护一个读写位置（指针）：

| 方法 | 作用 |
| --- | --- |
| `f.tell` | 返回当前指针位置（文本模式下是"不透明的数字"，不要当字节数用） |
| `f.seek(offset, whence)` | `whence=0` 从头，`1` 从当前位置，`2` 从末尾（文本模式下 `1` / `2` 基本不可用） |
| `f.seek(0)` | 回到开头 —— **读完一遍想再读一遍时必须先 `seek(0)`** |
| `f.flush` | 把缓冲区刷到磁盘（`with` 退出时自动 flush + close） |

### 1.5 异常体系：先认族谱再抓异常
```text
BaseException
├── SystemExit # sys.exit 抛出
├── KeyboardInterrupt # Ctrl+C
├── GeneratorExit
└── Exception # ← 业务异常都应该在这里
 ├── ArithmeticError → ZeroDivisionError
 ├── LookupError → IndexError / KeyError
 ├── OSError（别名 IOError） → FileNotFoundError / PermissionError / TimeoutError
 ├── ValueError → UnicodeDecodeError
 ├── TypeError / AttributeError / NameError
 └── RuntimeError → RecursionError
```
| 概念 | 说明 |
| --- | --- |
| `except Exception as e` | 捕获绝大多数业务异常，`e` 绑定异常对象 |
| 多 `except` 顺序 | **从上往下匹配，子类必须写在父类前面**，否则子类永远匹配不到 |
| `else` | `try` 块**正常完成**（没有异常、没有 `return`/`break`/`continue`）时执行 |
| `finally` | 无论发生什么都会执行，用于释放资源；**里面不要写 `return`**（会吞掉返回值和异常） |
| `raise` | 重新抛出当前异常（`raise` 单独用）或抛出新异常 |
| `raise E(...) from e` | 抛出新异常并保留 `__cause__`，异常链清晰 |

**执行顺序实测**：
```python
def flow(x):
    try:
        r = 10 / x
    except ZeroDivisionError as e:
        print(" except:", e)
    else:
        print(" else: 没异常，r =", r)
    finally:
        print(" finally: 清理")

        flow(2)
        # else: 没异常，r = 5.0
        # finally: 清理
        flow(0)
        # except: division by zero
        # finally: 清理
```
注意：如果 `try` 块里写了 `return`，`else` **不会**执行（因为 `try` 不是"正常完成"），但 `finally` 一定执行。

### 1.6 两种风格：LBYL vs EAFP
| 风格 | 全称 | 写法 | 适用 |
| --- | --- | --- | --- |
| LBYL | Look Before You Leap | `if os.path.exists(p): ...` | 检查便宜、失败常见 |
| EAFP | Easier to Ask Forgiveness than Permission | `try: ... except FileNotFoundError: ...` | **Python 推荐**：省一次系统调用，且天然避免检查与使用之间的竞态 |
```python
# LBYL：两次访问文件系统，且两次之间文件可能被删掉
if os.path.exists(path):
 with open(path) as f: ...

# EAFP：一次访问，异常即答案
try:
 with open(path) as f: ...
except FileNotFoundError:
 ...
```
**但要遵守一条铁律**：`try` 块只包"你确定会抛这种异常"的最小代码范围。把 20 行代码一股脑塞进 `try`，会导致真正的 bug 被 `except` 误吞。

### 1.7 常用文件工具
| 需求 | 标准库方案 |
| --- | --- |
| 路径拼接 / 判断 | `os.path.join`、`os.path.exists`、`os.path.getsize` |
| 现代路径对象 | `pathlib.Path`（`p.exists`、`p.read_text`、`p.glob("*.csv")`） |
| 复制 / 移动 / 删除目录 | `shutil.copy2`、`shutil.move`、`shutil.rmtree` |
| 遍历目录 | `os.walk` / `Path.rglob` |
| CSV | `csv.reader` / `csv.DictReader` / `csv.writer` |
| JSON | `json.load` / `json.dump`（`ensure_ascii=False` 保留中文） |

## 2. 最小可运行示例
```text
import os
import shutil

base = "demo_files"
shutil.rmtree(base, ignore_errors=True) # 清理上次运行残留
os.makedirs(base, exist_ok=True)
path = os.path.join(base, "demo.txt")

# ---------- 1) 写：w 会清空，a 是追加，都要显式编码 ----------
with open(path, "w", encoding="utf-8") as f:
 f.write("第一行\n")
 f.writelines(["第二行\n", "第三行\n", "第四行\n"])

# ---------- 2) 读：三种方式与它们的内存代价 ----------
with open(path, "r", encoding="utf-8") as f:
 print("read 全文长度:", len(f.read)) # 16（含 4 个换行符）

with open(path, "r", encoding="utf-8") as f:
 print("readline:", repr(f.readline)) # '第一行\n'
 print("readlines:", f.readlines) # ['第二行\n', '第三行\n', '第四行\n']

print("逐行遍历（大文件首选）:")
with open(path, "r", encoding="utf-8") as f:
 for line in f:
 print("", line.rstrip("\n"))

# ---------- 3) 指针：读完想再读必须 seek(0) ----------
with open(path, "r", encoding="utf-8") as f:
 print("起始 tell:", f.tell) # 0
 f.read
 print("读完后 readline:", repr(f.readline)) # '' ← 已在末尾
 f.seek(0)
 print("seek(0) 后:", repr(f.readline)) # '第一行\n'

# ---------- 4) 'w' 截断 vs 'a' 追加 ----------
with open(path, "w", encoding="utf-8") as f:
 f.write("只剩这一行\n")
print("w 之后大小:", os.path.getsize(path)) # 17 字节（utf-8 中文 3 字节）

with open(path, "a", encoding="utf-8") as f:
 f.write("追加一行\n")

# ---------- 5) 异常四件套：else 只在正常完成时执行 ----------
def safe_div(x):
 try:
 result = 10 / x
 except ZeroDivisionError as e:
 print(" except:", e)
 result = None
 else:
 print(" else: 计算成功")
 finally:
 print(" finally: 无论成败都执行（放清理代码）")
 return result

print("safe_div(2) ->", safe_div(2))
print("safe_div(0) ->", safe_div(0))

# ---------- 6) 自定义异常 + 异常链 ----------
class ParseError(Exception):
 """自定义业务异常"""

def to_int(text):
 try:
 return int(text)
 except ValueError as e:
 raise ParseError(f"无法把 {text!r} 转成整数") from e # 保留原始异常

try:
 to_int("abc")
except ParseError as e:
 print("捕获:", e, "| 原始原因:", type(e.__cause__).__name__)
 # 捕获: 无法把 'abc' 转成整数 | 原始原因: ValueError

# ---------- 7) 上下文管理器：自定义 + 异常穿透 ----------
class ManagedFile:
 def __init__(self, name, mode):
 self.name, self.mode, self.fp = name, mode, None

 def __enter__(self):
 self.fp = open(self.name, self.mode, encoding="utf-8")
 return self.fp

 def __exit__(self, exc_type, exc_val, exc_tb):
 self.fp.close
 print(" __exit__ 收到异常类型:", exc_type) # 正常时为 None
 return False # 不吞异常

with ManagedFile(path, "r") as fp:
 print("首行:", fp.readline.strip)

try:
 with ManagedFile(path, "r") as fp:
 raise RuntimeError("业务出错")
except RuntimeError as e:
 print("异常正常向外传播:", e)

# ---------- 8) 备份：shutil 一行 vs 手动读写 ----------
shutil.copy2(path, os.path.join(base, "demo.bak"))
print("备份文件存在:", os.path.exists(os.path.join(base, "demo.bak")))

shutil.rmtree(base)
```
真实运行输出（节选）：
```text
read 全文长度: 16
readline: '第一行\n'
readlines: ['第二行\n', '第三行\n', '第四行\n']
起始 tell: 0
读完后 readline: ''
seek(0) 后: '第一行\n'
w 之后大小: 17
 except: division by zero
 finally: 无论成败都执行（放清理代码）
safe_div(0) -> None
 else: 计算成功
 finally: 无论成败都执行（放清理代码）
safe_div(2) -> 5.0
捕获: 无法把 'abc' 转成整数 | 原始原因: ValueError
首行: 只剩这一行
 __exit__ 收到异常类型: None
 __exit__ 收到异常类型: <class 'RuntimeError'>
异常正常向外传播: 业务出错
```
**关键点说明**

| 位置 | 关键点 |
| --- | --- |
| `encoding="utf-8"` | 不写就跟随平台默认编码，Windows 上是 GBK，跨平台必乱码 |
| `read` 后 `readline` 返回 `''` | 指针已在末尾，必须 `seek(0)` |
| `os.path.getsize` 为 17 | utf-8 下中文占 3 字节，"只剩这一行\n" = 5×3 + 1 + 1 = 17 |
| `else` 分支 | 只在 `try` 正常完成时执行，用来把"成功后的动作"和"可能出错的代码"分开 |
| `finally` | 资源清理的最终防线；不要在里面 `return` |
| `raise ... from e` | 保留 `__cause__`，报错信息里能看到"原始原因"，方便排查 |
| `__exit__` 返回 `False` | 异常继续向外传播；返回 `True` 会静默吞掉异常 |
| `shutil.copy2` | 复制内容 + 元数据（时间戳），比手动 `read`/`write` 更可靠 |

## 3. 常见坑
| 坑 | 现象 | 原因 | 正确做法 |
| --- | --- | --- | --- |
| 不写 `encoding` | 读取中文文件报 `UnicodeDecodeError: 'gbk' codec can't decode byte...` | Windows 默认编码是 GBK，文件是 utf-8 | 所有文本 `open` 都写 `encoding="utf-8"` |
| 用 `w` 打开想读的文件 | 文件内容全没了 | `w` 会**立即截断**文件 | 读用 `r`，读写用 `r+`/`a+`，新建才用 `w` |
| 二进制模式传 `encoding` | `ValueError: binary mode doesn't take an encoding argument` | `b` 模式操作 bytes | 去掉 `encoding`，或改用文本模式 |
| 只读模式写入 | `io.UnsupportedOperation: not writable` | `r` 模式禁止写 | 需要写就换 `w`/`a`/`r+` |
| 路径里的 `\` 被当转义符 | `SyntaxError` 或路径错误 | `"C:\new\test"` 中 `\n` `\t` 被转义 | 用原始字符串 `r"C:\new\test"` 或正斜杠 `"C:/new/test"` |
| `write` 没写换行 | 所有内容挤在一行 | `write` 不自动加 `\n` | 手动加 `"\n"`，或 `writelines` 时自己带换行，或 `print(..., file=f)` |
| 写完立刻用别的程序打开看不到内容 | 文件是空的或内容不全 | 内容还在缓冲区 | `with` 退出会自动 flush；不想等就 `f.flush` |
| 边 `for line in f` 边 `f.read` | 行为混乱、丢数据 | 两者共享同一个指针 | 一个文件对象只用一种读法 |
| 忘 `close` | 文件被占用 / `ResourceWarning: unclosed file` | 句柄没释放 | 一律用 `with` |
| `except:` 裸捕获 | 连 `KeyboardInterrupt`、`SystemExit` 都被吞，Ctrl+C 都杀不掉 | 裸 `except` 等价于 `except BaseException` | 至少写 `except Exception as e:`，并记录日志 |
| 多 `except` 顺序写反 | 具体分支永远不执行 | `except` 从上往下匹配，父类在前会先吃掉 | 子类写在前（`FileNotFoundError` 在 `OSError` 前） |
| `try` 块包得太大 | 真 bug 被误判成"正常业务异常" | 捕获范围过宽 | `try` 只包真正会抛异常的那一两行 |
| `finally` 里写 `return` | 返回值被覆盖、异常被吞 | `finally` 的 `return` 优先于 `try` 的 | 永远不要在 `finally` 里 `return` |
| `except Exception as e` 在 `except` 外使用 `e` | Python 3 中 `e` 已被删除，报 `NameError` | `except` 块结束会执行隐式 `del e` | 需要留存就 `err = e` 赋值给别的名字 |
| 用 `assert` 做业务校验 | 加 `-O` 运行时校验失效 | `assert` 会被优化掉 | 校验用 `if ... raise ValueError(...)`，`assert` 只用于内部不变量和调试 |
| 手动备份覆盖源文件 | 数据丢失 | 目标路径写成了源路径 | 备份前判断目标是否已存在 / 加时间戳 |
| 用 `readlines` 读大文件 | 内存暴涨甚至 OOM | 一次把所有行读进内存 | 改用 `for line in f` |

**Q1：`with open(...) as f` 和 `try/finally` 有什么区别？`with` 是怎么实现的？**

功能上等价：都保证"无论是否异常都关闭文件"。区别在**抽象层次**：`try/finally` 是手写流程控制，你必须自己记得写 `f.close`；`with` 是基于**上下文管理器协议**的语法糖，把"进入时准备、退出时清理"这件事交给对象自己负责。

实现机制：`with expr as name:` 会先求值 `expr` 得到上下文管理器对象 `cm`，然后：
```python
cm = expr
name = cm.__enter__
try:
    语句块
except BaseException as e:
    if not cm.__exit__(type(e), e, e.__traceback__):
        raise
else:
    cm.__exit__(None, None, None)
```
即 `__enter__` 的返回值绑定给 `as` 后面的名字；`__exit__` 无论成败都被调用，它的返回值决定异常是否被吞掉（返回假值则继续抛出）。所以只要实现了这两个方法，任何对象都能被 `with` 管理 —— 标准库的 `threading.Lock`、`socket`、`contextlib.suppress` / `contextlib.ExitStack` 都是这么做的。

</details>

<details><summary>参考答案</summary>

**Q2：`try/except/else/finally` 四个子句分别在什么时候执行？**

- `try`：放入**可能抛异常的最小代码块**；
- `except`：`try` 中抛出匹配类型的异常时执行，可以写多个，按从上到下匹配，子类必须写在父类前面；
- `else`：只有在 `try` 块**正常完成**（没有异常，也没有 `return` / `break` / `continue`）时执行。它存在的价值是把"不该被 except 覆盖的后续代码"移出 try，缩小异常捕获范围；
- `finally`：无论如何都执行（含异常、`return`、`break`），用于释放资源；若 `finally` 中也有 `return`，它会覆盖 `try` / `except` 的返回值，并且会吞掉正在传播的异常 —— 所以**不要在 `finally` 里写 `return`**。

推荐写法顺序是 `try → except → else → finally`，但只有 `try` 是必需的。

</details>

<details><summary>参考答案</summary>

**Q3：为什么 Python 更推荐 EAFP（先做再捕获异常）而不是 LBYL（先检查再操作）？**

三个原因：① **性能**：LBYL 在"通常成功"的场景下多做一次系统调用/查找（`os.path.exists` + `open`），而 EAFP 只有成功路径一次开销；② **正确性**：检查和操作之间存在时间窗，文件可能在两者之间被删除或权限被改变，LBYL 反而更脆弱；③ **可读性**：EAFP 把"正常流程"写在主线，把异常情况集中到 `except`，代码主线更干净 —— 这也符合 Python 的 `KeyError` / `int` / `open` 都直接抛异常的设计。

但 EAFP 有前提：`try` 的范围必须足够小，只包含真正会抛该异常的那几行；同时异常必须是**可预期的**（`FileNotFoundError` 是，`AttributeError` 往往意味着有 bug，不该靠 except 兜着）。

</details>

## 5. 自测题
<details><summary>1. `open("a.txt", "w")` 和 `open("a.txt", "a")` 有什么区别？如果文件本来有 1000 行内容呢？</summary>

`w` 打开时会**立即把文件清空**（truncate 到 0 字节），无论后面是否真的写入；`a` 打开时不清空，写入位置在文件末尾，所以是追加。

对已有 1000 行的文件：用 `w` 打开后文件立刻变成空的，原来的 1000 行全部丢失；用 `a` 打开则在第 1000 行后面追加。

如果只是想"读"，用 `r`；想"既读又写、不清空"，用 `r+`（注意打开时指针在开头，写入会覆盖原内容）。另外 `w` 模式下如果文件不存在会创建，`r` 模式则会抛 `FileNotFoundError`。

</details>

<details><summary>2. 下面代码为什么可能泄漏文件句柄？怎么改？</summary>
```python
def read_config(path):
 f = open(path, "r")
 data = json.load(f)
 f.close
 return data
```
如果 `json.load(f)` 抛出异常（文件内容不是合法 JSON），`f.close` 就不会执行，句柄一直占用，直到垃圾回收才可能释放（CPython 引用计数会在 `f` 被回收时关闭，但这是**实现细节**，不能依赖，PyPy 上更明显）。

改成：
```python
def read_config(path):
    with open(path, "r", encoding="utf-8") as f:
        return json.load(f)
```
`with` 在任何出口（正常返回、异常、`return`）都会调用 `__exit__` 关闭文件。顺便补上了 `encoding`。

</details>

<details><summary>3. 下面的输出是什么？为什么？</summary>
```text
def f:
 try:
 return "try"
 finally:
 print("finally")

print(f)
```
输出 `finally` 然后 `try`。执行 `return "try"` 时，返回值先被计算并暂存，然后 `finally` 块运行；`finally` 结束后才真正返回。所以屏幕上的 `finally` 先出现，但函数返回的仍是 `"try"`。

如果 `finally` 里写成 `return "finally"`，那么最终返回 `"finally"`，且 `try` 中的异常也会被吞掉 —— 这是最容易制造的隐蔽 bug 之一。

</details>

<details><summary>4. `except (ValueError, TypeError) as e` 和写两个 `except` 有区别吗？</summary>

功能上等价，都是"匹配任意一种类型"。区别：① 用元组只能共用一段处理逻辑；写两个 `except` 可以分别处理（比如 `ValueError` 提示用户重输、`TypeError` 记日志并报警）；② 可读性上，类型列表较长时元组更紧凑。

需要按类型差异化处理时必须分开写，且**顺序**很关键：
```python
try:
 open("x.txt")
except FileNotFoundError:
 print("文件不存在")
except OSError as e: # OSError 是 FileNotFoundError 的父类
 print("其他 IO 错误", e)
```
如果把 `OSError` 写在前面，`FileNotFoundError` 分支永远不会被触发。

</details>
