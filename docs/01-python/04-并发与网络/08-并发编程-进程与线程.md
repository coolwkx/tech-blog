## 1. 核心概念
### 1.1 并发 vs 并行
| 概念 | 定义 | 硬件前提 | 例子 |
| --- | --- | --- | --- |
| 并发 concurrency | 一段时间内**交替**执行多个任务 | 单核即可 | 单核 CPU 上用时间片轮转跑 3 个软件 |
| 并行 parallelism | 同一时刻**真正同时**执行多个任务 | 需要多核 | 16 核 CPU 同时跑 4 个计算任务 |
| 多任务 multitasking | 同一时间内执行多个任务（给人感觉） | — | 操作系统同时开浏览器和音乐播放器 |

**关键点**：单核只能并发，不能并行。并发是"看起来同时"，并行是"真的同时"。它们不是对立的，而是"多任务"的两种实现层次 —— 现代系统里两者同时存在（多核并行 + 每核上并发）。

### 1.2 进程 / 线程 / 协程
| 维度 | 进程 Process | 线程 Thread | 协程 Coroutine |
| --- | --- | --- | --- |
| 定位 | 资源分配的最小单位 | CPU 调度的最小单位 | 用户态协作式任务 |
| 内存空间 | **独立**（各自一份） | **共享**同一进程内存 | 共享 |
| 创建开销 | 大（要拷贝/初始化资源） | 小 | 极小 |
| 通信方式 | IPC（Queue / Pipe / 共享内存 / socket） | 直接读写共享变量 | 直接共享 |
| 切换成本 | 高 | 中 | 极低 |
| 能否用多核 | ✅（绕过 GIL） | ❌（受 GIL 限制） | ❌ |
| 稳定性 | 一个进程崩溃不影响其他进程 | 一个线程崩溃可能拖垮整个进程 | 同线程 |
| 适用 | CPU 密集型 | I/O 密集型 | 高并发 I/O（`asyncio`） |

**进程与线程的 6 条关系（值得记住）**：

1. 线程依附在进程里，没有进程就没有线程；
2. 一个进程默认提供一条线程（主线程），进程可以创建多条线程；
3. 进程之间不共享全局变量，线程之间共享全局变量；
4. 创建进程的资源开销比创建线程大；
5. 进程是操作系统资源分配的基本单位，线程是 CPU 调度的基本单位；
6. 线程不能独立执行，必须依存于进程。

### 1.3 为什么是"拷贝"：进程间数据隔离的原理
创建子进程时，操作系统让子进程拥有**独立的地址空间**。可以这样理解："子进程是主进程的一个副本，好比一对双胞胎"。

实测：
```text
主进程 g_list = ['主进程']
子进程 append('子进程')
子进程退出后，主进程看到的 g_list: ['主进程'] ← 没变
子线程 append('子线程')
主线程看到的 g_list: ['子线程'] ← 变了
```
- **进程**：每个进程操作的是自己的 `g_list`，名字相同但内存不同，所以互不影响；
- **线程**：所有线程共用同一个进程的堆和全局变量，所以立刻可见。

> 结论：想在进程之间传数据，必须走 IPC（`multiprocessing.Queue` / `Pipe` / `Manager` / 共享内存 / socket）；想在进程之间"共享一个计数器"，用普通全局变量是无效的。

### 1.4 `multiprocessing` 常用 API
| 项 | 用法 | 说明 |
| --- | --- | --- |
| 创建进程 | `mp.Process(target=fn, name=..., args=, kwargs={})` | `target` 是函数对象（不加括号） |
| 启动 | `p.start` | 真正 fork/spawn 出子进程 |
| 等待结束 | `p.join(timeout=None)` | 阻塞当前进程直到子进程结束 |
| 是否存活 | `p.is_alive` | 返回布尔 |
| 后台进程 | `p.daemon = True`（必须在 `start` 前设置） | 主进程退出时子进程被强制终止 |
| 强制结束 | `p.terminate` | **不推荐**：可能留下僵尸进程、不清理资源 |
| 当前进程 | `mp.current_process` / `os.getpid` | 取 `pid` 用于日志与调试 |
| 父进程号 | `os.getppid` | 验证"子进程由谁创建" |
| 进程池 | `mp.Pool(n)` / `ProcessPoolExecutor(n)` | 复用进程，避免频繁创建开销 |
| 队列 | `mp.Queue` | 进程安全，可跨进程传对象（需可 pickle） |
| 管道 | `mp.Pipe` | 双向/单向，比 Queue 轻量 |
| 共享状态 | `mp.Value` / `mp.Array` / `mp.Manager` | 需要加锁保护 |

**必须记住的一条**：`target=` 传的是**函数名，不加括号**。写 `target=worker` 会立刻在主进程里执行 `worker` 并把返回值（通常是 `None`）传给 `Process`，然后报 `TypeError: 'NoneType' object is not callable`。

### 1.5 `threading` 常用 API
| 项 | 用法 | 说明 |
| --- | --- | --- |
| 创建线程 | `threading.Thread(target=fn, args=, kwargs={}, name=..., daemon=...)` | 同样传函数名 |
| 启动 / 等待 | `t.start` / `t.join` | `join` 阻塞到该线程结束 |
| 守护线程 | `daemon=True` 或 `t.setDaemon(True)`（3.10 起弃用） | 主线程退出即被终止 |
| 当前线程 | `threading.current_thread` | 名字、`ident` |
| 活跃线程数 | `threading.active_count` / `threading.enumerate` | 调试用 |
| 互斥锁 | `threading.Lock` | `with lock:` 或 `acquire` / `release` |
| 可重入锁 | `threading.RLock` | 同一线程可多次获取 |
| 条件变量 | `threading.Condition` | 生产者-消费者 |
| 信号量 | `threading.Semaphore(n)` | 限制并发数 |
| 线程池 | `concurrent.futures.ThreadPoolExecutor(n)` | **生产环境首选**，返回 `Future` |

> 现实建议：手写 `Thread` + `join` 只适合教学和简单的"起几个后台任务"。真正的并发任务编排用 `concurrent.futures` 的 `ThreadPoolExecutor` / `ProcessPoolExecutor`（`ex.map` / `ex.submit` + `as_completed`），异常处理和超时都更规范。

### 1.6 GIL：它到底是什么
**GIL（Global Interpreter Lock，全局解释器锁）** 是 CPython 解释器里的一把互斥锁，保证**同一时刻只有一个线程在执行 Python 字节码**。

| 问题 | 答案 |
| --- | --- |
| GIL 保护什么？ | 解释器内部状态（引用计数、对象分配等），让实现变简单 |
| 多线程能并行算 CPU 吗？ | ❌ 不能。4 个 CPU 密集线程 ≈ 1 个线程的总算力 |
| 那多线程有什么用？ | ✅ I/O 等待时 GIL 会被**释放**（如 `time.sleep`、`socket.recv`、文件读写），其他线程可以跑 |
| 多进程受 GIL 影响吗？ | ❌ 不受，每个进程有自己的解释器和 GIL |
| GIL 会被移除吗？ | CPython 3.13 起提供实验性的 free-threaded 构建（PEP 703），但生态与性能仍在演进，现阶段主流仍是带 GIL 的 CPython |

**GIL 不等于"线程安全"**：GIL 只在"字节码之间"切换，一条语句可能对应多条字节码，切换可能发生在中间。所以"看起来原子"的 `x += 1`（`LOAD` → `ADD` → `STORE`）依然可能被中途打断 —— 这就是竞态条件的根源。

### 1.7 竞态条件（race condition）与锁
经典场景：**检查-然后-行动（check-then-act）不是原子的**。
```text
初始 balance = 100，两个线程各取 60
t1: 检查 balance(100) >= 60 → 成立
t2: 检查 balance(100) >= 60 → 成立 ← 问题出在这
t1: balance = 100 - 60 = 40
t2: balance = 100 - 60 = 40（用旧值）或 40 - 60 = -20
```
实测结果（稳定复现）：
```text
余额竞态(无锁): -20 (正确结果应为 40)
余额竞态(加锁): 40
```
**修复：把"检查 + 修改"整体放进临界区**。
```text
lock = threading.Lock

def withdraw:
 with lock: # 进入临界区，同一时刻只有一个线程能进来
 if balance[0] >= 60:
 time.sleep(0.001) # 模拟耗时的写操作
 balance[0] -= 60
```
| 写法 | 说明 |
| --- | --- |
| `with lock:` | **推荐**，出异常也会自动释放 |
| `lock.acquire` / `try ... finally: lock.release` | 手动版，容易忘记释放 |
| `lock.acquire(blocking=False)` | 不阻塞，拿不到立刻返回 `False` |
| 同一线程重复 `acquire` 同一把 `Lock` | **死锁**（用 `RLock` 可重入） |
| 忘记释放 / 两个锁交叉获取 | 死锁，程序卡住不再响应 |

> 一个必须澄清的点：**GIL 让竞态更难复现，但不让它消失**。本机实测（CPython 3.12）："2 个线程各循环 100 万次 `g_num += 1`"这个经典 demo **跑出了 1000000 的"正确"结果**（8 线程 × 50 万也同样正确），因为 GIL 的切换间隔默认 5ms，而 `+=` 的字节码窗口太小，很难被打断。但这**不是保证** —— 一旦代码里出现真正的多步操作（函数调用、`sleep`、I/O、`dict` 多步更新），竞态立刻复现。所以正确的学习姿势是：用"取款"这类带明确窗口的例子理解竞态，而不是背"100 万次加 1 会少"这个未必成立的结论。

### 1.8 `daemon` 与"主进程等待"
| 行为 | 表现 |
| --- | --- |
| 默认 | 主进程/主线程会**等待所有子进程/子线程结束**才退出 |
| `daemon=True` | 主进程/主线程退出时，子进程/子线程被**强制终止** |
| `p.terminate` | 手动强制结束子进程，不推荐（可能留下僵尸进程、不清理资源） |

**为什么默认要等待？** 因为子进程可能需要把结果写回文件/数据库，直接杀掉会丢数据。daemon 适用于"纯背景任务"（心跳、监控、刷新缓存），它们的消失不影响正确性。

注意：**daemon 进程不能创建子进程**，否则会抛 `AssertionError: daemonic processes are not allowed to have children`。

### 1.9 Windows 上的 `spawn` 与 `if __name__ == "__main__":`
Linux 默认用 `fork`（直接复制父进程内存），Windows/macOS 默认用 `spawn`（**重新启动一个 Python 解释器，重新 import 主模块**）。这就是为什么多进程代码**必须**把启动逻辑放进 `if __name__ == "__main__":`：
```python
if __name__ == "__main__":
 p = mp.Process(target=worker)
 p.start
 p.join
```
否则子进程在 import 主模块时又会执行一遍 `mp.Process(...).start`，形成**无限递归创建进程**，直到系统资源耗尽（Windows 上通常表现为报错刷屏或直接卡死）。

## 2. 最小可运行示例

```text
import multiprocessing as mp
import os
import threading
import time

g_list = [] # 全局变量：验证进程不共享 / 线程共享

def cpu_task(n):
 total = 0
 for i in range(n):
 total += i * i
 return total

def io_task(seconds):
 time.sleep(seconds)

def append_item(tag):
 g_list.append(tag)

def run_serial_cpu(times, n):
 for _ in range(times):
 cpu_task(n)

def run_process_cpu(times, n):
 ps = [mp.Process(target=cpu_task, args=(n,)) for _ in range(times)]
 for p in ps:
 p.start # 先全部启动
 for p in ps:
 p.join # 再全部等待 → 才是真并行

def run_thread_cpu(times, n):
 ts = [threading.Thread(target=cpu_task, args=(n,)) for _ in range(times)]
 for t in ts:
 t.start
 for t in ts:
 t.join

def bench(fn, *args):
 start = time.perf_counter
 fn(*args)
 return time.perf_counter - start

def race_withdraw(use_lock):
 """两个线程同时从 100 里取 60，正确结果必须剩 40"""
 balance = [100]
 lk = threading.Lock

 def withdraw:
 if use_lock:
 with lk: # 临界区
 if balance[0] >= 60:
 time.sleep(0.001) # 放大"检查-修改"窗口
 balance[0] -= 60
 else:
 if balance[0] >= 60:
 time.sleep(0.001)
 balance[0] -= 60

 ts = [threading.Thread(target=withdraw) for _ in range(2)]
 for t in ts:
 t.start
 for t in ts:
 t.join
 return balance[0]

if __name__ == "__main__": # Windows spawn 机制下必须有这一层保护
 print("CPU 核心数:", os.cpu_count)

 # CPU 密集：4 份 × 1200 万次循环 —— 只有多进程能用满多核
 for name, fn in [("串行", run_serial_cpu),
 ("多进程", run_process_cpu),
 ("多线程", run_thread_cpu)]:
 print(f"CPU 密集 - {name}: {bench(fn, 4, 12_000_000):.3f}s")

 # I/O 密集：6 份 × sleep 0.4s —— 等待时 GIL 被释放，多线程就够
 def run_serial_io(times, seconds):
 for _ in range(times):
 io_task(seconds)

 def run_thread_io(times, seconds):
 ts = [threading.Thread(target=io_task, args=(seconds,)) for _ in range(times)]
 for t in ts:
 t.start
 for t in ts:
 t.join

 for name, fn in [("串行", run_serial_io), ("多线程", run_thread_io)]:
 print(f"I/O 密集 - {name}: {bench(fn, 6, 0.4):.3f}s")

 # 进程隔离 vs 线程共享
 g_list.append("主进程")
 p = mp.Process(target=append_item, args=("子进程",))
 p.start; p.join
 print("子进程 append 后主进程看到:", g_list) # ['主进程']

 g_list.clear
 t = threading.Thread(target=append_item, args=("子线程",))
 t.start; t.join
 print("子线程 append 后主线程看到:", g_list) # ['子线程']

 # 竞态与锁
 print("余额竞态(无锁):", race_withdraw(False)) # -20
 print("余额竞态(加锁):", race_withdraw(True)) # 40

 # 守护线程
 d = threading.Thread(target=lambda: [time.sleep(0.1) for _ in range(100)], daemon=True)
 d.start
 print("守护线程 is_alive:", d.is_alive, "| 存活线程数:", threading.active_count)
```

本机实测输出（16 核 Windows，CPython 3.12.14）：

```text
CPU 核心数: 16
CPU 密集 - 串行: 2.831s
CPU 密集 - 多进程: 1.649s
CPU 密集 - 多线程: 2.722s

I/O 密集 - 串行: 2.403s
I/O 密集 - 多线程: 0.401s

子进程 append 后主进程看到: ['主进程']
子线程 append 后主线程看到: ['子线程']
余额竞态(无锁): -20
余额竞态(加锁): 40
守护线程 is_alive: True | 存活线程数: 2
```

**关键点说明**

| 位置 | 关键点 |
| --- | --- |
| `mp.Process(target=cpu_task, args=(n,))` | 传函数名**不加括号**；`args` 必须是元组，单参数也要写 `(n,)` |
| 先全部 `start` 再全部 `join` | 边 start 边 join 会退化成串行，看不到并行效果 |
| CPU 密集 1.7x 提速 | 多进程能用多核；进程创建与数据搬运有额外开销，所以达不到理想的 4x |
| 多线程 CPU 密集几乎无加速 | 受 GIL 限制，多个线程争一把锁轮流执行字节码 |
| I/O 密集 6x 提速 | `sleep`/网络/文件等待时 GIL 被释放，线程真正并发 |
| 进程 `g_list` 不变 | 子进程是独立地址空间的副本，改的是自己的内存 |
| 线程 `g_list` 变了 | 同进程共享堆，全局变量就是同一份 |
| `with lk:` 包住 `if` 和 `-=` | 临界区必须覆盖"检查 + 修改"全过程，只锁一半等于没锁 |
| `daemon=True` | 主线程退出时守护线程立刻被终止，不阻塞退出 |

### 2.1 进程间通信（IPC）

进程之间不共享内存，所以要把数据传回去必须用 `Queue` 等机制：

```python
import multiprocessing as mp

def producer(queue):
 for i in range(3):
 queue.put(i)
 queue.put(None) # 哨兵值表示"生产结束"

 def consumer(queue):
 while True:
 item = queue.get
 if item is None:
 break
 print("消费:", item)

 if __name__ == "__main__":
 q = mp.Queue
 p1 = mp.Process(target=producer, args=(q,))
 p2 = mp.Process(target=consumer, args=(q,))
 p1.start; p2.start
 p1.join; p2.join
```

| 机制 | 特点 | 适用 |
| --- | --- | --- |
| `Queue` | 进程安全、可传任意可 pickle 对象、内部自带锁 | 生产者-消费者，最常用 |
| `Pipe` | 更轻量，两端 `send` / `recv` | 只有两个进程通信 |
| `Value` / `Array` | 共享内存，快但要自己加锁 | 共享计数器、大数组 |
| `Manager.dict/list` | 代理对象实现"像共享变量"，方便但慢 | 结构复杂、性能不敏感 |

> `Queue` 里的元素必须能被 `pickle` 序列化，所以 lambda、打开的文件对象、socket 都传不过去。

## 3. 常见坑
| 坑 | 现象 | 原因 | 正确做法 |
| --- | --- | --- | --- |
| `target=worker` | `TypeError: 'NoneType' object is not callable` | 加了括号先把函数执行了，把返回值当成了任务 | 写 `target=worker` |
| 忘记 `if __name__ == "__main__":` | Windows 上子进程无限递归创建，程序卡死或报错刷屏 | spawn 会重新 import 主模块并再次执行启动代码 | 把 `Process(...).start` 放进 `__main__` 保护块 |
| 单参数写成 `args=(5)` | `TypeError: argument after * must be an iterable` 或参数被拆开 | `(5)` 是整数不是元组 | 写 `args=(5,)` |
| 边 start 边 join | 总耗时等于串行累加，没有并发效果 | `join` 会阻塞到该子任务结束 | 先循环 `start`，再循环 `join` |
| 想在进程里改全局变量 | 主进程看不到修改 | 进程有独立地址空间 | 用 `Queue` / `Pipe` / `Manager` 回传 |
| 共享计数器不用锁 | 偶尔出现"少了"的结果 | `+=` 是"读-改-写"三步，非原子 | `with lock:` 包住整个读改写 |
| 用 GIL 当线程安全的理由 | 数据偶尔错乱 | GIL 只在字节码间切换，不保证语句原子性 | 所有跨线程共享的可变状态都要保护 |
| `daemon=True` 设置在 `start` 之后 | `RuntimeError: cannot set daemon status of active thread` | daemon 只能在启动前设置 | 在构造参数里写 `daemon=True` |
| daemon 进程里再创建子进程 | `AssertionError: daemonic processes are not allowed to have children` | Python 的硬性限制 | 需要派生任务就别用 daemon |
| 用 `terminate` 收尾 | 僵尸进程 / 数据丢失 / 资源未释放 | 强杀不走清理逻辑 | 优雅退出：发哨兵值到 Queue 或设 `Event` |
| 线程里抛异常 | 主线程完全不知道，任务静默失败 | 子线程异常不会传播到主线程 | 在任务函数内 `try/except` 并记录；或用 `future.result` 取异常 |
| 死锁 | 程序卡住不响应 | 两个锁交叉获取，或同线程重复获取 `Lock` | 固定加锁顺序；可重入用 `RLock`；用 `with` 保证释放 |
| 线程数开太多 | 切换开销大，反而更慢 | 线程切换有成本，且受 GIL 限制 | I/O 密集用线程池（几十~几百），CPU 密集用进程池（≈核数） |
| `Queue` 传不可 pickle 对象 | `TypeError: cannot pickle '_thread.lock' object` | 跨进程序列化 | 只传基础类型/可 pickle 数据；或用 `Manager` |
| 子进程打印顺序混乱 | 输出交错甚至丢失 | 多进程 stdout 缓冲各自独立 | 加 `flush=True`，或写日志文件统一收集 |
| 在 Windows 上测多进程耗时却比串行慢 | 小任务反而更慢 | spawn 要重新启动解释器并 import 模块，开销大 | 任务粒度要够大；或改用进程池复用进程 |

## 4. 面试问答
<details><summary>参考答案</summary>

**Q1：进程和线程有什么区别？Python 里怎么选？**

本质区别：**进程是资源分配的基本单位，线程是 CPU 调度的基本单位**。一个进程拥有独立的地址空间、文件句柄等资源；线程共享所属进程的全部资源，只是各自有独立的栈和寄存器。

| 对比项 | 进程 | 线程 |
| --- | --- | --- |
| 内存 | 独立 | 共享 |
| 通信 | 需 IPC | 直接读写变量 |
| 开销 | 大 | 小 |
| 崩溃影响 | 隔离 | 可能拖垮整个进程 |
| 并行能力 | 能用多核 | 受 GIL 限制 |
| 稳定性 | 强 | 弱 |

选型规则：**CPU 密集型（数值计算、加解密、图像处理）用多进程**，因为只有多进程能绕过 GIL 用满多核（实测 4 份计算任务：串行 2.831s → 多进程 1.649s）；**I/O 密集型（网络请求、文件/数据库读写）用多线程或协程**，因为等待时 GIL 会被释放（实测 6 份 sleep 任务：串行 2.403s → 多线程 0.401s，快 6 倍）。高并发 I/O 场景协程（`asyncio`）比线程更省资源。

</details>

<details><summary>参考答案</summary>

**Q2：什么是 GIL？它为什么存在，有什么影响？**

GIL（Global Interpreter Lock）是 CPython 解释器级别的互斥锁，保证**同一时刻只有一个线程执行 Python 字节码**。

为什么存在：CPython 用引用计数做内存管理，`ob_refcnt` 的增减必须原子，否则多个线程可能同时释放同一对象造成崩溃；用一把全局锁比给每个对象加细粒度锁实现简单得多，也保护了 C 扩展（numpy 等）的兼容性，并让单线程性能更好。

影响：① **CPU 密集型多线程无法并行**，多线程做纯计算基本不提速；② **I/O 密集型不受影响**，因为 I/O 阻塞前解释器会主动释放 GIL；③ 想用多核做计算必须用多进程（或 C 扩展、`numpy` 这类在计算过程中释放 GIL 的库）。

**最重要的一点**：GIL 不等于线程安全。GIL 只在字节码切换点（默认 5ms 或每 N 条指令）生效，`x += 1` 这类操作由多条字节码组成，中间可能被打断，所以共享可变状态依然必须用锁保护。补充：CPython 3.13 起有实验性的 free-threaded 构建（PEP 703）在推进去除 GIL，但生产环境主流仍是带 GIL 的解释器。

</details>

<details><summary>参考答案</summary>

**Q3：什么是竞态条件？怎么避免？**

竞态条件是**多个执行单元（线程/进程）以不确定的顺序访问同一共享资源，导致结果依赖调度时机**的现象。它出现的三个条件：① 有共享状态；② 有"读-改-写"这类非原子操作；③ 缺少互斥保护。

典型例子就是"取款"：两个线程都先检查 `balance >= 60` 成立，然后各自扣款，最终余额变成 `-20`。本机实测无锁结果为 `-20`，加锁后为 `40`。

避免手段：

1. **加锁**（`threading.Lock` + `with`）——最直接，注意锁的粒度要覆盖"检查+修改"整个临界区，并且固定加锁顺序以避免死锁；
2. **不用共享可变状态**——消息传递（`Queue`）、函数式风格（传入数据、返回新数据）、每个线程持有独立副本；
3. **用原子/线程安全的数据结构**——`queue.Queue`、`collections.deque` 的 `append/popleft`；
4. **减少共享粒度**——用 `threading.local` 给每个线程独立数据；
5. **换模型**——多进程天然隔离，或 `asyncio` 单线程事件循环里"不主动让出就不切换"。

要注意的是：竞态往往是**偶发**的，单元测试很难稳定复现，所以设计阶段就要避免共享状态，而不是指望测试发现问题。

</details>

## 5. 自测题
<details><summary>1. 下面代码有什么问题？</summary>
```text
import multiprocessing as mp
import time

def work:
 time.sleep(2)
 print("子进程完成")

p = mp.Process(target=work)
p.start
print("主进程结束")
```
在 Windows 上运行会因为缺少 `if __name__ == "__main__":` 保护而失控：spawn 启动子进程时会重新 import 这个模块，于是子进程又执行 `p.start`，无限递归创建进程。

正确写法：
```text
import multiprocessing as mp
import time

def work:
 time.sleep(2)
 print("子进程完成")

if __name__ == "__main__":
 p = mp.Process(target=work)
 p.start
 p.join
 print("主进程结束")
```
另外注意：即便没加 `join`，主进程默认也会**等待**子进程结束才退出，所以这里看不到"主进程先结束"的效果。

</details>

<details><summary>2. 为什么在子进程里修改全局列表，主进程看不到？线程呢？</summary>

因为进程有**独立的地址空间**。创建子进程时，操作系统给子进程一套独立的内存（Linux `fork` 是写时复制，Windows `spawn` 是重新启动解释器并 import 模块），所以"同名的全局变量"在两个进程里是两个不同的对象，互不影响。实测：子进程 `append` 后主进程的列表仍为初始值。要在进程间传数据必须用 `Queue` / `Pipe` / `Manager` / 共享内存。

线程则共享同一个进程的堆和全局命名空间，所以子线程的修改对主线程立即可见。代价就是要自己处理竞态。

</details>

<details><summary>3. 什么时候应该用进程池而不是手动 `Process`？池大小怎么定？</summary>

应该在**任务数量多、单个任务粒度小、需要复用执行单元**时用池。手动 `Process` 每创建一个进程都要付出启动 + 模块 import + 资源初始化的成本（Windows spawn 尤其明显），如果任务是"1000 个小文件的解析"，逐个 `Process` 的开销可能远大于收益。进程池预先起好固定数量的工作进程，用队列派发任务，开销被摊薄；同时 `concurrent.futures` 还提供 `map` / `as_completed` / `future.result` 的异常与超时处理。

池大小的经验值：

| 任务类型 | 建议池大小 |
| --- | --- |
| CPU 密集（进程池） | `os.cpu_count` 或 `cpu_count - 1` |
| I/O 密集（线程池） | 远大于核数，常见 20~200，按目标服务的 QPS 和延迟调 |
| 混合型 | 分开两个池，或先 profiling 再定 |

再往上就是"别自己调优"的领域：压力测试 + 观测（响应时间、CPU 利用率、队列长度）才是最终依据。

</details>

<details><summary>4. 为什么 `p.terminate` 不推荐？有哪些替代方案？</summary>

`terminate` 直接向进程发终止信号，子进程**没有机会**执行 `finally`、`__exit__`、写日志、关闭文件、提交事务，可能留下：僵尸进程、损坏的临时文件、未释放的锁/端口、写到一半的数据。要注意：`terminate()` 不会给子进程清理资源的机会，容易留下僵尸进程。

替代方案：

1. **协作式退出**：用 `multiprocessing.Event` 作为"停止标志"，工作循环里定期检查 `event.is_set`，然后自然 return；
2. **哨兵值**：向 `Queue` 里 put 一个 `None`，消费者读到就退出；
3. **`daemon=True`**：允许主进程退出时回收，但适合"允许被杀"的背景任务；
4. **超时 + 优雅降级**：`p.join(timeout)` 超时后再记录日志并考虑升级处理；
5. **用 `concurrent.futures`**：`future.cancel` 只能在任务未开始前取消，配合 `as_completed(timeout=...)` 控制整体时限。

</details>
