# 文本预处理与分词全流程

> **一句话总结**：把「原始文本 → 模型可用的 token id」这条链路完整走通 —— 先分清字节、码位与字素簇，再做清洗与归一化，最后用 BPE / WordPiece / Unigram 切成子词；并回答一个关键问题：为什么现代 NLP 放弃了词级分词。
>
> **前置知识**：Python 字符串与 `re` 模块；正则表达式；神经网络需要整数 id（embedding 查表）；Transformer 的 `attention_mask` 概念。
>

> 1. 看一眼乱码文本，就判断出是编码问题、归一化问题还是分词问题；
> 2. 手写可运行的 BPE 训练 + 编码器，并说清 WordPiece、Unigram 与它的差异；
> 3. 正确配置 `padding` / `truncation` / `attention_mask`，避开 padding 侧与 `max_length` 的坑；
> 4. 估算一段文本的 token 数、显存与 API 费用量级，并解释词表与特殊 token 的设计取舍。

---

## 1. 为什么需要它
模型看不到文字，只看到整数 id。这条链路任何一环出错，损失都是**静默**的：不报错、不崩溃，指标只是莫名其妙掉几个点。

### 1.1 词级分词（word-level tokenization）的三个死穴

| 痛点 | 具体表现 | 量级 |
| --- | --- | --- |
| OOV（out-of-vocabulary） | 没见过的词只能映射成 `[UNK]`，信息归零 | 形态丰富语言（土耳其语、芬兰语）测试集 OOV 率可达 5% ~ 30% |
| 词表爆炸 | 想减少 OOV 就得把屈折形式、拼写变体全塞进词表 | 100 万词的 embedding：1e6 × 768 × 4 B ≈ **2.86 GiB**，只为存一张表 |
| 长尾稀疏 | 只出现 1~2 次的词，embedding 基本学不出语义 | Zipf 定律：语料中绝大多数词都在长尾 |

而且「词」这个概念本身就不牢靠：中文没有空格，`研究生物` 是 `研究/生物` 还是 `研究生/物`？德语会造复合词（`Lebensversicherungsgesellschaft`），日语没有分词边界。**让分词结果决定模型的输入单元，等于把一个语言学难题塞进了工程链路。**

### 1.2 一个具体的失败案例
朴素流水线 `text.lower.split()` → 查词表。训练集里出现过 `Café` 与 `café`，测试集来的是 `cafe\u0301`：

- `café`（U+00E9，1 个码位）与 `cafe\u0301`（`e` + 组合重音，2 个码位）**肉眼完全一样**，`==` 却返回 `False`；
- 词表里只会存其中一种写法，另一种必然落到 `[UNK]`；
- 同一个词在训练集里被拆成两个稀疏 key，语义各学一半。

这不是假想：macOS 返回的文件名默认是 NFD（分解形式），Windows / Linux 多为 NFC（预组合形式），跨平台抓取的数据天然混着两种写法。所以需要一条**确定性、尽量可逆、对未见词友好**的流水线。

## 2. 核心思想

```text
原始 bytes → [解码] str → [清洗 去 HTML/URL/控制符/零宽字符]
 → [归一化 NFKC / 大小写 / 全半角] → [可选中文分词 jieba+HMM]
 → [子词分词 BPE / WordPiece / Unigram] → [查词表] token id
 → [截断 + padding] 配 attention_mask → 模型
```

三条原则：**归一化在前、分词在后**（否则同一个词有多种切法）；**尽量无损可逆**（`decode(encode(x))` 能还原，方便定位问题）；**训练与推理用同一个分词器、同一版本**（分词器是模型的一部分）。

### 2.1 编码层：四个「长度」概念
「这个字符串有多长」有四种答案，混用就会出错。

| 层级 | 定义 | Python 里怎么数 | `é` | `e`+U+0301 | `👩‍👩‍👧‍👦` |
| --- | --- | --- | --- | --- | --- |
| byte | UTF-8 编码单元 | `len(s.encode("utf-8"))` | 2 | 3 | 25 |
| code unit | UTF-16 编码单元（JS/Java 的 `length`） | `len(s.encode("utf-16-le")) // 2` | 1 | 2 | 11 |
| code point | Unicode 码位 | `len(s)` | 1 | 2 | 7 |
| grapheme cluster | 用户感知的「一个字」 | 需 `regex` 的 `\X` | 1 | 1 | 1 |

`👩‍👩‍👧‍👦` 由 4 个 emoji + 3 个 ZWJ（U+200D）组成：7 个码位、11 个 UTF-16 单元、25 字节，但用户只当它是 1 个字。推论：`len(s)` 在中文里约等于字数，在 emoji 与组合字符上完全不可靠；前端 `maxlength="10"` 数的是 UTF-16 单元，与后端 `len(s)` 不是一回事；按字符截断必须按 grapheme cluster 切，否则会把 `é` 截成孤立的 `e`。

```python
import unicodedata as ud

pre, dec = "caf\u00e9", "cafe\u0301" # NFC 预组合 vs NFD 分解
print(len(pre), len(dec)) # 4 5 —— 长度不同
print(pre == dec) # False —— 码位序列不同
print(ud.normalize("NFC", pre) == ud.normalize("NFC", dec)) # True
for ch in ["A", "中", "é", "👍"]:
 print(repr(ch), hex(ord(ch)), len(ch.encode("utf-8"))) # 1 / 3 / 2 / 4 字节
family = "\U0001F469\u200D\U0001F469\u200D\U0001F467\u200D\U0001F466"
print(len(family), len(family.encode("utf-8")), # 7 码位 / 25 字节
 len(family.encode("utf-16-le")) // 2) # 11 UTF-16 单元
```

要点：`ud.normalize("NFC", s)` 只做**规范等价**，不会展开 `ﬁ` 这类连字；`s.encode("utf-8")` 才是磁盘 / HTTP 上的真实字节（中文 3 字节、emoji 4 字节）；`ud.combining(ch)` 非 0 只说明是组合记号，不等于「独立字符」。

### 2.2 清洗与归一化

| 形式 | 全称 | 做什么 | 典型效果 |
| --- | --- | --- | --- |
| NFC | Canonical Composition | 规范等价 + 尽可能组合 | `e`+`U+0301` → `é` |
| NFD | Canonical Decomposition | 规范等价 + 拆开 | `é` → `e`+`U+0301` |
| NFKC | Compatibility Composition | 兼容等价 + 组合 | `ＡＢＣ`→`ABC`，`①`→`1`，`㍿`→`株式会社` |
| NFKD | Compatibility Decomposition | 兼容等价 + 拆开 | `km²`→`km2`，`ﬁ`→`fi` |

**NFKC 是 NLP 里最常用的形式**（统一全角、连字、上下标、罗马数字），但它**不是无损的**：兼容等价会把原本语义不同的字符画上等号。中文场景尤其要注意 `ud.normalize("NFKC", "，") == ","`，全角标点会被换成半角 ASCII。

```python
import re, html
import unicodedata as ud

raw = ("<p>限时 5 折&nbsp;仅需&nbsp;<b>￥3.5</b>！</p> ""官网 https://a./x?y=1 活动\u200b截止 12\u202f月\ufeff1 日\x07")
text = html.unescape(raw) # &nbsp; -> \xa0
text = re.sub(r"<[^>]+>", "", text) # 去 HTML 标签
text = re.sub(r"https?://\S+|www\.\S+", " <URL> ", text) # URL 占位，别直接删
text = "".join(ch for ch in text if ud.category(ch)[0] != "C") # 去控制符 / 零宽字符
text = re.sub(r"\s+", "", text).strip() # 合并空白
print(text) # 限时 5 折 仅需 ￥3.5 ！ 官网 <URL> 活动截止 12 月1 日
print(ud.normalize("NFKC", text).lower()) # 限时 5 折 仅需 ¥3.5 ! 官网 <url> 活动截止 12 月1 日
```

`\u200b`（零宽空格）、`\ufeff`（BOM）、`\u00ad`（软连字符）的类别都是 `Cf`，**`str.strip()` 与 `str.split()` 都拿它们没办法**（`isspace` 为 `False`），混进词里就会造出一个词表里不存在的「新词」。

**清洗过度导致信息丢失**（这一栏比「怎么清洗」更值得记住）：

| 过度操作 | 丢掉了什么 | 后果 |
| --- | --- | --- |
| 删除全部标点 | 否定、语气、句边界 | `好，但是太贵了！` → `好但是太贵了`，情感极性可能反转 |
| 删除数字中的 `.` | 数值语义 | `3.5 折` → `35 折`；`v1.2` → `v12` |
| 全局 NFKC | 全角标点、圈号、上标 | `①`→`1` 丢失顺序标记；`km²`→`km2`；中文 `，`→`,` |
| 全局 `lower` | 大小写携带的类别信息 | `Apple`（公司）vs `apple`（水果）；`US`→`us`；`mAh`→`mah` |
| 删除停用词 | 否定词、程度副词 | `not good` → `good`；`非常不好` → `不好` |

经验法则：**清洗规则要么由验证集指标证明有效，要么不进流水线**。标注数据不足时宁可保留噪声，也不要删掉语义。

### 2.3 分词粒度对比

| 维度 | 字符级 char | 词级 word | 子词级 subword |
| --- | --- | --- | --- |
| 词表大小 | 100 ~ 5k | 100k ~ 数百万 | 30k ~ 200k |
| OOV | 几乎不存在（新字符除外） | 5% ~ 30%+ | 字级约 0；byte-level 严格为 0 |
| 序列长度 | 最长（英文 1 词 ≈ 5 字符） | 最短 | 居中，约为字符级的 1/2 ~ 1/3 |
| 语义单元 | 太碎，单字符无独立语义 | 完整但稀疏 | 词根 / 词缀，可组合出未见词 |
| 典型代表 | char-CNN；未分词的中文 BERT | word2vec 词表 | BPE / WordPiece / Unigram |
| 主要代价 | 注意力开销按长度平方增长 | OOV + 词表爆炸 | 切分不确定，一词多切 |

一个反直觉的事实：**`bert-base-chinese` 的词表是字级的**（21128 个 token，绝大多数是单个汉字），靠 Whole Word Masking 补回词级信息。所以「中文 BERT 用子词分词」并不准确 —— 是「现代多语言 / 生成式模型普遍用子词」。

### 2.4 为什么主流方案放弃了词级分词
1. **OOV 无解**：开放词表永远装不下所有词；子词把未见词拆成已知片段（`un` + `happy` + `ness`），至少保留部分语义。
2. **词表大小与覆盖率解耦**：子词用 3 万 ~ 20 万 token 就能覆盖几乎任意文本，且与语言数量无关。
3. **形态学友好**：`play / plays / played / playing` 共享 `play`，参数共享，长尾也能学到。
4. **多语言共享一套词表**：mBERT / XLM-R 覆盖 100+ 语言，靠的就是子词片段。
5. **免去语言学预处理**：不用词典、不用分词标准、不依赖空格，中日泰文一视同仁 —— 这是 SentencePiece 的核心卖点。
6. **效率折中**：相比字符级，子词把序列缩短 2~3 倍，注意力 O(n²) 与推理成本显著下降。

## 3. 最小可运行示例
以下是**只用标准库**的极简 BPE（byte-pair encoding）：训练 + 编码 + 解码，逻辑与 Sennrich 2016 的原始算法一致。

```python
from collections import Counter

END = "</w>" # 词尾标记：让 BPE 区分词内后缀与词尾后缀

def pretokenize(text):
    """按空白预分词，每个词拆成字符序列，词尾补 END。"""
    corpus = Counter
    for word in text.lower.split():
        corpus["".join(word) + "" + END] += 1
        return corpus

    def get_stats(corpus):
        """统计所有相邻符号对的频次（按词频加权）。"""
        stats = Counter
        for symbols, freq in corpus.items():
            syms = symbols.split()
            for a, b in zip(syms, syms[1:]):
                stats[(a, b)] += freq
                return stats

            def merge_pair(corpus, pair):
                """把语料中出现过的 pair 全部合并成新符号。"""
                pattern, repl = "".join(pair), "".join(pair)
                return {symbols.replace(pattern, repl): freq for symbols, freq in corpus.items()}

            def train_bpe(text, num_merges):
                """训练：反复选频次最高的相邻对合并，记录合并顺序。"""
                corpus, merges = pretokenize(text), []
                for _ in range(num_merges):
                    stats = get_stats(corpus)
                    if not stats: # 已合并成整词
                        break
                    pair = max(stats, key=lambda p: (stats[p], p)) # 同分按字典序，保证可复现
                    corpus = merge_pair(corpus, pair)
                    merges.append(pair)
                    return merges

                def encode(word, merges):
                    """编码：按训练顺序，对新词依次套用每条合并规则。"""
                    symbols = list(word.lower()) + [END]
                    for pair in merges:
                        out, i = [], 0
                        while i < len(symbols):
                            if i + 1 < len(symbols) and (symbols[i], symbols[i + 1]) == pair:
                                out.append("".join(pair))
                                i += 2 # 命中就吞掉两个符号
                            else:
                                out.append(symbols[i])
                                i += 1
                                symbols = out
                                return symbols

                            def decode(tokens):
                                return "".join(tokens).replace(END, "").strip()

                            if __name__ == "__main__":
                                corpus_text = "low " * 5 + "lower " * 2 + "newest " * 4 + "widest " * 3 + "new " * 3
                                merges = train_bpe(corpus_text, num_merges=8)
                                for step, (a, b) in enumerate(merges, 1):
                                    print(f"merge {step:2d}: {a!r} + {b!r} -> {a + b!r}")
                                    print("vocab size:", len({c for c in corpus_text.lower() if not c.isspace} | {END}
                                    | {"".join(m) for m in merges}))
                                    for word in ["lowest", "newest", "widest", "slow"]:
                                        toks = encode(word, merges)
                                        print(f"encode({word!r}) = {toks} decode -> {decode(toks)!r}")
```

实际运行输出（Python 3.12，纯标准库）：

```text
merge 1: 'w' + '</w>' -> 'w</w>'
merge 2: 't' + '</w>' -> 't</w>'
merge 3: 's' + 't</w>' -> 'st</w>'
merge 4: 'n' + 'e' -> 'ne'
merge 5: 'l' + 'o' -> 'lo'
merge 6: 'e' + 'st</w>' -> 'est</w>'
merge 7: 'lo' + 'w</w>' -> 'low</w>'
merge 8: 'w' + 'est</w>' -> 'west</w>'
vocab size: 19
encode('lowest') = ['lo', 'west</w>'] decode -> 'lowest'
encode('newest') = ['ne', 'west</w>'] decode -> 'newest'
encode('widest') = ['w', 'i', 'd', 'est</w>'] decode -> 'widest'
encode('slow') = ['s', 'low</w>'] decode -> 'slow'
```

**逐行说明**：

| 代码 | 作用 | 容易误解的点 |
| --- | --- | --- |
| `END = "</w>"` | 词尾标记 | 没有它 `est` 无法区分词尾（`newest`）与词中；GPT-2 用 `Ġ` 表示词首空格，思路相同 |
| `pretokenize` | 统计词频并把词拆成字符 | 生产环境要先归一化，否则 `Café` 与 `cafe\u0301` 会变成两条记录 |
| `get_stats` | 统计相邻符号对频次 | 频次要**按词频加权**，不是按出现次数 |
| `merge_pair` | 用 `str.replace` 全局替换 | 符号内部不含空格，所以 `"a b"` 只会匹配两个相邻的完整符号，不会误伤 |
| `max(stats, key=...)` | 取频次最高的对 | 频次为整数，同分时顺序不定；加 `(stats[p], p)` 做二级排序才可复现 |
| `merges.append(pair)` | 保存合并顺序 | **合并顺序既是词表 id 的生成顺序，也是编码时的套用顺序**，丢了就无法复现 |
| `encode` 外层 `for pair` | 按训练顺序套用规则 | 不是「重跑训练」，只用有序的 merges 列表；未登录字符自然退化为单字符 |
| `decode` | 拼回字符串 | `</w>` 换回空格即近似无损；真实 tokenizer 用 metaspiece `▁` 保证严格可逆 |

## 4. 深入机制
### 4.1 BPE 完整算法
BPE 原本是 1994 年的**数据压缩**算法（Gage），Sennrich 等人 2016 年把它搬到 NMT 上做子词切分。

**训练**：预分词、统计词频，每个词表示成字符序列 + 词尾标记 → 统计所有相邻符号对频次 → 取最高频的一对合并成新符号，并把 `(a, b)` 追加到 merges → 回到统计，重复 `k` 次。**编码**：把新词拆成字符，**按 merges 的顺序**逐条套用合并规则。复杂度上，朴素实现每轮合并后重扫全部语料为 O(k · N)；`tokenizers` 用优先队列 + 并查集把每轮降到接近 O(N log N)，并支持并行。

工程要点：**`k` 决定词表大小**（`vocab_size = 初始符号数 + k`，GPT-2 是 50257，BERT 是 30522，Llama-3 是 128256）；**byte-level BPE** 把文本先切成 UTF-8 字节、初始符号固定为 256 个字节，因此永远不会 OOV，emoji 与罕见汉字都能用字节表示，代价是中文一个汉字可能占 2~3 个 token；**预分词很关键**，GPT-2 用正则把 `'s`、`'t` 等缩写单独切块，避免 BPE 跨词合并出短语级符号；**推理切分不唯一**，训练出的 merges 只给出一种确定切分，这正是 Unigram 想解决的问题。

### 4.2 WordPiece：用似然替代频次
WordPiece 由 Google 在 NMT 中提出（Wu et al. 2016），BERT 用的就是它。与 BPE 有两点差异。

**差异一：合并准则不是频次，而是似然提升**，实现上为打分函数 `score(a, b) = freq(ab) / (freq(a) * freq(b))`，选得分最高的一对合并。直觉：`freq(ab)` 大说明常见，`freq(a) * freq(b)` 大说明 a、b 各自本来就常见（合并收益低）。这个比值接近互信息，所以 WordPiece 更愿意合并「共同出现但各自并不常见」的片段（如 `qu`、`##ing`），而 BPE 会先把 `e`、`s` 这种高频字符组掉。

**差异二：词内前缀 `##`** 标记「该子词不是词首」。**推理时是贪心最长匹配**（不是 BPE 的按序合并）：从词首开始找词表里存在的最长子串；一个都匹配不上就整个词输出 `[UNK]`。

```python
def wordpiece(word, vocab, max_len=20):
    """vocab 里的续接子词自带 '##' 前缀，查表时必须补上前缀。"""
    tokens, start = [], 0
    while start < len(word):
        end, hit = min(len(word), start + max_len), None
        while start < end: # 从最长往最短试
            piece = word[start:end]
            key = piece if start == 0 else "##" + piece
            if key in vocab:
                hit, break_end = key, end
                break
            end -= 1
        else:
            tokens.append("[UNK]") # 一个子词都匹配不上
            break
        tokens.append(hit)
        start = break_end
        return tokens

    vocab = {"un", "##want", "##ed", "play", "##ing", "low", "##est", "##er", "new"}
    for w in ["unwanted", "playing", "lowest", "lower", "xyzzy"]:
        print(f"{w:10} -> {wordpiece(w, vocab)}")
        # unwanted -> ['un', '##want', '##ed'] playing -> ['play', '##ing']
        # lowest -> ['low', '##est'] lower -> ['low', '##er']
        # xyzzy -> ['[UNK]'] 词表外整词兜底
```

坑点：**查表要带 `##` 前缀**。只比较 `word[start:end]` 而不补前缀，`lowest` 会被切成 `low` + `[UNK]` —— 这个 bug 极其常见，且只在小的玩具词表上才会暴露。

### 4.3 Unigram LM：概率模型 + EM + Viterbi
Kudo 2018 的 Subword Regularization 提出 Unigram 语言模型分词，也是 SentencePiece 的另一种工作模式。**模型假设**：每个子词独立，句子 `x = (x₁, x₂, …, xₘ)` 的概率是各子词概率之积 `P(x) = Π p(xᵢ)`，且 `Σ_{w ∈ V} p(w) = 1`。

**训练用 EM**：
1. **初始化**：用较大的种子词表（BPE 或后缀数组枚举高频子串），给每个子词初始概率；
2. **E 步**：对每句话用前向-后向（或 Viterbi 近似）枚举所有切分，算出每个子词的**期望出现次数**；
3. **M 步**：用期望次数重新归一化，得到新的 `p(w)`；
4. **剪枝**：每轮按「删掉它损失多少似然」排序，删掉最不划算的一批子词（论文用 α 控制裁剪比例），直到达到目标词表大小。

**推理用 Viterbi**：在所有切分中找概率最大的路径（取对数后即最大和问题）。**子词正则化**（subword regularization）：训练时不用最优切分，而是按 `P(x)` **采样**若干切分（forward-filtering backward-sampling），相当于对分词做数据增强，让模型不依赖某一种切分 —— 这也是「同一句话两次 tokenize 结果不同」的来源，推理时必须关掉采样。

```python
import math

def viterbi(text, logp, unk_logp):
    """在给定子词对数概率下，找概率最大的切分（DP + 回溯）。"""
    n = len(text)
    best = [(-math.inf, 0)] * (n + 1) # best[i] = (到位置 i 的最优对数概率, 前驱)
    best[0] = (0.0, 0)
    for end in range(1, n + 1):
        for start in range(end):
            score = best[start][0] + logp.get(text[start:end], unk_logp)
            if score > best[end][0]:
                best[end] = (score, start)
                tokens, cur = [], n
                while cur > 0: # 回溯出切分
                    prev = best[cur][1]
                    tokens.append(text[prev:cur])
                    cur = prev
                    return tokens[::-1]

                probs = {"low": 0.20, "lo": 0.10, "l": 0.05, "o": 0.05, "w": 0.05, "e": 0.05, "s": 0.05,
                "t": 0.05, "wes": 0.08, "est": 0.10, "west": 0.12, "lowest": 0.05}
                logp = {k: math.log(v) for k, v in probs.items()}
                unk = math.log(1e-6) # 未登录子词的兜底概率
                for w in ["lowest", "lowestest", "west"]:
                    pieces = viterbi(w, logp, unk)
                    print(f"{w:10} -> {pieces} score={sum(logp.get(p, unk) for p in pieces):.3f}")
                    # lowest -> ['lowest'] score=-2.996
                    # lowestest -> ['lowest', 'est'] score=-5.298
                    # west -> ['west'] score=-2.120
```

`lowest` 的多种切分（`lowest`、`low`+`est`、`l`+`o`+`west`）都在候选里，Viterbi 选概率乘积最大的那条；把 `lowest` 的概率调低一点，结果就会切换到 `['low', 'est']`。

### 4.4 SentencePiece 的工程价值
Kudo & Richardson 2018。它把「归一化 + 分词 + 反分词」打包成一个**语言无关**的黑盒：

| 特性 | 解决的问题 |
| --- | --- |
| 直接吃原始文本（raw text） | 不需要预先按空格分词，中日泰文与英文同一套流程 |
| 内置 normalizer | 归一化规则随模型一起保存（NFKC、去控制符、自定义规则），训练推理一致 |
| 无损可逆 | 用 metaspiece `▁`（U+2581）表示空格，`decode(encode(x))` 能严格还原原文 |
| 两种模型可选 | `model_type` 支持 `bpe` 与 `unigram`，同一套接口对比效果 |
| `byte_fallback` | 词表外字符退化为 UTF-8 字节序列，彻底消除 `[UNK]` |

`▁` 的巧妙之处：真空格会与「词边界」信息纠缠（清洗时容易被 `strip` 掉），换成可见的特殊符号后，分词器可以自己决定空格归属，反解码时再换回空格 —— 这就是「无损可逆」的实现方式。T5、ALBERT、XLM-R、Llama 系列都用了 SentencePiece。

### 4.5 中文分词
中文没有空格，且**分词标准不唯一**：`研究生物` 可以是 `研究/生物` 也可以是 `研究生/物`，`南京市长江大桥`、`乒乓球拍卖完了` 都是经典歧义。所以中文分词本质是一个**序列标注 / 词图寻优**问题。

```python
import jieba
import jieba.posseg as pseg

text = "我来到北京清华大学"
print("精确模式 :", list(jieba.cut(text))) # 默认，适合大多数下游任务
print("全模式 :", list(jieba.cut(text, cut_all=True))) # 所有可能词，有冗余，适合特征提取
print("搜索引擎模式:", list(jieba.cut_for_search(text))) # 长词再切细，提高召回，适合检索
jieba.add_word("杭研大厦") # 自定义词典：领域新词必须加，否则必被切错
print("加词典后:", list(jieba.cut("他来到了网易杭研大厦")))
print("词性标注:", [(w, flag) for w, flag in pseg.cut("深度学习模型部署")])
```

jieba 官方 README 的对照输出：`精确模式` = 我/ 来到/ 北京/ 清华大学；`全模式` = 我/ 来到/ 北京/ 清华/ 清华大学/ 华大/ 大学；`搜索引擎模式` = 我/ 来到/ 北京/ 清华/ 华大/ 大学/ 清华大学。

**jieba 的内部思路**：用前缀词典构建句子的 **DAG（有向无环图）**，枚举所有可能成词的切分；再用**动态规划**找「词频概率乘积」最大的路径，处理已知词与歧义；对 DAG 里未登录的单字片段，用 **HMM**（状态集 `B/M/E/S`，即 Begin/Middle/End/Single）跑 **Viterbi** 解码，处理新词。

**CRF 路线**：把分词、词性、NER 统一成序列标注，用线性链 CRF 建模标签转移（`B` 后不能直接接 `S` 这类约束天然被建模），配合特征模板做全局最优解码；深度时代则用 **BiLSTM-CRF / BERT-CRF**，CRF 层负责保证标签序列合法。

**中文为什么也需要子词分词**：词典方案永远有未登录词（网络新词、专有名词、中英混排），而 subword 天然兜底；分词错误会**传播**到所有下游任务，而子词切分不需要语言学正确，只需统计上高效；多语言模型想共用一套词表，就必须放弃「按中文词典切词」；实践中 `bert-base-chinese` 直接按字切效果已经不差，说明中文 token 粒度不一定要到「词」。

### 4.6 词表构建与特殊 token

| Token | 作用 | 备注 |
| --- | --- | --- |
| `[UNK]` | 词表外兜底 | byte-level / `byte_fallback` 之后基本用不到 |
| `[CLS]` | BERT 句首；其输出向量做句表示 | 只有 BERT 系（encoder-only）用 |
| `[SEP]` | 句子 / 片段分隔，句对任务的关键 | 句对输入为 `[CLS] A [SEP] B [SEP]` |
| `[PAD]` | 补齐到定长 | **必须让 `attention_mask` 屏蔽**，否则 attention 会算进无意义位置 |
| `[MASK]` | MLM 掩码占位 | 训练专用；推理阶段不应出现 |
| BOS / EOS | 生成起点 / 终点 | decoder-only 通常只用 BOS，或干脆不加 |

不同模型的约定差异（写代码时别硬编码）：

| 模型 | 句首 / 句尾 | 特殊 token 长相 |
| --- | --- | --- |
| BERT | `[CLS]` … `[SEP]` | `[CLS]` / `[SEP]` / `[PAD]` / `[MASK]` / `[UNK]` |
| RoBERTa | `<s>` … `</s>` | 没有 `[CLS]`，用 `<s>` 的向量做句表示 |
| GPT-2 | 无 BOS/EOS | 没有 `[PAD]`，需手动 `tokenizer.pad_token = tokenizer.eos_token` |
| T5 | 无 BOS，`</s>` 结尾 | 用 `<extra_id_0>` 做 span 掩码 |
| Llama-3 | `<\|begin_of_text\|>` | 对话模板里还有 `<\|start_header_id\|>` 等 |
| Qwen | `<\|im_start\|>` / `<\|im_end\|>` | Chat 模板必须走 `apply_chat_template` |

**词表构建流程**：领域语料（尽量贴近线上分布）→ 归一化（与推理一致）→ 训练 tokenizer（`vocab_size` / `min_frequency` / `special_tokens`）→ 评估（平均 token/词、OOV 率、长尾覆盖率）→ 保存（`tokenizer.json` / `vocab.txt` / `merges.txt` / `sentencepiece.model`）→ 与 checkpoint 一起版本化。

要点：**`vocab_size` 是取舍**，小词表导致序列长、注意力开销大，大词表导致 embedding 参数多、长尾 token 训练不足，30k ~ 128k 是当前常见区间；**特殊 token 的 id 必须固定**且不会被切碎（`tokenizers` 里用 `AddedToken` 注册并在训练前占位）；**改词表要同步改模型**，加了 token 必须 `model.resize_token_embeddings(len(tokenizer))`，且新 token 的 embedding 需要继续训练才有效。

## 5. 常见坑

| 坑 | 现象 | 原因 | 正确做法 |
| --- | --- | --- | --- |
| 把 token 当词 | 按词数估成本，与实际差 2~3 倍 | token 是子词片段：1 个英文词 ≈ 1.3 token，1 个汉字 ≈ 0.6~2 token | 用真实 tokenizer 数 token，别用字数 / 词数替代 |
| 忽略 `attention_mask` | 指标正常但生成结果随机；padding 越多越差 | `[PAD]` 参与了 attention 与 pooling，均值池化把 0 向量算进去 | 始终传 `attention_mask`；池化时按 mask 加权 |
| padding 侧选错 | 同一输入，单独推理与批量推理结果不一致 | decoder-only 是 causal attention + 位置编码，右侧 padding 会让真实 token 的位置与可见性随 batch 变化 | GPT 类设 `tokenizer.padding_side = "left"`；BERT 类右侧即可 |
| `padding="max_length"` 没给 `max_length` | 5 token 的句子被补到 512，费用翻百倍 | 默认取 `model_max_length` | 显式 `max_length=...`，或批量内用 `padding="longest"` |
| 清洗掉标点 | 情感分类 F1 掉点，否定句全判正 | `not good` → `good`；`3.5` → `35` | 保留标点或映射为专门 token；改动前先跑消融 |
| 忘了 `truncation` | 报 `Token indices sequence length is longer than...` 或静默截断 | 超 `model_max_length` 时行为取决于是否显式传参 | 显式 `truncation=True, max_length=...`；长文用滑窗 + stride |
| 训练 / 推理分词器不一致 | 离线实验好、上线掉点 | 训练脚本自带清洗，服务端直接调 `AutoTokenizer` | 把归一化写进 tokenizer（SentencePiece normalizer / `tokenizers` pipeline） |
| 分词器版本漂移 | 加载旧 checkpoint 时 id 对不上，输出乱码 | 词表文件被更新，id 顺序变了 | tokenizer 与权重绑定同一版本目录，一起发布 |
| 零宽字符残留 | 看似相同的两句话命中不同 id | `\u200b` `\ufeff` `\u00ad` 类别为 `Cf`，`strip` / `split` 不处理 | 清洗时按 `unicodedata.category(ch) == "Cf"` 显式删除 |
| 中文没做全半角统一 | `ＡＢＣ` 与 `ABC`、`１２３` 与 `123` 变成两套 id | 全角字符是独立码位 | `NFKC` 归一化（注意它会改全角标点） |

### 5.1 工程实践：`AutoTokenizer`
`tokenizers` 是 Rust 实现的高性能分词库，`transformers` 的 `AutoTokenizer` 是它的便捷封装。两者从同一个 `tokenizer.json` 加载，结果必须一致；若发现不一致，通常是加载参数（如 `add_special_tokens`）不同，而不是算法不同。

```python
from transformers import AutoTokenizer

tok = AutoTokenizer.from_pretrained("bert-base-chinese")
ids = tok.encode("自然语言处理很有趣", add_special_tokens=True) # 单条：只返回 ids
print(ids, tok.convert_ids_to_tokens(ids))

batch = tok.batch_encode_plus( # 等价于直接调用 tok(...)；padding/truncation 必须显式给
["这是一条比较长的样本文本" * 30, "短文本"],
padding="max_length", # "longest" | "max_length" | True | False
truncation=True, # 只截右边；句对可用 "only_first" / "only_second"
max_length=32, return_attention_mask=True, return_token_type_ids=False,
)
print({k: len(v[0]) for k, v in batch.items()})
print(batch["attention_mask"][1]) # 短句右侧补 0，告诉模型这些位置无效
print(tok.decode(batch["input_ids"][1], skip_special_tokens=True))
print("vocab:", tok.vocab_size, "| model_max_length:", tok.model_max_length)
```

| 参数 | 作用 | 易错点 |
| --- | --- | --- |
| `padding` | 补齐到等长 | `True` 只在批量输入下合法；`"max_length"` 必须配 `max_length` |
| `truncation` | 超长截断 | 默认只截右侧；选择题句对别把答案截掉 |
| `max_length` | 截断 / 补齐的目标长度 | 与 `tok.model_max_length`（模型上限）是两回事 |
| `return_attention_mask` | 返回有效位置掩码 | **永远打开**，尤其配合 padding 时 |
| `return_tensors` | 返回 `pt` / `tf` / `np` 张量 | 不装 torch 时传 `"pt"` 会直接报错 |
| `add_special_tokens` | 是否插入 `[CLS]` / `[SEP]` | 手工拼模板时必须设 `False`，否则特殊 token 重复 |

### 5.2 token 数与上下文 / 费用

```python
def budget(chinese_chars, english_words, tpc, tpw=1.3):
 """tpc：每个汉字平均占多少 token；tpw：每个英文单词平均占多少 token。"""
 return chinese_chars * tpc + english_words * tpw

# 以下为经验值，仅用于粗估量级，务必用真实 tokenizer 在自己的数据上实测
profiles = {"cl100k_base (GPT-3.5/4)": 1.5, "o200k_base (GPT-4o)": 1.0, "Llama-3 tiktoken": 1.6}
zh, en = 10_000, 10_000
for name, tpc in profiles.items():
 print(f"{name:24} {zh} 汉字 + {en} 英文词 ≈ {budget(zh, en, tpc):,.0f} tokens")
# cl100k_base (GPT-3.5/4) 10000 汉字 + 10000 英文词 ≈ 28,000 tokens
# o200k_base (GPT-4o) 10000 汉字 + 10000 英文词 ≈ 23,000 tokens
# Llama-3 tiktoken 10000 汉字 + 10000 英文词 ≈ 29,000 tokens
ctx, price_per_mtok = 128_000, 2.5 # 美元 / 百万 input token，按实际价格替换
print(f"128k 上下文 ≈ {ctx / profiles['o200k_base (GPT-4o)']:,.0f} 个汉字（纯中文，未扣输出）")
print(f"这批文本按 ${price_per_mtok}/1M tokens 计 ≈ ${budget(zh, en, 1.0) / 1e6 * price_per_mtok:.4f}")
```

结论：**上下文窗口是 token 数而不是字数**，128k 上下文在纯中文场景约放 10 万 ~ 13 万汉字（o200k 词表），换成 cl100k 只有 8 万左右；**成本按 token 计**，同一份中文材料换词表更适配中文的模型，token 数能差 30% ~ 50%，直接反映在账单上；估算时必须**给输出与多轮历史留额度**，多轮对话每轮都要重算完整历史，token 数随轮数近似平方增长。

## 6. 面试问答
**Q1：BPE 用频次选合并对，WordPiece 用什么？两者切分结果有什么本质差异？**

<details>
<summary>参考答案</summary>

WordPiece 用的是**似然提升**，实现上为 `score(a, b) = freq(ab) / (freq(a) * freq(b))`，选得分最高的一对合并 —— 这个比值接近点互信息，偏好「共同出现但各自并不常见」的片段，而不是 BPE 那种先把最高频字符组掉的策略。结果差异：BPE 容易产出高频但语义弱的片段（`e`、`est`），WordPiece 更倾向 `##ing`、`qu` 这类有构词意义的片段。

差异还体现在推理方式上：BPE 按训练得到的 merges 顺序逐条套用，结果是确定的；WordPiece 是贪心最长匹配，从词首找词表里存在的最长子串，这是 BERT 类 tokenizer 的默认行为。两者都基于词表做确定切分，这正是 Unigram 用概率模型 + 采样要打破的局限。

</details>

**Q2：为什么 GPT 系列用 byte-level BPE，而 BERT 用 WordPiece？byte-level 解决了什么？**

<details>
<summary>参考答案</summary>

byte-level BPE（GPT-2 起）把文本先按 UTF-8 编码成字节，初始符号集固定为 256 个字节，再做 BPE 合并。三个好处：**严格无 OOV**，任何字符串都能表示成字节序列，不需要 `[UNK]`；**词表干净**，不用为每种语言预留特殊处理；**可逆性好**，字节层可完全还原。

代价是**非 ASCII 语言的 token 效率下降**：一个汉字 UTF-8 占 3 字节，最坏要 3 个 token 表示一个字（实际会被合并成 1~2 个高频 token）。BERT 面向分类与抽取，用 WordPiece（30k 词表，多语言版 110k+）在序列长度与精度上更划算；GPT 面向开放域生成与多语言，选 byte-level 换取永不 OOV。

</details>

**Q3：为什么 padding 有左右之分？什么模型必须用左侧 padding？**

<details>
<summary>参考答案</summary>

关键在于 **causal attention + 位置编码**。decoder-only 模型生成时每个位置只能看见自己左侧的 token，且位置 id 由「第几个 token」决定。右侧 padding 下，批量生成时不同样本的真实 token 会被挤到不同位置，位置 id 与可见范围随 batch 内最长样本变化 —— 同一个请求单独推理和放进 batch 里推理，输出会不一致。

左侧 padding 时真实 token 始终**右对齐**，最后一个位置永远是真实 token，`past_key_values` 的切分与 position id 计算都稳定，所以 `tokenizer.padding_side = "left"` 是 decoder-only 批量生成的标配。BERT 类双向模型不存在方向性问题，右侧 padding 更自然，配合 `attention_mask` 屏蔽 `[PAD]` 即可。

</details>

**Q4：中文需要分词吗？jieba 分词和子词分词该怎么选？**

<details>
<summary>参考答案</summary>

分场景看，不是「必须」：

- **传统模型 / 检索 / 关键词抽取**：需要。TF-IDF、BM25、TextRank 以「词」为统计单元，要先用 jieba 切分；检索场景用搜索引擎模式（长词再切细）提高召回。
- **预训练语言模型**：通常**不需要显式分词**。`bert-base-chinese` 本身就是字级词表，BPE / Unigram 中文分词器也多以「字 + 高频多字词」混合切分。先 jieba 再喂 BERT 反而引入分词错误、让 OOV 变多。
- **自建中文子词词表**：领域术语密集（医疗、法律、金融）、文言文、大量中英混排时值得做，能显著缩短序列、减少 `[UNK]`，但词表要与模型一起训练（或 `resize_token_embeddings` 后继续预训练）。

分词歧义（`研究生物` / `南京市长江大桥`）在字级或子词模型里基本被绕过，这也是「中文必须分词」在现代 NLP 里被弱化的原因。

</details>

## 7. 自测题
1. `s = "cafe\u0301"`，`len(s)` 是多少？怎样让 `ud.normalize("NFC", s) == "café"` 成立，为什么它成立？
2. BPE 训练时把词尾标记 `</w>` 去掉会发生什么？举一个具体的切分错误例子。
3. 为什么 `padding="max_length"` 而不指定 `max_length` 可能让 API 费用暴涨 100 倍？
4. Unigram 训练为什么需要 EM？训练完成后为什么推理还要用 Viterbi？
5. 已知 `freq(a)=100, freq(b)=100, freq(ab)=20` 与 `freq(c)=2, freq(d)=2, freq(cd)=3`，WordPiece 优先合并哪一对？BPE 呢？

<details>
<summary>参考答案</summary>

1. `len(s) == 5`（`c a f e` + U+0301）。NFC 会把「基础字符 + 组合记号」按**规范等价**映射成预组合字符 `é`（U+00E9），两侧都变成 4 个码位且逐码位相等；NFKC 同样能达成，但会附带兼容映射的副作用。
2. 去掉 `</w>` 后 BPE 无法区分「词尾的 est」与「词中的 est」。例如 `newest` 学到的 `est` 会与 `estimate` 里的 `est` 共用一个符号，`newest` 可能被切成 `n` + `ew` + `est`（若 `ew` 在别处高频），词尾信息丢失、后缀语义被稀释。GPT-2 用 `Ġ`（前导空格）承担类似角色，SentencePiece 用 `▁`。
3. 不传 `max_length` 时它取 `tokenizer.model_max_length`（BERT 是 512，某些模型是 4096 甚至更大）。一句 5 个 token 的输入被补到 512，padding 部分同样计入 API 的输入 token 计费，成本放大约 100 倍，注意力算力也白付。
4. Unigram 的目标是最大化语料在**所有可能切分**下的边际似然，而切分是隐变量，无法直接求导 → 用 E 步算期望计数、M 步重估概率。推理时不再需要边际化，给定词表后只需在马尔可夫链上找**单条最优路径**，Viterbi（DP）即可，按最大子词长度截断后近似 O(n)。
5. WordPiece：`20 / (100 × 100) = 0.002` 对比 `3 / (2 × 2) = 0.75`，选 `(c, d)`。BPE 只看频次，选 `(a, b)`（20 > 3）。这就是两者最直观的区别 —— WordPiece 更愿意合并「两个都不常见但总一起出现」的片段。

</details>
