> **一句话总结**：微调面试不会考「什么是反向传播」，而是考**决策与归因**——为什么选 LoRA、α/r 怎么定、显存不够先看谁、SFT 之后模型变差该怪数据还是怪超参；能把「现象 → 假设 → 验证方法 → 修复动作」这条链讲完整的人，比背下 LoRA 公式的人更容易通过。
> **前置知识**：Transformer 基本结构、SFT 流程、LoRA/QLoRA 的原理、显存构成（权重/梯度/优化器状态/激活/KV cache）、常用评测指标。
> **学完能做到**：1. 用 30 秒答出 20 道高频题的主干，并能在追问下展开到工程细节；2. 按「现象 → 假设 → 验证 → 修复」四步回答任何故障类问题；3. 用一张速查表完成方法选型。

## 1. 面试答题总则

### 1.1 面试官在听什么

微调方向的面试题几乎都能归到三类：

| 类型 | 例子 | 面试官想确认 |
|---|---|---|
| 决策类 | 该用全参还是 LoRA？该不该微调？ | 你是否理解成本与收益的边界 |
| 参数类 | α/r 怎么调？学习率取多少？ | 你是否真的动过手，而不是只读过论文 |
| 归因类 | SFT 后变差了怎么办？loss 不降怎么办？ | 你能否在信息不全时给出可执行的排查顺序 |

绝大多数候选人栽在第三类：只答「调小学习率试试」，而没有先问「你是怎么变差的——是指标掉了、格式坏了、还是通用能力退化」。**归因类题目得分的关键是先诊断再开药。**

### 1.2 万能四步框架

任何「效果不好 / 出问题」类问题，都按这个顺序答：

```
① 现象：先明确「变差」的准确含义（哪个指标、掉了多少、分布有没有偏）
② 假设：列出 2~3 个最可能的原因，按先验概率排序
③ 验证：每个假设给一个能一次证伪的实验（成本从低到高）
④ 修复：给出对应的最小改动，并说明怎么确认修好了
```

### 1.3 核心概念速查

| 术语 | 一句话解释 |
|---|---|
| SFT | 用监督数据（指令-回答对）继续训练，让模型学会遵循指令与输出格式 |
| 全参微调（Full FT） | 更新全部参数，效果上限最高，显存与存储成本最高 |
| LoRA | 冻结主干，为权重矩阵加一个低秩旁路 `BA`，只训 `A`、`B` |
| QLoRA | 基座量化到 4-bit + LoRA，进一步压低显存（配合 NF4 双重量化与 paged optimizer） |
| Adapter | 在层间插入小模块，只训这些模块；有额外推理延迟 |
| Prefix / P-Tuning | 在输入或每层注入可学习的连续 prompt 向量 |
| 灾难性遗忘 | 微调后预训练阶段获得的能力下降 |
| 损失掩码（loss mask） | 只在需要监督的 token 位置计算 loss（多轮对话中只算 assistant） |
| packing | 把多条短样本拼进一个序列以提高利用率，必须配合正确的 position id 与 mask |
| 显存账本 | 权重 + 梯度 + 优化器状态 + 激活 + KV cache 五项之和 |

## 2. 第一组：概念与决策

### Q1. 微调到底在做什么？它和预训练、RAG、提示词工程分别解决什么问题？

<details markdown="1">
<summary markdown="1">参考答案</summary>

**30 秒版**：预训练是学语言与通用知识，微调是用少量监督数据把模型的**输出分布与行为**调整到特定任务上；提示词工程不改参数、只改上下文；RAG 是为模型补上它**不知道的、会过期的**外部知识。三者解决的是不同问题，经常组合使用。

**展开版**：

- **预训练**：在海量无标注语料上做自监督学习，获得语言能力与压缩在参数里的世界知识。它决定的是模型的**能力上限**。
- **微调（SFT）**：用指令-回答对继续训练，改变的是模型的**条件输出分布**——即「面对这类输入，应该输出什么形式和风格」。它擅长教格式、风格、领域语言、任务范式，不太擅长注入大量新事实。
- **提示词工程**：不改参数，靠指令、示例、格式约束引导模型。成本最低、迭代最快，但受限于基座模型已有能力，且无法保证输出格式的绝对稳定。
- **RAG**：把外部文档检索后塞进上下文。适合知识频繁更新、需要引用出处、知识量远超参数容量的场景。

**选型判断**：

| 需求 | 首选 |
|---|---|
| 模型不知道这个知识 | RAG |
| 模型知道但输出格式/风格不对 | 提示词工程 → 不够则 SFT |
| 需要固定格式、低延迟、可离线部署 | SFT（通常配 LoRA） |
| 需要引用出处、知识每天变 | RAG |
| 需要改变模型的行为偏好（更有礼貌、更少幻觉） | 偏好对齐（DPO/RLHF），不单是 SFT |

**追问预判**：
- *「SFT 能不能教新知识？」* —— 能，但效率很低。知识密集型内容更适合 RAG；SFT 教知识容易变成「背下来」，泛化差，还容易诱发幻觉。
- *「RAG 和微调能不能只用一种？」* —— 能，但要看瓶颈在哪。如果检索已经给出正确上下文而模型仍然答错，那是模型能力/格式问题，该微调；如果检索根本没召回正确文档，微调救不了。

</details>

### Q2. 什么时候必须全参微调，什么时候 LoRA 就够了？

<details markdown="1">
<summary markdown="1">参考答案</summary>

**30 秒版**：默认用 LoRA；只有在「数据量足够大（十万级+）、任务与预训练分布差异很大、且 LoRA 已经调到极限仍不达标」时才考虑全参。全参的优势是上限高，代价是显存、存储（每份权重几十 GB）和灾难性遗忘风险都更高。

**展开版**——判断维度有四个：

| 维度 | 倾向 LoRA | 倾向全参 |
|---|---|---|
| 数据量 | < 5 万条 | > 10 万条且质量高 |
| 任务与基座差距 | 同语言同领域，学格式/风格 | 跨语言、跨模态、全新任务范式 |
| 算力预算 | 单卡 / 消费级显卡 | 多卡且允许长时间训练 |
| 部署 | 需要多任务热切换（LoRA 可插拔） | 只服务一个任务，可接受独立权重 |

**LoRA 不够用的典型信号**：

1. 训练 loss 正常下降但验证指标长期卡在平台，加大 r、加长训练都不动；
2. 任务需要模型建立全新的词汇/符号体系（例如自定义的领域标记语言）；
3. 需要同时改变很多层的表示（不只是注意力的投影矩阵）。

**工程上的折中**：先做 LoRA 基线，同时用同一批数据跑一个「只训最后 N 层」的全参对照。如果两者差距在 1 个点以内，就用 LoRA 上线——省下的存储与运维成本是实打实的。

**追问预判**：
- *「LoRA 和全参的效果差距一般有多大？」* —— 在常见领域微调任务上通常在 0~2 个点以内，很多场景 LoRA 甚至更好（因为正则化效应更抑制过拟合）。差距大的场景通常是数据量大、任务差异大。
- *「LoRA 能合并进基座吗？」* —— 可以，`W' = W + (alpha/r) * BA`，合并后推理零额外延迟。代价是失去「一个基座挂多个 LoRA」的灵活性。

</details>

### Q3. 一个业务需求来了，你怎么判断该不该微调？

<details markdown="1">
<summary markdown="1">参考答案</summary>

**30 秒版**：先做提示词基线，再判断瓶颈在哪。如果「提示词 + few-shot + 检索」已经能达到验收标准，就不微调；如果瓶颈是格式稳定性、领域语言、延迟或成本，才进入微调路线。

**展开版**——一张决策清单：

```
① 需求能否被 3~5 句指令 + 少量示例表达清楚？
    能 → 先做提示词工程，设一个可量化的验收线
② 模型是否缺知识？
    是 → 先上 RAG（成本低、可更新、可溯源）
③ 提示词已经调好，但表现不稳定（格式失败、风格漂移、长尾任务差）
    是 → 微调（通常 LoRA）
④ 是否需要私有部署、低延迟、低成本？
    是 → 微调一个更小的模型，往往比调大模型 + 长上下文更划算
⑤ 是否有 ≥ 500~1000 条高质量标注数据，且能持续维护？
    否 → 先解决数据问题，微调会很痛苦
```

**必须一起算的成本**：

- 数据成本：标注、清洗、审核（往往占总成本的一半以上）；
- 训练成本：GPU 小时；
- **维护成本**：基座升级要重训、数据分布漂移要重训、评测集要持续更新——这一项最容易被忽略，但它是长期成本的主体。

**追问预判**：
- *「什么时候微调是错的答案？」* —— 当需求本质是「知识更新」或「检索问题」时。用微调去背知识，会得到一个小、脆、且一更新就要重训的模型。
- *「小模型微调 vs 大模型提示词，怎么选？」* —— 看延迟与成本约束。数据量足够时，小模型微调后在窄任务上常常追平大模型，而推理成本低一到两个数量级。

</details>

### Q4. 低秩假设（low-rank hypothesis）为什么成立？LoRA 为什么有效？

<details markdown="1">
<summary markdown="1">参考答案</summary>

**30 秒版**：微调带来的权重变化 `ΔW` 本身是低秩的（intrinsic dimension 很低），所以用 `W + BA`（`B ∈ R^{d×r}`、`A ∈ R^{r×k}`、`r ≪ min(d,k)`）就能近似它。这既大幅减少了可训练参数，又因为冻住主干而自带正则效果。

**展开版**：

1. **经验依据**：微调后的权重变化矩阵的秩远小于原始权重矩阵的秩，且把随机投影降到很低维度再微调，效果依然接近全参微调——说明「适应下游任务」所需的有效自由度很小。
2. **数学形式**：

   ```
   h = Wx + ΔWx = Wx + (alpha / r) * B A x
   A: d × r，Kaiming 均匀初始化
   B: r × k，零初始化   ← 训练起点 ΔW = 0，保证初始等同于原模型
   ```

3. **为什么有效**：
   - 参数效率：可训练参数从 `d×k` 降到 `r×(d+k)`；
   - 正则效应：低秩约束把更新限制在一个小子空间里，抑制过拟合，也因此**减少灾难性遗忘**；
   - 无推理延迟（合并后）；
   - 可插拔：一个基座 + 多个 LoRA 权重（每个几 MB 到几百 MB），便于多任务切换。

4. **实践中的加餐**：`B` 零初始化是必须的，否则训练初期模型输出会突变。同理，LoRA 常配合更大的学习率（1e-4 ~ 3e-4，比全参的 1e-5 ~ 5e-5 高一到两个数量级），因为只有少量参数在更新。

**追问预判**：
- *「r 和 alpha 谁在控制更新的幅度？」* —— `alpha / r` 是缩放因子。约定俗成的做法是调 r 时同步把 alpha 设为 `2r`，让缩放保持常数，把「表达力」和「更新幅度」两个因素解耦开。
- *「LoRA 加在哪些模块上？」* —— 常见做法是 `q_proj`、`v_proj`（最省参数），实践中 `q/k/v/o + gate/up/down` 全部加通常效果更好但参数更多。可训练参数与「加的范围」成正比。

</details>

## 3. 第二组：方法与参数

### Q5. LoRA 的 alpha 和 r 该怎么调？

<details markdown="1">
<summary markdown="1">参考答案</summary>

**30 秒版**：`r` 控制表达力（低秩子空间维度），`alpha` 只控制缩放幅度 `alpha/r`。常用做法是固定 `alpha = 2r`，只扫 `r ∈ {4, 8, 16, 32, 64}`；数据少、任务简单取小 r，任务复杂、数据多取大 r。经验默认起点是 `r=8`、`alpha=16`。

**展开版**：

| r | 可训练参数 | 适用场景 | 风险 |
|---|---|---|---|
| 4 | 极少 | 风格/格式微调、数据 < 5k | 欠拟合，任务学不动 |
| 8 | 少 | **默认起点** | 平衡最好 |
| 16 ~ 32 | 中 | 领域知识密集型任务、数据 1 万~10 万 | 遗忘风险上升 |
| 64 ~ 128 | 较多 | 接近全参的场景、数据 10 万+ | 过拟合、遗忘、成本上升 |

调参顺序建议：

```
① 先固定 r=8、alpha=16，把学习率、epoch、数据配比调好
② 再扫 r（每次只改 r，并把 alpha 设为 2r 保持缩放不变）
③ 如果指标对 r 完全不敏感 → 瓶颈不在容量，而在数据或任务定义
④ 如果 r 越大越好且还没收敛 → 说明任务确实需要更多容量，考虑全参
```

**容易踩的坑**：

- **只调 r 不调 alpha**：`alpha/r` 变了，有效学习率也变了，你其实是在同时改两个变量，实验结论不可解释；
- **忘了 target_modules**：只加 `q_proj` 和加全部线性层，参数量差好几倍，效果差异可能比 r 的影响还大；
- **忘了 dropout**：LoRA 层通常配 `lora_dropout=0.05 ~ 0.1`，小数据集上对稳定性帮助明显。

**追问预判**：
- *「alpha 调大有什么代价？」* —— 放大 `BA` 的贡献，等效于提高有效学习率。太大会不稳定甚至发散，太小则学不动。它不能替代学习率来调。
- *「r 越大越容易遗忘吗？」* —— 是。r 越大，可表达的参数更新空间越大，越容易偏离预训练权重。这是一个明确的容量-保持权衡。

</details>

### Q6. QLoRA 和 LoRA 的区别是什么？什么时候必须用 QLoRA？

<details markdown="1">
<summary markdown="1">参考答案</summary>

**30 秒版**：QLoRA = 4-bit 量化基座 + LoRA。基座权重压到 4-bit（NF4）且冻结，LoRA 旁路仍用 FP16/BF16 训练；显存大幅下降，效果接近 16-bit LoRA。当显存不够、或想在单张消费级显卡上微调 7B/13B 模型时用它。

**展开版**——QLoRA 的三个关键技术：

| 技术 | 作用 |
|---|---|
| **NF4**（4-bit NormalFloat） | 一种对正态分布权重信息论最优的 4-bit 数据类型，比普通 INT4 精度损失更小 |
| **双重量化**（double quantization） | 对量化常数本身再做一次量化，每参数再省约 0.37 bit |
| **Paged Optimizer** | 优化器状态在显存吃紧时换出到 CPU 内存，避免 OOM 峰值 |

**LoRA vs QLoRA 对比**：

| 维度 | LoRA | QLoRA |
|---|---|---|
| 基座精度 | FP16/BF16 | 4-bit NF4（冻结） |
| 可训练部分 | FP16/BF16 | FP16/BF16（计算时反量化） |
| 7B 模型训练显存 | 约 16~20 GB | 约 6~10 GB |
| 训练速度 | 快 | 慢 20%~40%（反量化开销） |
| 效果 | 基线 | 与 LoRA 接近，通常差 0~1 个点 |
| 推理 | 合并后无额外开销 | 需反量化或合并；也可用 4-bit 推理省显存 |

**什么时候必须用**：

- 单卡 24 GB 想训 13B 以上；
- 单卡 16 GB 想训 7B；
- 显存受限但可以接受更长训练时间。

**追问预判**：
- *「QLoRA 训练慢为什么还能接受？」* —— 因为它把「能不能训」变成了「多久训完」。对于算力受限的团队，可训练性优先于速度。
- *「QLoRA 的 4-bit 量化会影响最终效果吗？」* —— 通常影响很小，因为梯度只作用在 LoRA 上，量化误差主要体现在前向计算中。但极端小样本任务上可能更敏感，值得实测。
- *「能用 INT8 吗？」* —— 可以（`load_in_8bit`），显存收益小于 4-bit，但精度损失更小，是一个中等保守的选择。

</details>

### Q7. 损失掩码（loss mask）为什么必须做？不做会怎样？

<details markdown="1">
<summary markdown="1">参考答案</summary>

**30 秒版**：因为不是所有 token 都是「要模型学会生成的」。多轮对话里 system prompt 和 user 输入是上下文，不是监督目标；只在 assistant 的回复上算 loss，模型才会专注学「怎么回答」而不是「怎么复述提问」。不做掩码会带来三个问题：学到复述用户、对训练轮次过拟合、loss 数值被稀释。

**展开版**——三类必须掩码的位置：

| 位置 | 该不该算 loss | 不掩码的后果 |
|---|---|---|
| system prompt | 否 | 模型可能学着生成 system 内容 |
| user 输入 | 否 | 模型学会复述问题，甚至自问自答 |
| assistant 回复 | **是** | —— |
| padding token | 否 | loss 被大量无意义位置稀释，梯度被拉偏 |
| 多轮中较早的轮次 | 通常保留（因果注意力下不应看到未来） | 视角不同，见下 |

**实现要点**：

```python
# labels 中把不计算 loss 的位置置为 -100（PyTorch CrossEntropyLoss 的 ignore_index）
labels = input_ids.clone()
labels[~assistant_token_mask] = -100

# 也可以按「轮次级」掩码：只保留最后一轮 assistant
```

**为什么不是「越多监督越好」**：让模型预测 user 的输入，等价于在训练一个「对话续写器」，它会把大量算力花在建模用户的语言习惯上，而不是学回答。在数据量小的时候，这种监督噪声的杀伤力非常明显——表现为模型开始模仿用户的错别字和口语风格。

**追问预判**：
- *「如果我把 user 也算了 loss，指标一定是变差吗？」* —— 不一定立刻变差，但会浪费容量、并让模型更倾向于「续写」而不是「回答」，在多轮场景里尤其容易出现自问自答。
- *「多轮对话该只训最后一轮，还是所有 assistant 轮次都训？」* —— 推荐所有 assistant 轮次都训（信息利用率高），但要用因果注意力保证不看未来。只训最后一轮适合「最后一轮才是目标任务」的场景，样本效率低。

</details>

### Q8. LoRA 的 target_modules 怎么选？只加 qv 够吗？

<details markdown="1">
<summary markdown="1">参考答案</summary>

**30 秒版**：`q_proj` + `v_proj` 是历史默认（来自原论文），参数量最省；但要效果最好，通常是把注意力（q/k/v/o）和 FFN（gate/up/down）全部加上。选择原则是「参数量预算允许时，覆盖面越广越好」。

**展开版**：

| 配置 | 相对参数量 | 效果 | 适用 |
|---|---|---|---|
| 只 `q_proj`、`v_proj` | 1× | 基线 | 极小样本、快速试验 |
| `q/k/v/o` | 2× | 通常 +0.5~1.5 点 | 通用选择 |
| `q/k/v/o` + FFN | 3~4× | 通常再 +0.5~1 点 | 数据量较大、任务较难 |
| 全部线性层 | 4×+ | 边际收益递减 | 逼近全参场景 |

**关键认知**：`target_modules` 对效果的影响常常**大于 r**。很多「r 调了没反应」的实验，真实瓶颈是覆盖面太窄。

**实例化时的写法差异**（不同框架的关键字不同，但都要显式指定）：

```python
from peft import LoraConfig, TaskType

cfg = LoraConfig(
    task_type=TaskType.CAUSAL_LM,
    r=8,                     # 低秩维度
    lora_alpha=16,           # 缩放 = alpha / r = 2
    lora_dropout=0.05,       # 小数据集上建议 0.05 ~ 0.1
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj",
                    "gate_proj", "up_proj", "down_proj"],
    bias="none",             # 通常不训 bias，进一步省参数
)
```

**追问预判**：
- *「`bias` 该不该训？」* —— 一般 `none`。训练 bias 收益很小，但对齐类任务上偶尔有帮助；`all` 会显著增加参数量且更容易过拟合。
- *「modules_to_save 是干什么的？」* —— 用于把某些模块（如 `lm_head`、分类头）设为全参训练并与 LoRA 一起保存。当新增了词表 token 或换了任务头时通常需要它，否则保存的 adapter 加载后会缺这些权重。

</details>

## 4. 第三组：数据

### Q9. 微调一般需要多少数据？质量与数量如何取舍？

<details markdown="1">
<summary markdown="1">参考答案</summary>

**30 秒版**：没有绝对数字，但可以参考量级：LoRA 微调风格/格式 1000~5000 条即可见效；领域任务 1 万~5 万条明显更稳；对话类通常需要 1 万条以上。质量优先于数量——**1000 条干净数据往往好过 1 万条含 30% 噪声的数据**。

**展开版**——按任务类型的经验区间：

| 任务 | 冷启动 | 明显收益区间 | 备注 |
|---|---|---|---|
| 分类（PET 式完形填空） | 20 ~ 100 | 500 ~ 5000 | 类数 ≥ 10 时每类至少 20 条 |
| 单轮指令 SFT | 1000 ~ 5000 | 1 万 ~ 10 万 | 指令多样性 > 绝对条数 |
| 多轮对话 | 2000 ~ 1 万 | 10 万+ | 需覆盖中断、纠错、话题切换 |
| 领域知识注入 | 不推荐 | —— | 优先 RAG |

**质量判断的可操作标准**（比「高质量」三个字有用）：

1. **标签一致性**：随机抽 100 条，两人独立判，看 Kappa 是否 > 0.8；
2. **格式完整性**：字段齐全、轮次合法、无模板残留；
3. **回答可验证**：能给出「这句话对不对」的判定依据（有出处 / 有确定答案）；
4. **多样性**：指令模板数、任务类型数、长度分布是否覆盖真实使用场景；
5. **无泄漏**：与评测集无同源样本。

**为什么「数据量优先」会失败**：模型是优秀的模仿者。训练数据里 30% 的答案啰嗦、跑题或含幻觉，模型就会把这种「平均风格」学走。更麻烦的是，这类问题在训练 loss 上看不出来——loss 会正常下降，因为模型确实完美拟合了这批数据。

**追问预判**：
- *「只有 200 条数据怎么办？」* —— 优先考虑 PET/P-Tuning 这类提示学习路线、或者做数据增强（改写法、模板扩增），并且把验收标准降低、明确告知业务方泛化风险。
- *「重复训练损失（重复数据多个 epoch）有用吗？」* —— 少量重复（2~3 epoch）有用；大量重复（10+）会直接导致复述训练样本，上线后被用户发现「背答案」。

</details>

### Q10. 数据集是怎么划分的？什么样的划分会泄漏？

<details markdown="1">
<summary markdown="1">参考答案</summary>

**30 秒版**：随机切分只在样本独立同分布时才安全。真实场景里同一用户、同一商品、同一文档切出来的片段高度相关，必须按**外部键分组切分**或**按时间切分**，否则评测指标会虚高，线上暴跌。

**展开版**——三类切分方式：

| 方式 | 做法 | 适用 | 风险 |
|---|---|---|---|
| 随机切分 | `train_test_split` | 样本确实独立（如不同来源的短文本） | 同源样本两边都有 |
| 分组切分 | 按 `item_id` / `user_id` / `doc_id` 分组，整组进同一侧 | 用户/商品/文档有多个样本 | 需要维护分组键 |
| 时间切分 | 用过去的数据训练，用未来的数据测试 | 时间序列、内容随季节变化 | 分布漂移过快时测试集过难 |

**常见泄漏的四种形态**：

1. **同源文本泄漏**：同一篇文档切出的两个 chunk 分到两侧；
2. **同用户/同商品泄漏**：同一用户的相似提问两边都有；
3. **标注泄漏**：数据里残留了标签词的痕迹（例如输入里出现了「这是正面的评论」）；
4. **模板泄漏**：PET 类任务里，模板字面量被写进了数据文件，导致模型只要记住模板就能答对。

**排查手段**（成本从低到高）：

- 文本指纹交集检查（精确重复）；
- n-gram 重合率统计（近似重复）；
- 分组键交集检查（`set(train.item_id) & set(test.item_id)` 必须为空）；
- **线上-离线对比**：如果离线提升 10 个点而线上没动，先怀疑泄漏。

**追问预判**：
- *「验证集和测试集要不要分开？」* —— 要。验证集用于选模型与调参，测试集只在最终验收时用一次。反复用测试集调参会把它变成验证集，指标失去意义。
- *「数据量小的时候按时间切分会不会测试集太小？」* —— 会。折中做法是「分组 + 时间」双重约束：先按时间框定范围，再在范围内按组切分。

</details>

### Q11. 灾难性遗忘是什么？SFT 之后通用能力掉了很多怎么办？

<details markdown="1">
<summary markdown="1">参考答案</summary>

**30 秒版**：灾难性遗忘指微调后模型丢失了预训练阶段获得的能力，本质是参数为适配新分布发生了漂移。应对手段按优先级：① 混入通用数据回放；② 降低 LoRA 秩 / 减小学习率；③ 加 KL 或 L2-SP 正则；④ 只训部分层；⑤ 减少 epoch。

**展开版**——现象、度量、缓解：

**现象**：通用基准分下降（知识、推理、阅读理解）、语言能力退化（生硬、中英夹杂）、指令遵循下降（不再遵守格式要求）、拒答能力削弱。

**度量**：

```
遗忘率 = (微调前分数 - 微调后分数) / 微调前分数 × 100%
```

要点是**评测配置必须完全一致**（同一套提示词、同一解码参数），并优先看相对下降率而非绝对分。工程上常用 200~500 条的分层抽样「遗忘哨兵集」做低成本监控。

**缓解手段对比**：

| 手段 | 强度 | 代价 | 什么时候用 |
|---|---|---|---|
| 数据回放（混入通用指令数据） | 强 | 需准备通用数据，占训练预算 | **首选**，尤其领域数据高度同质时 |
| 降低 LoRA 秩 r | 中 | 可能欠拟合目标任务 | 用 LoRA 且发现遗忘时的第一反应 |
| 降低学习率 / 减少 epoch | 中 | 收敛变慢 | 训练 loss 已经很低但通用能力在掉 |
| KL 正则（约束输出分布） | 中 | 需旧模型前向，`beta` 要调 | 追求平滑过渡、有旧权重 |
| L2-SP（约束参数偏离） | 中弱 | 需要预训练权重副本 | 没有旧模型前向预算时 |
| 只训部分层 | 中 | 可能拟合不足 | 任务与预训练接近 |

**回放配比的经验起点**：任务数据 : 通用指令数据 = 1 : 1 到 4 : 1；同质化严重时放宽到 1 : 2。

**追问预判**：
- *「LoRA 是不是天然不容易遗忘？」* —— 相对全参是，但不是免疫。r 大、epoch 多、学习率高时同样会明显遗忘。它只是把更新的自由度限制住了。
- *「通用数据从哪来？」* —— 公开指令数据集、业务侧的历史通用对话、以及少量基座模型的自我生成数据（注意过滤质量）。关键是这些数据必须覆盖你想保住的能力维度。

</details>

### Q12. 数据清洗你会做哪几件事？

<details markdown="1">
<summary markdown="1">参考答案</summary>

**30 秒版**：按顺序做六件事——精确去重、语义去重、长度过滤、格式校验、标签/意图平衡、泄漏检测。其中**泄漏检测**最容易被跳过，也最容易让所有后续工作白做。

**展开版**：

| 步骤 | 手段 | 关键注意 |
|---|---|---|
| 精确去重 | NFKC 归一化 + 折叠空白 + MD5 指纹 | 按「指纹 + 标签」去重，别丢掉冲突样本这个信号 |
| 语义去重 | 向量相似度贪心去重，阈值 0.95 左右 | 阈值 0.90 开始有误伤，先人工抽查误删率 |
| 长度过滤 | 按 token 数设上下限 | 多轮对话按轮丢弃最老轮次，不要按 token 硬切 |
| 格式校验 | 字段齐全、角色交替、无模板残留、无未闭合代码块 | 用脚本批量校验，输出失败清单 |
| 平衡性 | 统计标签/意图分布与每类的指令模板数 | 「摘要」只有 2 种写法、「翻译」有 40 种 → 模型会绑定措辞 |
| 泄漏检测 | 指纹交集 + n-gram 重合 + 分组键交集 | 训练集与评测集必须来自独立采集批次 |

**附加的两件事**（视任务）：

- **污染检测**：检查数据里是否混入了评测基准的题目（尤其是从网上抓的数据）；
- **重复率控制**：同一语义样本的重复次数上限（如 ≤3 次），避免模型复述。

**追问预判**：
- *「语义去重和精确去重哪个性价比高？」* —— 精确去重几乎零成本、零误伤，必做；语义去重的收益取决于数据的模板化程度，如果数据是批量生成的，语义去重收益极大。
- *「怎么发现训练数据里混了评测集的题？」* —— 用评测集的题目做 n-gram 与 embedding 双向检索，命中率高就人工复核。

</details>

## 5. 第四组：训练与显存

### Q13. 微调 7B 模型的显存怎么算？给个账本。

<details markdown="1">
<summary markdown="1">参考答案</summary>

**30 秒版**：显存 = 权重 + 梯度 + 优化器状态 + 激活 + KV cache。全参微调 7B 的粗略账本是 16.8 GB（权重）+ 16.8（梯度）+ 67（Adam 的一二阶动量，FP32）+ 激活，轻松超过 80 GB；LoRA 因为冻结主干，只多了很少的梯度与优化器状态，7B 大约 16~20 GB 就能训；QLoRA 则压到 6~10 GB。

**展开版**——逐项拆解（以 7B、BF16 为例）：

| 项 | 计算 | 7B 结果 |
|---|---|---|
| 权重（BF16） | 7B × 2 B | 14 GB |
| 梯度（BF16） | 7B × 2 B | 14 GB |
| Adam 一阶动量（FP32） | 7B × 4 B | 28 GB |
| Adam 二阶动量（FP32） | 7B × 4 B | 28 GB |
| **全参合计（不含激活）** | | **84 GB** |
| LoRA：可训练参数（r=8，q/v） | 约 4M × (2+2+4+4) B | < 0.1 GB |
| 激活值 | 与 batch × seq_len × 层数 × hidden 成正比 | 数 GB，随配置变化大 |
| KV cache（推理） | 2 × 层数 × 序列长 × KV 头数 × head_dim × 精度 | 长上下文时数 GB |

**几条实用换算**：

- BF16 权重：**约 2 GB / 10 亿参数**；
- LoRA 训练 7B：**16~20 GB**（1×24 GB 卡可跑，batch 与 seq_len 受限）；
- QLoRA 训练 7B：**6~10 GB**；
- 全参 7B：**≥ 80 GB**（需要多卡 + ZeRO/FSDP 切分，否则单卡放不下）。

**追问预判**：
- *「激活值怎么省？」* —— 梯度检查点（gradient checkpointing）用时间换显存，可省 50%~70% 激活显存，代价是慢 20%~30%；flash-attention 降低注意力部分的显存与访存开销。
- *「优化器为什么是大头？」* —— Adam 要为每个参数维护两个 FP32 动量，4+4=8 字节/参数，加上 FP32 master weights，实际开销常是权重的 4~6 倍。这也是 8-bit Adam、Adafactor 等「省优化器状态」方法存在的原因。

</details>

### Q14. 训练 OOM 了，排查顺序是什么？

<details markdown="1">
<summary markdown="1">参考答案</summary>

**30 秒版**：固定顺序是——① 确认 OOM 发生在什么时候（加载模型时 / 训练几步后 / 验证时）；② 调小 batch size 并配合梯度累积；③ 降 seq_len；④ 开梯度检查点；⑤ 换 QLoRA / 8-bit 优化器；⑥ 缩小 LoRA 覆盖范围或改用更小的基座。每一档都要记录显存峰值，别一次改三样。

**展开版**——按「先廉价、后昂贵」的顺序：

| 顺序 | 动作 | 显存收益 | 代价 |
|---|---|---|---|
| 0 | 先定位阶段：加载即 OOM = 权重/精度问题；跑几步才 OOM = 激活或碎片问题 | —— | —— |
| 1 | `batch_size` 减半 + 梯度累积补回等效 batch | 线性下降 | 训练变慢 |
| 2 | 降低 `max_seq_len` / 开 packing | 线性下降 | 长样本被截断 |
| 3 | 开梯度检查点 | 激活降 50%~70% | 慢 20%~30% |
| 4 | 换 QLoRA（4-bit 基座）+ paged optimizer | 权重与优化器状态大降 | 训练慢 20%~40% |
| 5 | 用 8-bit Adam | 优化器状态降约 75% | 精度略降 |
| 6 | 缩小 `target_modules` 或降低 r | 小幅 | 效果可能下降 |
| 7 | 换更小基座 / 多卡 ZeRO-3、FSDP | 大 | 工程复杂度上升 |

**先问自己三个问题**（面试时说出来会加分）：

1. **OOM 的时间点**：`CUDA out of memory` 发生在模型加载时？前向时？反向时？还是在 `optimizer.step()`？后两者通常指激活或优化器状态是大头。
2. **显存峰值是否在波动**：波动大说明有变长样本（长序列把峰值拉高），解决方案是 packing + 按长度分桶，而不是无脑减小 batch。
3. **是否是碎片化**：`reserved` 远大于 `allocated` 时是显存碎片，配 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` 比降 batch 更对症。

**追问预判**：
- *「为什么减小 batch 有效，梯度累积等价吗？」* —— 梯度累积在数学上近似等价于大 batch，但不完全等价（BatchNorm 行为、随机性），对 LoRA 微调通常可以接受。
- *「显存看起来够但还是 OOM？」* —— 检查是否是碎片、是否忘了 `torch.no_grad()`（验证时）、是否有多个进程占卡、以及是否算上了 KV cache。

</details>

### Q15. 多轮对话数据怎么构造和训练？

<details markdown="1">
<summary markdown="1">参考答案</summary>

**30 秒版**：按对话轮次拼成一条序列，用角色模板（或 chat template）分隔，**只在 assistant 轮次上计算 loss**；注意超长样本按轮丢弃而不是硬截断，并保证 position id 与 attention mask 正确。

**展开版**——四个关键设计点：

1. **角色模板**：用基座模型官方 chat template，不要自己发明。模板与基座不匹配是多轮训练效果差的常见原因（模型没见过这种特殊 token 排布）。
2. **loss mask 粒度**：
   - 轮次级：只训 assistant 回复的 token；
   - 样本级：多轮中所有 assistant 轮次都训（推荐），或只训最后一轮（适合最后一轮是目标任务的场景）。
3. **长度处理**：按轮丢弃最老轮次，保留 system prompt（如果它是固定行为约束）与最后一轮；不要按 token 从中间硬切，会把一条回复切成两半。
4. **多样性**：数据要覆盖中断、用户纠错、话题切换、以及「无法回答」的情形。只训练「顺利的一问一答」会导致模型在真实对话中崩掉。

**要避免的三种坏数据**：

| 坏数据 | 后果 |
|---|---|
| 空 assistant 回复或占位的「（略）」 | 模型学会输出占位符 |
| 轮次不交替（连续两条 user） | 训练时角色混淆，推理时可能自问自答 |
| 把模型自己的历史错误回答当正样本 | 错误被强化，且会放大 |

```python
# 多轮数据的损失掩码示意（伪代码，需按具体 chat template 适配）
def build_labels(input_ids, assistant_spans, ignore_index=-100):
    """assistant_spans: List[Tuple[int, int]]，每个 assistant 回复的 [start, end) 区间"""
    labels = list(input_ids)
    keep = set()
    for s, e in assistant_spans:
        keep.update(range(s, e))
    for i in range(len(labels)):
        if i not in keep:
            labels[i] = ignore_index
    return labels
```

**追问预判**：
- *「多轮比单轮难在哪？」* —— 上下文依赖与错误累积。模型不仅要答对，还要和前文保持一致；训练数据里的历史错误会被当成上下文，进一步放大。
- *「system prompt 要参与 loss 吗？」* —— 不参与。它是行为约束的上下文，让模型学会「生成 system prompt」没有业务意义。

</details>

### Q16. 训练过程中你盯哪些指标？loss 不降怎么办？

<details markdown="1">
<summary markdown="1">参考答案</summary>

**30 秒版**：盯四个数——训练 loss、验证集指标、学习率曲线、梯度范数。loss 不降先分三类：根本没动（学习率/数据问题）、动了又卡住（容量或数据问题）、在震荡（学习率过大或 batch 太小）。

**展开版**——先分类，再对症：

| 现象 | 最可能原因 | 验证方法 | 修复 |
|---|---|---|---|
| loss 从第一步就几乎不变 | 学习率太小；标签被 mask 光了；数据格式错（标签没对上） | 打印一个 batch 的 labels，确认非 `-100` 的位置存在；把 lr 乘 10 试跑 50 步 | 修数据管线；提高 lr |
| loss 前几步正常，之后平台 | 容量不足（r 太小、覆盖面太窄）；任务超出模型能力 | 加大 r / 扩 target_modules 试跑 | 扩容量；或改用全参 |
| loss 震荡不收敛 | lr 过大；batch 太小；warmup 不足 | 看梯度范数是否尖峰；看 loss 曲线周期 | 降 lr、加 warmup、加梯度累积 |
| 训练 loss 降但验证指标不升 | 过拟合；数据分布不一致；评测口径有问题 | 对比验证集与训练集的输入分布；检查评测脚本 | 早停、增数据、加 dropout/weight decay |
| loss 降到极低但输出很差 | 数据里有重复样本被记住了；或者评测解码参数不对 | 算复述率；人工看 20 条输出 | 去掉重复数据、减少 epoch |

**必看的四个量**：

1. **训练 loss 的滑动平均**（不要看单步，噪声太大）；
2. **验证集指标随步数的曲线**（选模型唯一依据）；
3. **学习率曲线**（确认 warmup 生效、没有提前衰减到 0）；
4. **梯度范数**（尖峰通常预示不稳定，需剪裁或降 lr）。

**追问预判**：
- *「warmup 为什么必要？」* —— 训练初期 Adam 的二阶动量估计不准，直接上大学习率容易发散；warmup 让学习率从接近 0 开始爬升，通常取总步数的 3%~10%。
- *「梯度剪裁设多少？」* —— 常用 `max_grad_norm=1.0`。它不改善收敛速度，但显著提升稳定性，几乎总是建议开。

</details>

## 6. 第五组：评估与故障

### Q17. 如何判断是数据问题还是超参问题？

<details markdown="1">
<summary markdown="1">参考答案</summary>

**30 秒版**：看曲线形状和指标构成。**训练 loss 降不下去 → 数据或容量问题；训练 loss 很低而验证指标差 → 过拟合或数据分布不一致；两者都好但线上差 → 评测口径或分布漂移**。超参问题的特征是「同一份数据换参数就能变好」；数据问题的特征是「怎么调参数都卡在同一个平台」。

**展开版**——一张归因决策表：

| 观察 | 归因 | 验证实验 |
|---|---|---|
| 训练 loss 长期在 1.5 以上不降 | 数据管线错（标签未对齐/被 mask）；任务超出模型能力 | 取 20 条样本过拟合，看 loss 能否降到接近 0 |
| 训练 loss 能降到很低，验证指标差 | 过拟合或数据分布不一致 | 减少 epoch / 加数据；检查训练集与验证集来源 |
| 训练与验证都卡在同一水平 | 模型容量不足或数据信息量不足 | 加大 r / 换全参对照；检查标注一致性 |
| 指标对超参极其敏感（小改就崩） | 学习率过大或数据量过小 | 降低 lr，跑 3 个种子看方差 |
| 指标很好但 badcase 集中在某几类 | 数据不平衡或某类样本质量差 | 按类统计 F1；人工看该类 20 条 |
| 训练指标好、线上差 | 分布漂移或评测泄漏 | 线上-离线指标对比；复查切分方式 |

**最有诊断价值的一个实验：小样本过拟合测试。** 取 20~50 条训练样本，用较大学习率训 200 步，看训练 loss 能否降到接近 0、输出能否精确复现。

- **能** → 数据管线与模型容量都没问题，瓶颈在数据量或分布；
- **不能** → 管线有 bug（标签错位、mask 全空、数据没进 dataloader），或模型容量确实不够。

这个实验只要几分钟，却能把「数据 / 超参 / 代码」三类原因一次分开，是排查效率最高的动作。

**追问预判**：
- *「模型把训练集背下来了说明什么？」* —— 说明容量和管线都正常，是过拟合信号。要么加数据，要么减 epoch，要么加正则。
- *「多种子方差很大怎么办？」* —— 先看是数据量太小还是学习率太大。分类任务上如果 3 个种子的 F1 标准差 > 2 个点，说明实验设置本身不稳，任何「提升 1 个点」的结论都不可信。

</details>

### Q18. 微调的评估指标应该怎么设计？

<details markdown="1">
<summary markdown="1">参考答案</summary>

**30 秒版**：四个维度一起看——目标任务指标、通用能力保持、格式合规率、过拟合检查。基线必须是「未微调 + 好提示词 + few-shot」，并且要跑多随机种子报均值 ± 标准差。

**展开版**：

| 维度 | 指标 | 采集方式 |
|---|---|---|
| 目标任务 | Accuracy / macro-F1 / EM / ROUGE-L / 人工通过率 | 留出测试集 |
| 通用能力保持 | 通用基准回归的相对下降率、保持率（几何平均） | 200~500 条遗忘哨兵集，必要时跑全量 |
| 格式合规率 | JSON 可解析率、schema 通过率、必填字段齐全率 | 解析器批量跑，设绝对下限（如 ≥99%） |
| 过拟合 | 训练/验证 loss gap、验证指标峰值后的回落、复述率 | 训练日志 + n-gram 重合统计 |

**基线设计**（四行对比）：

| 组别 | 说明 |
|---|---|
| A. 零样本 | 只给指令 |
| B. few-shot | 好提示词 + 3~5 示例 ← **主基线** |
| C. 微调 | 报告方法、参数量、训练成本 |
| D. 微调 + few-shot | 判断两者互补还是互相覆盖 |

**容易被忽略的两点**：

1. **格式合规率必须单列**。一个 F1 涨了 9 个点但 JSON 解析率从 99% 掉到 78% 的模型，在生产上是严重回归；
2. **要报告成本**。GPU 小时、峰值显存、推理延迟。只报效果的对比实验是不完整的。

**追问预判**：
- *「为什么基线不用『未微调的裸模型』？」* —— 因为那会高估微调收益。决策要回答的是「相对于最便宜的可用方案（提示词工程），微调值不值」。
- *「怎么衡量灾难性遗忘？」* —— 同一套评测配置跑微调前后，计算相对下降率；优先看单基准的最差下降，别只看平均分。

</details>

### Q19. SFT 之后模型反而变差了，怎么排查？

<details markdown="1">
<summary markdown="1">参考答案</summary>

**30 秒版**：先定义「变差」——是目标任务指标掉、还是通用能力掉、还是格式变坏？然后按顺序排查：数据质量（有没有脏数据/重复）、loss mask（是不是把提问也算进去了）、学习率与 epoch（是不是过拟合）、基座与数据分布是否匹配。最常见的原因是数据质量与过拟合，而不是方法本身。

**展开版**——按概率排序的原因与验证：

| 排序 | 原因 | 特征表现 | 验证方法 | 修复 |
|---|---|---|---|---|
| 1 | 数据里有脏样本（错误答案、跑题、格式残缺） | badcase 集中在某几类或某批数据 | 按数据批次统计错误率；抽 50 条人工看 | 清洗；按来源回溯问题批次 |
| 2 | 过拟合（epoch 太多、数据太少） | 训练 loss 极低，验证回落，开始复述训练样本 | 算复述率；看验证曲线峰值 | 早停、减 epoch、加数据、加 dropout |
| 3 | 学习率过大 | 训练不稳、输出风格突变、格式崩坏 | 降 lr 十倍重跑对照组 | 降 lr、加 warmup |
| 4 | loss mask 错误 | 模型学会复述提问、自问自答 | 打印 labels 确认非 `-100` 位置 | 修正 mask |
| 5 | 通用能力遗忘 | 通用基准明显下降，目标任务其实还行 | 通用基准回测 | 混入通用数据回放；降 r |
| 6 | 数据分布与评测不一致 | 训练集风格与真实输入差距大 | 对比训练输入与真实输入的分布 | 重新采样，覆盖真实分布 |
| 7 | 灾难性的格式覆盖 | 训练数据格式单一，模型只会这一种输出 | 用不同格式的指令测 | 丰富格式多样性 |

**通用动作**：把「微调后变差」的样本做成 **regression set**（微调前对、微调后错的样本集合），逐条看。这个集合的规模不大，但归因效率极高，而且它本身就是回归测试集的雏形。

**追问预判**：
- *「模型开始重复训练数据里的话，是什么原因？」* —— 典型的过拟合 + 数据重复率过高。降低 epoch、去重、增加改写比例。
- *「目标任务变好了，但通用能力掉了 15%，能上线吗？」* —— 不能直接上线。先加回放数据重训；如果业务上确实只需要单一能力（比如纯分类小模型），要在验收文档里明确写出「放弃通用能力」这个取舍，并确认业务方接受。

</details>

### Q20. 线上效果怎么验证？离线指标和线上表现不一致怎么办？

<details markdown="1">
<summary markdown="1">参考答案</summary>

**30 秒版**：离线只是筛选，线上才是验收。用影子模式或小流量 A/B，盯业务指标（任务完成率、人工采纳率、投诉率）与工程指标（延迟、成本、格式失败率）。离线-线上不一致的头号原因是测试集泄漏或分布漂移。

**展开版**——线上验证的四步：

```
① 影子模式（shadow）：新老模型同时跑，只记录不生效。看输出差异分布与格式失败率
② 小流量 A/B：5% 流量，跑足统计周期，看业务指标与工程指标
③ 灰度扩大：50% → 100%，同时保留一键回滚
④ 上线后监控：分布漂移、格式失败率、用户反馈（badcase 回流）
```

**离线-线上不一致的四种根因**：

| 根因 | 表现 | 修复 |
|---|---|---|
| 测试集泄漏 | 离线虚高 5~20 点，线上几乎没动 | 按外部键分组切分；评测集独立采集 |
| 分布漂移 | 离线好、线上差，且随时间变差 | 训练数据覆盖真实长尾；建立线上 badcase 回流机制 |
| 指标口径不同 | 离线用 macro-F1，线上关注「用户是否采纳」 | 尽量让离线指标与业务指标对齐，或至少建立映射 |
| 工程因素 | 模型答对了但超时、被截断、格式解析失败 | 监控延迟、max_new_tokens、格式失败率 |

**建议必建的三个线上监控**：

1. **格式失败率**（有硬上限，超标告警）；
2. **输出分布漂移**（长度、重复率、拒答率的日环比）；
3. **badcase 回流闭环**（用户投诉/人工标记 → 进回归集 → 下次训练前必须过）。

**追问预判**：
- *「A/B 要跑多久？」* —— 由最小可检测效应和方差决定，通常至少一周以覆盖工作日/周末的行为差异。业务指标波动大的场景需要更长。
- *「线上指标掉了但要快速定位，你会先看什么？」* —— 先分「模型变了」和「输入变了」：对比近 7 天的输入分布（长度、意图占比）与输出分布，再决定是回滚模型还是处理数据漂移。

</details>

## 7. 微调速查表

| 方法 | 可训练参数量（7B 为例） | 训练显存（7B，粗略） | 适用场景 | 典型坑 |
|---|---|---|---|---|
| 全参微调 | 100%（约 7B） | ≥ 80 GB（单卡放不下） | 数据 10 万+、任务与基座差距大、追求上限 | 遗忘严重；每份权重几十 GB，多任务无法复用；需要 ZeRO/FSDP |
| LoRA | 0.1% ~ 1%（r=8 约 4M） | 16 ~ 20 GB | **默认首选**：领域适配、风格/格式微调、多任务热切换 | 只加 `q/v` 覆盖面太窄；只调 r 不调 alpha；忘配 dropout |
| QLoRA | 同 LoRA（主干 4-bit 冻结） | 6 ~ 10 GB | 单卡消费级显卡微调 7B/13B | 训练慢 20%~40%；极端小样本上对量化误差更敏感 |
| Adapter | 1% ~ 5% | 20 ~ 24 GB | 需要模块化、可组合的多任务 | 增加推理延迟；层间插入改变结构，与部分加速库不兼容 |
| Prefix-Tuning | 0.1% ~ 3% | 16 ~ 22 GB | 生成任务、需要长前缀控制风格 | 前缀占用序列长度；训练不稳定，需重参数化 |
| P-Tuning v1 | < 0.1%（仅输入层伪 token） | 15 ~ 18 GB | NLU 任务、小样本、小模型 | 小参数量模型上明显弱于全参；需要 attention mask 重算与位置偏移 |
| P-Tuning v2 | 0.1% ~ 3%（逐层 prompt） | 16 ~ 22 GB | 追求与全参可比的 PEFT，且模型较小 | 逐层参数需要专门实现；与部分推理框架适配成本高 |
| PET（完形填空） | 0 ~ 少量（复用 MLM Head） | 远低于上述（常可 CPU/小卡） | 分类任务、样本量几十到几百 | 模板方差大；超多分类难设计标签词；推理需兜底映射 |

**选型口诀**：显存不够先量化（QLoRA），效果不够先加覆盖面（target_modules / r），遗忘严重先加回放，都不行再上全参。

## 8. 常见坑速查

| 坑 | 症状 | 一句话修复 |
|---|---|---|
| 基线太弱 | 微调收益被高估 20+ 点 | 主基线必须是「未微调 + 好提示词 + few-shot」 |
| 忘了 loss mask | 模型复述提问、自问自答 | 非 assistant 位置置 `-100` |
| 只调 r 不调 alpha | 实验结论不可解释 | 固定 `alpha = 2r`，一次只动一个变量 |
| 测试集泄漏 | 离线好、线上一动不动 | 按 item/user/时间分组切分 |
| 只看训练 loss | loss 到 0.01 就以为成功 | 以验证集指标为唯一选模型依据 |
| 忽略格式失败率 | F1 涨但 JSON 解析率跌到 78% | 格式合规率单列并设绝对下限 |
| 显存不够就换小模型 | 效果掉一大截 | 按 batch → seq_len → 梯度检查点 → QLoRA 顺序降级 |
| 多种子不报告 | 结论不可复现 | 跑 3 个种子，报均值 ± 标准差，禁止挑种子 |
| 数据重复率过高 | 上线后「背答案」 | 去重 + 控制单样本重复上限（≤3 次） |
| chat template 与基座不匹配 | 多轮训练后模型输出混乱 | 用基座官方 template，不要自己发明特殊 token |
| 基座升级后直接套用旧 LoRA | 效果异常 | 基座版本变更后必须重训并重跑评测 |

## 9. 自测

<details markdown="1">
<summary markdown="1">参考答案</summary>

**Q1. 用一句话说清 LoRA 的 alpha 和 r 分别控制什么。**

`r` 控制低秩子空间的维度（表达力 / 容量），`alpha` 通过 `alpha/r` 这个缩放因子控制 LoRA 分支对最终输出的贡献幅度（等效于调有效学习率）。工程上通常固定 `alpha = 2r`，这样可以只扫 r 而让缩放保持恒定，避免一次改两个变量。

**Q2. 训练时 OOM，你的第一反应应该是什么？**

先定位 OOM 发生在哪个阶段：加载模型时（权重/精度问题）、前向/反向时（激活问题）、还是 `optimizer.step()` 时（优化器状态问题）。然后按 batch → seq_len/packing → 梯度检查点 → QLoRA/8-bit 优化器 → 缩小 target_modules → 换更小基座 的顺序逐档降级，每档记录显存峰值，一次只改一个变量。

**Q3. 为什么说「小样本过拟合测试」是排查效率最高的实验？**

因为它只用 20~50 条样本、几分钟时间，就能把「数据管线有没有 bug」和「模型容量够不够」分开：如果训练 loss 能降到接近 0 且能复现样本，说明管线和容量都正常，问题在数据量或分布；如果降不下去，说明管线有 bug（标签错位、mask 全空、数据没进 dataloader）或容量确实不足。这一步能避免在错误的方向上花掉几天时间。

**Q4. 灾难性遗忘最有效的缓解手段是什么？**

数据回放——在训练集里混入 20%~50% 的通用指令数据，让旧分布持续参与梯度更新。它比调超参更根本，因为它直接改变了优化的目标分布。只有在无法准备通用数据时，才退而求其次用降低 LoRA 秩、降低学习率、KL/L2-SP 正则这些手段。

</details>
