> **一句话总结**：提示工程（Prompt Engineering）是在**不改动模型权重**的前提下，通过精心设计的提示（含角色设定、分隔符、示例、输出格式约束与思考引导）把大模型的输出对齐到任务意图；核心只有两条原则——**写清晰的指令**和**给模型充足的思考时间**。
> **前置知识**：大模型基本概念、In-context learning（见《01-大模型基础与演进》）、Python 字符串格式化与 JSON 解析。
> **学完能做到**：1. 用「清晰指令 + 分隔符 + 少样本 + 结构化输出」四件套写出稳定可用的提示；2. 针对金融文本分类/信息抽取/文本匹配三类任务设计可解析的 prompt；3. 用「初版 → 分析结果 → 迭代」的循环把模糊需求打磨成可用 prompt。

## 1. 核心概念

### 1.1 什么是提示工程

**提示工程（Prompt Engineering）**，也被称为**上下文学习（in-context learning）**，
是指通过精心设计的提示技术来引导 LLM 行为，**而无需更改模型权重**，目标是使模型输出与给定任务的人类意图一致。

两个关键判断：

| 特点 | 说明 |
|---|---|
| 直观可控 | 提示调整提供了对模型行为的直观控制 |
| 措辞敏感 | 对提示的确切措辞和设计敏感，因此需要精心制定的准则才能实现期望结果 |

一句话对比传统做法：**传统机器学习需要专业算法人员做 NLP/CV 特征工程与模型训练；提示工程让非专业人员也能用自然语言驱动大模型完成任务**——这是它在金融等业务领域迅速落地的根本原因。

### 1.2 两大原则（本笔记的主线）

| 原则 | 含义 | 落地技巧 |
|---|---|---|
| ① 写清晰的指令 | 清晰、具体地表达需求，提供充足上下文 | 分隔符、结构化输出、参考示例、角色扮演 |
| ② 给模型充足的思考时间 | 不要让它「匆忙下结论」 | 指定步骤、指导模型先自行求解再对比 |

> 为什么这两条就够了？因为 LLM 的能力**已经存在于参数里**，prompt 的作用是**把任务精确定位**（原则一）
> 与**引导它把中间推理展开**（原则二）。前者解决「对齐意图」，后者解决「复杂任务算错」。

### 1.3 提示工程的四大应用方向

| 方向 | 典型子任务 | 的例子 |
|---|---|---|
| 文本概括 | 限制输出长度、设置关键角度侧重、关键信息抽取 | 电商熊猫公仔评论摘要 |
| 文本转换 | 翻译、语种识别、语气风格调整、格式转换、拼写语法纠正 | 把口语微信改成商务信函、JSON 转 HTML 表格 |
| 推理与判断 | 多步骤任务、判断解答正确性 | 太阳能发电站费用题批改 |
| 信息抽取/分类/匹配 | 结构化输出、实体抽取、语义相似判断 | 金融三大任务（见 2.4） |

### 1.4 金融项目：三个任务与 Prompt 设计要点

第四章的项目背景：金融领域数据激增，AI 在金融的落地场景是**风险评估、投资决策、客户服务**；
项目用 `Qwen2.5-7B` / `ChatGLM-6B` 以 **few-shot / zero-shot 的 in-context learning** 方式完成三类任务。

| 任务 | 业务场景 | 输入 | 期望输出 | Prompt 设计要点 |
|---|---|---|---|---|
| 金融文本分类 | 识别与评估信用风险、市场风险、操作风险 | 金融文本段落 | 类别名（新闻报道/公司公告/财务公告/分析师报告） | 给出**所有类别 + 每类一个样例**，让模型知道「什么叫分类」 |
| 金融文本信息抽取 | 抽实体名称、日期、金额，减少人工工作量 | 股票信息段落 | JSON（日期/股票名称/开盘价/收盘价/成交量） | 先定义 **schema**；要求 JSON 输出；缺失值约定用「原文中未提及」；多个值用逗号分隔 |
| 金融文本匹配 | 信息检索与过滤、匹配相关金融文本 | 句子对 | 「是 / 不是」（相似 / 不相似） | 明确只回答是否相似、**不要做多余回答**；给相似与不相似各一个样例 |

## 2. 关键机制

### 2.1 清晰指令的四种构造技巧

#### ① 分隔符（delimiter）

分隔符就像是 prompt 中的「墙」，把**不同的指令、上下文、输入**隔开，避免意外混淆。
可用 ` ``` `、`"""`、`<>`、`<tag></tag>`、`:` 等，只要能明确起到隔断作用即可。

```python
prompt = f"""把用三个反引号括起来的文本总结成一句话。```{text}```"""
```

**为什么要用分隔符**：模型无法区分「哪部分是给我的指令、哪部分是要处理的数据」时，
待处理文本里若含有类似指令的句子（提示注入），模型可能把数据当指令执行。
分隔符给了模型明确的结构信号，也让同一段 prompt 模板可以安全地拼接任意用户输入。

#### ② 结构化输出（structured output）

结构化输出就是按某种格式组织的内容（JSON、HTML、XML、Markdown），便于在代码中进一步解析处理。

```python
prompt = f"""请生成包括书名、作者和类别的虚构的、非真实存在的中文书籍清单，
并以 JSON 格式提供，其中包含以下键：book_id、title、author、genre。"""
```

**为什么要指定键名**：把「自由文本」变成「可 `json.loads` 的对象」，
下游程序无需写脆弱的正则解析，直接按字段取值，工程上稳定得多。

#### ③ 参考示例（few-shot）

在要求模型执行实际任务之前，给模型一两个**已完成的样例**，让它了解我们的要求和期望的输出样式。
例如要求模型用一致的隐喻风格回答问题，先给一组祖孙对话样例（孩子问「何为耐心」，祖辈用河流/交响乐作喻），
再让它回答「何为韧性」，模型就会沿用同样的隐喻风格。

#### ④ 角色扮演（role）

让模型充当一个角色，它会**更专业、更明确**地回复。例如：

```text
我需要你充当一个 AI 算法面试官的角色，自主地对我进行 AI 面试过程中常考的问题提问。
你可以一次问一个问题，我回答完，你再出第二道题。
```

> 角色设定为什么有效：它在上下文中激活了与「面试官」「文案专家」相关的语言模式与知识子集，
> 相当于给模型的输出分布做了一次「先验引导」。

### 2.2 让模型思考：两种可靠手法

#### ① 指定步骤（把复杂任务拆成有序子任务）

原则：**给予语言模型充足的推理时间**。让它匆忙给出结论，结果很可能不准确——就像让人在极短时间内解数学题。

示例任务：对一段文本依次做「一句话摘要 → 翻译成英语 → 列出英语摘要中的人名 → 输出 JSON」四步：

```python
prompt = f"""1-用一句话概括下面用<>括起来的文本。
2-将摘要翻译成英语。
3-在英语摘要中列出每个名称。
4-输出一个 JSON 对象，其中包含以下键：English_summary，num_names。
请使用以下格式：
文本：<要总结的文本>
摘要：<摘要>
翻译：<摘要的翻译>
名称：<英语摘要中的名称列表>
输出JSON：<带有 English_summary 和 num_names 的 JSON>
Text: <{text}>"""
```

结果示例：`摘要` → `翻译` → `名称：Jack、Jill` → `JSON: {"English_summary": "...", "num_names": 2}`。

**为什么有效**：① 明确步骤避免了模型在一次生成中「跳步」；② 强制先输出中间结果（摘要、翻译），
让后续步骤基于**已生成的事实**而非隐式推断，任务复杂度被逐层降低；③ 固定输出骨架便于程序解析。

#### ② 指导模型求解（先自己算，再对比答案）

任务：判断学生对「太阳能发电站首年运营成本」的解答是否正确。
**朴素做法**（直接让模型判断）会失败：模型看到学生答案里「维护费用 = 100,000 + 100x」
就顺着认可了，直接回答「学生的解决方案是正确的」——**这是错误的**（维护费用应是 10x，总费用 360x，而学生算出 450x）。

**改进做法**：在 prompt 中要求模型**先自行求解，再与学生的解法对比**：

```python
prompt = f"""请判断学生的解决方案是否正确，请通过如下步骤解决这个问题：
步骤：首先，自己解决问题。然后将您的解决方案与学生的解决方案进行比较，
对比计算得到的总费用与学生计算的总费用是否一致，并评估学生的解决方案是否正确。
在自己完成问题之前，请勿决定学生的解决方案是否正确。
使用以下格式：
问题：问题文本
学生的解决方案：学生的解决方案文本
实际解决方案和步骤：实际解决方案和步骤文本
学生计算的总费用：学生计算得到的总费用
实际计算的总费用：实际计算出的总费用
学生计算的费用和实际计算的费用是否相同：是或否
学生的解决方案和实际解决方案是否相同：是或否
学生的成绩：正确或不正确
问题：<问题>
学生的解决方案：<学生答案>"""
```

改进后模型给出：`实际计算的总费用：360x+10万美元`、`学生计算的总费用：450x+10万美元`、
`学生的成绩：不正确`——**正确**。

**为什么有效**：关键句是「**在自己完成问题之前，请勿决定学生的解决方案是否正确**」。
它阻断了模型「顺着给定文本往下接」的捷径，强迫模型先生成自己的答案作为参照，
再与给定答案比对——这与人类批改作业的可靠做法一致。

### 2.3 迭代优化：把 prompt 当成「要调参的模型」

Prompt 的一次成功率可能较高，但仍**需要通过多次迭代找到最适合应用的形式**；设计高效 prompt 也需要多版本试错。

| 步骤 | 动作 |
|---|---|
| 1. 初步想法 | 编写初版 prompt（满足「清晰」与「给足思考时间」两条原则） |
| 2. 输入模型 | 把它交给模型执行 |
| 3. 结果检查 | 分析输出问题，定位 prompt 缺陷 |
| 4. 循环迭代 | 改进 prompt，重复直到「适合应用」 |

**完整案例：椅子产品说明书 → 电商营销文案**

| 轮次 | 发现的问题 | 解决方案（改 prompt） | 结果 |
|---|---|---|---|
| 初始 | 输出内容过长，不适合做简明电商广告语 | 在 prompt 中加长度限制：「使用最多 50 个词」 | 文案明显缩短 |
| 第 1 次迭代 | 文案偏重风格与氛围，技术细节少，**与目标受众关注点不符** | 明确受众与侧重：「该描述面向家具零售商，应具有技术性质，并侧重于产品的材料构造」，并要求末尾附 7 字符产品 ID | 内容转向材质、工艺、结构 |
| 第 2 次迭代 | 需要抽取尺寸信息并直接可用于网页 | 要求提取尺寸组织成表格，指定表名「产品尺寸」、列含义（名称 / 英寸测量值），并**格式化为 HTML 放在 `<div>` 中** | 直接产出可贴进网页的结构 |

**长度限制的一个工程细节**：设置长度要求时模型输出**不总能精确符合**，但基本能控制在可接受误差范围内。
原因是语言模型计算文本长度依赖分词器，而分词器在字符统计上不具备完美精度。
**实践建议**：不要依赖 prompt 做硬性长度控制（例如"最多 30 个汉字"）；
需要严格限制时应**在代码侧截断或校验重试**。

### 2.5 三大任务的可复用 Prompt 骨架

三个任务的 prompt 共用同一套骨架：**角色/任务说明 + 封闭输出空间 + few-shot 示例 + 待处理输入**。

| 任务 | 骨架要点 | `<Bot>` 示例答案 |
|---|---|---|
| 分类 | 「你是一个文本分类器，需按照要求将我给你的句子分类到：['新闻报道','公司公告','财务公告','分析师报告'] 类别中」 | `新闻报道` |
| 抽取 | 先给 schema（如 `{'金融': ['日期','股票名称','开盘价','收盘价','成交量']}`），再约定「按 JSON 输出、缺失信息用『原文中未提及』、多值用『,』分隔」 | `{"日期":["2023-01-10"], ...}` |
| 匹配 | 「当我给你两个句子时，你需要回答这两句话语义是否相似。只需要回答是否相似，不要做多余的回答」 | `是` / `不是` |

> 注意：示例中 `<Bot>` 的内容都是**人工预先写好的**（few-shot 的示范答案），不是模型真实输出；
> 它的作用是告诉模型「看到类似 `<User>` 的输入时，应当作出什么形式的回答」。

### 2.6 为什么 few-shot 能显著改善输出格式

| 层面 | zero-shot 的问题 | few-shot 提供的信息 |
|---|---|---|
| 任务定义 | 模型可能误解「分类」「抽取」的具体含义 | 用一个完整样例演示「输入形态 → 输出形态」 |
| 输出格式 | 格式漂移，句子里带解释文字 | 示例直接锚定输出词表与结构（如只回答「是/不是」） |
| 类别边界 | 相似类别容易混淆（公司公告 vs 财务公告） | 每类给一个样例，用实例划清边界 |
| 语言风格 | 语气不受控 | 示例起到「风格样板」作用 |

**成本视角**：few-shot 会增加输入 token 数（更长 prompt、更高费用与延迟），但**换来的是免训练**——
不需要标注数据、不需要训练、不需要维护多套权重，改 prompt 就能换任务。这是提示工程在业务侧最大的价值。

## 3. 可运行示例

### 3.1 金融文本分类（few-shot + 严格输出词表）

```python
import os
from openai import OpenAI

client = OpenAI(api_key=os.environ["OPENAI_API_KEY"])
LABELS = ["新闻报道", "公司公告", "财务公告", "分析师报告"]
SYSTEM = ("现在你是一个金融文本分类器，你需要按照要求将我给你的句子分类到："
f"{LABELS} 类别中。只输出一个类别名称。")

FEW_SHOT = [
("新闻报道", "今日，股市经历了一轮震荡，投资者密切关注政策调整。"),
("公司公告", "本公司宣布成功完成最新一轮并购交易。"),
("财务公告", "本公司年度财务报告显示，去年实现稳步增长的盈利。"),
("分析师报告", "最新的行业分析报告指出，科技公司的创新将成为未来增长的主要推动力。"),
]


def build_messages(sentence: str):
 msgs = [{"role": "system", "content": SYSTEM}]
 for label, example in FEW_SHOT: # 用「类别：样例」给出参考示例
 msgs.append({"role": "user", "content": f"<User>：{example}"})
 msgs.append({"role": "assistant", "content": label})
 msgs.append({"role": "user", "content": f"<User>：{sentence}"})
 return msgs


 def classify(sentence: str) -> str:
 resp = client.chat.completions.create(
 model="gpt-4o-mini", messages=build_messages(sentence),
 temperature=0, max_tokens=16,
 )
 label = resp.choices[0].message.content.strip()
 return label if label in LABELS else f"非法输出：{label!r}" # 必须校验


 for t in ["今日，央行发布公告宣布降低利率，以刺激经济增长。",
 "公司资产负债表显示，公司偿债能力强劲，现金流充足。"]:
 print(f"[{classify(t)}] {t[:24]}...")
```

**要点**：`temperature=0` 保证稳定；把类别放进系统提示形成**封闭词表**；
输出用 `label in LABELS` 做校验（模型偶尔会输出「类别：新闻报道」这类多余文字）。

## 4. 常见坑

| 坑 | 现象 | 原因 | 正确做法 |
|---|---|---|---|
| 把「清晰」理解成「简短」 | 输出泛泛而谈、答非所问 | 缺少上下文与约束条件 | 提供充足上下文与具体约束；分清「清晰」≠「简短」 |
| 不写分隔符 | 模型把待处理文本当指令执行 | 指令与数据边界不清，易被提示注入 | 用 ` ``` ` / `<>` / `"""` 明确分隔指令与数据 |
| 只要求「输出 JSON」不指定键 | 键名随机、无法解析 | 模型自由发挥字段名 | 明确列出所有键名；进一步用 `response_format={"type":"json_object"}` 与 Pydantic 校验 |
| 直接让模型判断对错 | 模型认可明显错误的答案 | 顺承上下文的「附和」倾向 | 要求先自行求解、再对比，并加「在自己完成之前请勿决定」 |
| 依赖 prompt 精确控制长度 | 输出比要求长/短 | 长度依赖分词器，字符统计不精确 | prompt 给软约束，代码侧做截断与校验重试 |
| 概括与抽取混用 | 想只要某一角度信息却仍夹带其他信息 | Summarize 会保留整体语义 | 明确写「提取…信息」而非「概括」，并说明过滤其他信息 |
| 多语种输出顺序不定 | 后处理解析失败 | 未固定输出顺序 | 在 prompt 中固定字段顺序（中文→英文→法语→…） |
| few-shot 示例与目标格式不一致 | 模型模仿了错误的格式 | 示例本身不规范 | 示例必须与期望输出**逐字符同构**（含标点、字段名） |
| 示例里放模型的真实输出 | 错误被固化进 prompt | 用未经清洗的输出当示例 | 示例应由人工撰写并经校验 |
| 一次改多处 prompt | 无法归因，越改越乱 | 多变量同时变化 | 每次只改一个变量，记录结果（把 prompt 当版本管理） |
| 分类任务用高 temperature | 同一输入结果不稳定 | 采样随机性 | 分类/抽取/匹配用 `temperature=0` |
| 忽视输出校验 | 线上偶发解析崩溃 | 模型输出不完全受控 | 词表校验 + JSON 校验 + 失败重试/降级 |

## 5. 面试问答

**Q1：提示工程的两大原则是什么？分别解决什么问题？**

<details><summary>参考答案</summary>

两大原则是「**写清晰的指令**」与「**给模型充足的思考时间**」。

- 写清晰的指令：解决**任务对齐**问题。过简略的 prompt 让模型难以把握具体任务。
 落地技巧包括：清晰详尽地表达需求、用分隔符区分指令与数据、要求结构化输出、
 提供 few-shot 参考示例、让模型扮演角色。
- 给模型充足的思考时间：解决**复杂任务正确率**问题。模型与人类一样，匆忙下结论容易出错。
 落地技巧包括：在 prompt 中指定有序步骤（先摘要、再翻译、再抽取、最后输出 JSON），
 以及让模型先自行求解再与给定答案对比。

一句话：第一条让模型知道「要做什么」，第二条让模型「算得对」。
</details>

**Q2：为什么在判断「学生答案是否正确」这类任务中，要要求模型先自己解题？**

<details><summary>参考答案</summary>

因为语言模型有很强的**顺着上下文续写**的倾向。如果直接把「问题 + 学生解答」丢给模型并问「是否正确」，
模型容易顺着学生解答的推理链条往下接，从而认可一个错误的答案（示例中学生把维护费用写成
`100,000 + 100x`、总费用写成 `450x + 100,000`，模型回答「学生的解决方案是正确的」）。

改为要求「首先自己解决问题，再与学生的解决方案比较」并加上「**在自己完成问题之前，请勿决定学生的解决方案是否正确**」，
模型就会先生成自己的答案（正确为 `360x + 100,000`），再逐项对比得出「不正确」。
本质是：**用一个显式的中间产物（自己的解）作为判断依据，阻断模型依赖给定文本的捷径**，
同时把「判断」转化为「求解 + 比对」两个更简单的子任务。这与 chain-of-thought 的思路一致。
</details>

**Q3：在金融信息抽取任务中，如何保证模型输出的可解析性？**

<details><summary>参考答案</summary>

分四层保障：

1. **定义 schema**：先明确实体类型与属性，例如 `{'金融': ['日期','股票名称','开盘价','收盘价','成交量']}`，
 并在 prompt 中给出，让模型知道要抽哪些字段。
2. **约定缺失与多值规则**：句子中不存在的信息用 `['原文中未提及']` 表示，多个值用 `,` 分隔，
 避免模型自行发明占位符或格式。
3. **few-shot 示范完整结构**：给出一个 `<User>` 句子与人工写好的 `<Bot>` JSON，
 让模型模仿字段名与结构；服务端支持时再加 `response_format={"type": "json_object"}` 强制 JSON。
4. **代码侧后处理与校验**：先 `clean_response` 剥离 ` ```json ` 围栏，再 `json.loads`，
 并用 Pydantic 模型校验字段与类型（缺字段/类型错误可触发重试）。

这四层里最容易被忽略的是第 4 层——**模型输出永远要当作不可信输入处理**，
只靠 prompt 约定不足以支撑线上稳定性。
</details>

## 6. 自测题

**1. 写出提示工程「清晰指令」的四种构造技巧，并各举一个简短示例。**

<details><summary>参考答案</summary>

① **分隔符**：`把用三个反引号括起来的文本总结成一句话。```{text}``` `；
② **结构化输出**：`请生成书籍清单，以 JSON 返回，包含键 book_id、title、author、genre`；
③ **参考示例（few-shot）**：先给一组「孩子问耐心 / 祖辈用隐喻回答」的样例，再问「何为韧性」；
④ **角色扮演**：`我需要你充当一个 AI 算法面试官的角色，一次问一个面试常考题`。
</details>

**2. 概括（Summarize）和抽取（Extract）如何区分？各适合什么需求？**

<details><summary>参考答案</summary>

概括是对整段文本做压缩，**会保留整体语义**——即使指定「侧重价格与质量」，
输出中仍可能夹带「快递提前到货」这类其他信息。抽取是**只取某一角度的信息并过滤掉其余内容**。
如果只关心某一维度（如只关心运输时效），应明确写「提取……相关的信息」并要求过滤其他内容，
例如输出「产品运输相关的信息：快递提前一天到货。」。
</details>

**3. 为什么 prompt 里的长度限制（如"最多 30 个字"）常常不精确？工程上应如何处理？**

<details><summary>参考答案</summary>

因为语言模型判断文本长度依赖**分词器**，分词器在字符统计上不具备完美精度，尤其中文一词多 token 的情况，
因此输出长度只能在可接受误差范围内浮动。工程上应把 prompt 的长度要求当作**软约束**，
在代码侧做硬校验：超长则截断、或要求重写/重试，并在监控中统计长度分布。
</details>

**5. 用 ChatGLM-6B 跑的零样本/少样本任务，需要注意哪些工程限制？**

<details><summary>参考答案</summary>

语料明确提到：ChatGLM-6B 参数量 6B，下载到本地约需 12G+ 磁盘空间，**加载模型大概需要 13G 左右显存**；
显存不足时可进行**量化加载**以缩小模型成本（INT4 下推理最低约 6GB 显存）。
此外要注意：① 本地推理需按 ChatGLM 的对话模板拼接 prompt（`<User>`/`<Bot>` 或官方 `build_chat_input`）；
② 用 `inference` 推理、`init_prompts` 构造 prompt 的组织方式便于复用；
③ 抽取任务要单独写 `clean_response` 做后处理；④ 若换成 API 方式调用，则无需考虑显存，但要考虑 token 成本与网络延迟。
</details>
