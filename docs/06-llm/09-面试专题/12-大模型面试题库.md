## 2. 关键机制（高频题精讲）

### 2.1 用公式记住的三个核心定义

| 概念 | 公式 | 一句话解释 |
|---|---|---|
| 语言模型 | $P(W_1..W_n)=\prod_{i=1}^{n}P(W_i\mid W_1..W_{i-1})$ | 生成 = 逐词采样，打分 = 概率连乘（取 log 相加） |
| 缩放点积注意力 | $\mathrm{softmax}(QK^{\top}/\sqrt{d_k})V$ | 除以 $\sqrt{d_k}$ 防止 softmax 饱和、梯度消失 |
| 困惑度 | $\mathrm{PPL}=\exp(-\frac{1}{N}\sum\ln p(w_i))$ | 近似「平均在多少个词之间犹豫」，越小越好 |

**面试小技巧**：被问到「为什么除以 $\sqrt{d_k}$」，如果能补一句「点积方差随维度线性增长，softmax 会落入饱和区」
就明显高于只答「为了归一化」的水平。

### 2.2 高频对比题的「一句话本质区别」

| 对比 | 一句话本质区别 |
|---|---|
| BLEU vs ROUGE | BLEU 基于**精确率**（生成得准不准），ROUGE 基于**召回率**（覆盖全不全） |
| GPT vs BERT | GPT 是**单向 decoder、会生成**；BERT 是**双向 encoder、会理解** |
| MHA vs MQA vs GQA | 都是「几个 query 共享一套 K/V」的问题：MHA 不共享、MQA 全共享、GQA 分组共享 |
| Fine-tuning vs ICL | Fine-tuning **更新参数**，ICL **只改 prompt 不更新参数** |
| Hard Prompt vs Soft Prompt | 硬模板是**真实文本、人工设计**；软模板是**可训练向量、自动学习** |
| RAG vs 微调 | RAG **外置知识、可更新可溯源**；微调**内化能力、更新代价高** |
| 向量检索 vs BM25 | 向量检索匹配**语义**，BM25 匹配**词面**，二者互补构成混合检索 |
| 父子切分 | 子块**检索**（精度高），父块**返回**（上下文全） |
| Prompt Tuning vs P-Tuning v2 | 前者只在**输入层**加前缀，后者在**每一层**都加前缀 |
| `retrieval_k` vs `candidate_m` | 前者是**召回**宽度（宁多勿漏），后者是**精选**条数（宁精勿滥） |

### 2.3 三个最容易答漏的工程点

| 考点 | 容易漏掉的答案要点 |
|---|---|
| Function Call 原理 | **模型不会真的调用函数**，它只返回「函数名 + 参数 JSON」，由开发者在应用侧执行，再把结果作为 `role="tool"` 的消息送回模型做第二次生成 |
| Agent 与传统软件 | 除了「自主决策」，还要答出**范式迁移**：从「面向过程」到「面向目标」；以及任务范围从**有限域**到**无限域** |
| RAG 评估 | 除了四个指标名称，要能说出**归因逻辑**：忠实度低→修生成；上下文召回率低→修检索 |

## 3. 可运行示例

### 3.1 Function Call 完整两轮调用（可运行骨架）

```python
# 依赖：pip install openai>=1.0
# 关键：模型只返回「函数名 + 参数」，真正的函数执行发生在你的代码里
import json
import os
from openai import OpenAI

client = OpenAI(api_key=os.environ["OPENAI_API_KEY"])

# ---------- 第一步：定义真实函数 ----------
def get_current_weather(location: str) -> str:
    """得到给定地址的当前天气信息（示例返回固定数据）"""
    weather_info = {
    "location": location, "type": "晴",
    "high_temperature": "33", "low_temperature": "17", "week": "星期一",
    }
    return json.dumps(weather_info, ensure_ascii=False)

AVAILABLE_FUNCTIONS = {"get_current_weather": get_current_weather}

# ---------- 第二步：把函数定义（JSON Schema）交给模型 ----------
tools = [
{
"type": "function",
"function": {
"name": "get_current_weather",
"description": "获取给定位置的当前天气",
"parameters": {
"type": "object",
"properties": {
"location": {"type": "string", "description": "城市或区，例如北京、海淀"},
},
"required": ["location"],
},
},
}
]

# ---------- 第三步：两轮调用 ----------
def main():
    messages = [
    {"role": "system",
    "content": "你是一个天气播报小助手，你需要根据用户提供的地址来回答当地的天气情况，"
    "如果用户提供的问题具有不确定性，不要自己编造内容，提示用户明确输入"},
    {"role": "user", "content": "今天北京的天气如何"},
    ]

    # 第 1 轮：模型决定是否调用函数
    first = client.chat.completions.create(
    model="gpt-4o-mini", messages=messages, tools=tools, tool_choice="auto"
    )
    assistant_message = first.choices[0].message
    messages.append(assistant_message.model_dump())

    if assistant_message.tool_calls:
        tool_call = assistant_message.tool_calls[0]
        function_name = tool_call.function.name # 模型选中的函数名
        function_args = json.loads(tool_call.function.arguments) # 模型填好的参数
        print(f"[模型请求调用] {function_name}({function_args})")

        # 第 2 步：由「我们的代码」真正执行函数
        function_response = AVAILABLE_FUNCTIONS[function_name](**function_args)

        # 第 3 步：把函数结果作为 tool 消息送回模型
        messages.append({
        "role": "tool",
        "tool_call_id": tool_call.id, # 必须与本次调用 id 对应
        "name": function_name,
        "content": function_response,
        })

        # 第 2 轮：模型结合函数结果生成自然语言回答
        last = client.chat.completions.create(
        model="gpt-4o-mini", messages=messages, tools=tools, tool_choice="auto"
        )
        print("[最终回答]", last.choices[0].message.content)
    else:
        print("[直接回答]", assistant_message.content)

        if __name__ == "__main__":
            main()
```

**六步流程（面试要能背下来）**：
① 定义函数（真实 API／工具，或模拟函数）→
② 把函数定义作为 `tools` 参数提供给模型 →
③ 模型生成函数调用 JSON（含函数名与参数值）→
④ 后端系统根据 JSON 调用相应函数 →
⑤ 把函数结果作为额外上下文返回给模型 →
⑥ 模型综合原始查询与函数结果，生成最终输出。

## 4. 常见坑

| 坑 | 现象 | 原因 | 正确做法 |
|---|---|---|---|
| 以为模型会自己执行函数 | 代码里等不到结果 | 模型只返回函数名与参数的 JSON | 在应用侧解析参数、调用真实函数，再把结果回填 `role="tool"` |
| `tool_call_id` 对不上 | 报错或模型忽略结果 | 回填时没带对应 id | 严格使用 `tc.id`，多个调用要一一对应 |
| 忘了把 assistant 消息写回 | 模型重复调用同一函数 | 上下文中缺少「已请求过该调用」的记录 | 先把 `assistant_message.model_dump` 追加进 `messages` |
| 没有循环上限 | Agent 死循环、费用失控 | 模型可能反复调用工具 | 设 `max_turns`，超限返回兜底 |
| 函数描述含糊 | 模型选错函数或漏参数 | 工具描述是模型选择的唯一依据 | 描述写清用途与参数含义，`required` 标全 |
| 参数没做类型约束 | 传入类型错误、非法值 | JSON Schema 未写 `type`/`enum` | 用 `type`、`enum`、`required` 严格约束 |
| 让模型自由生成 SQL | SQL 注入、越权查询 | 执行了模型生成的任意语句 | 只暴露白名单查询函数 + 参数化查询 + 只读账号 + `LIMIT` |
| 用 `eval` 解析响应 | 可执行任意代码（严重安全风险） | 图方便解析文本 | 用 `json.loads`；示例中的 `eval(response.text)` 必须替换 |
| 没有超时与重试 | 外部 API 挂住整条链路 | 未设 `timeout` | 显式设超时并对失败返回可读错误给模型 |
| 直接把函数异常抛出 | 整个应用崩溃 | 未捕获异常 | 把错误信息作为工具返回值交给模型，让它换策略或告知用户 |
| 把 RAG 与 Function Call 混为一谈 | 答错定位 | 两者都是「外部信息」，但形态不同 | RAG 检索**非结构化文本片段**；Function Call 调用**结构化函数/API**，常配合使用 |

## 5. 面试问答

**Q1：为什么 Transformer 用 self-attention 取代 RNN？两者在长距离依赖与并行性上的差别是什么？**

<details>
<summary>参考答案</summary>

RNN 按时间步串行处理，存在两个硬伤：① **无法并行**——第 $t$ 步必须等第 $t-1$ 步算完，训练效率受序列长度限制；
② **长距离依赖衰减**——信息要沿时间步逐步传递，梯度在长链上容易消失。

self-attention 让序列中任意两个位置**直接计算相关性**，路径长度为 $O(1)$，因此长距离依赖建模更好；
而且所有位置可以一次性并行计算（矩阵乘法），充分利用 GPU。

代价是复杂度从 RNN 的 $O(n)$ 变成 $O(n^2)$（注意力矩阵是 $n\times n$），
这正是后续 Sparse Attention、GQA、KV Cache 优化要解决的问题。

</details>

**Q2：什么是 LoRA？为什么它能大幅降低微调成本？**

<details>
<summary>参考答案</summary>

LoRA 的核心假设是**下游任务所需的权重更新量是低秩的**。对原始权重 $W\in\mathbb{R}^{d\times d}$，
不做全量更新，而是用 $W + BA$ 近似，其中 $B\in\mathbb{R}^{d\times r}$、$A\in\mathbb{R}^{r\times d}$，$r\ll d$，
**只训练 $A$ 和 $B$**。

省成本的原因：① 可训练参数量下降几个数量级（`r=8` 时通常不到基座的 1%），
优化器状态、梯度与激活显存大幅减少；② 不需要为每个任务保存完整模型，只保存几十 MB 的 adapter；
③ 推理时把 $BA$ 合并回 $W$，**不引入额外推理延迟**。

工程要点：LoRA 学习率通常比全量微调大 1~2 个数量级（1e-4 ~ 3e-4），
`lora_alpha` 一般取 `r` 的 2~4 倍，`target_modules` 常选 `query`/`value`。
这与 P-Tuning 的区别是：LoRA 改的是**权重旁路**，P-Tuning 加的是**输入/每层的连续 prompt 向量**。

</details>

**Q3：什么是 RAG？它的完整流程是什么？如何评估？**

<details>
<summary>参考答案</summary>

RAG（Retrieval-Augmented Generation，检索增强生成）用「先检索、再生成」把外部知识接进大模型，
解决模型**无法获取最新知识与企业私有知识**的问题，本质是参数化知识与非参数化知识的结合。

完整流程：文档加载 → 分层切块（父块给上下文、子块建索引）→ 向量化入库 →
Query 改写（补全指代/扩展缩写/拆分对比查询）→ 意图分类路由 →
多策略检索（直接/HyDE/子查询/回溯）+ 稠密与稀疏混合 + 重排序 →
拼接上下文 → 受约束的 Prompt 生成（「只依据作答，不得编造」+ 兜底话术）。

评估用 RAGAS 一类框架，四个核心指标分两侧：
- 检索侧：`context_relevancy`（上下文是否只有相关信息，惩罚冗余）、
 `context_recall`（真实答案的论断有多少能归因于检索上下文）；
- 生成侧：`faithfulness`（答案是否由上下文推出，$F=|V|/|S|$，低分意味着幻觉风险）、
 `answer_relevancy`（反向生成问题 + 余弦相似度平均，衡量切题程度）。

归因逻辑是重点：**faithfulness 低 → 修生成（Prompt 约束、降温度）；context_recall 低 → 修检索（切块、混合检索、Query 改写）**。
评估数据集可用「测试样本代理 + 质量评审代理 + 评估代理」三代理自动构造，过滤后约保留一半。

</details>

**Q4：Function Call 的原理是什么？模型会自己执行函数吗？**

<details>
<summary>参考答案</summary>

Function Call 是 2023 年 6 月 OpenAI 公布的能力：**在语言模型中集成外部功能或 API 的调用能力**，
让模型在生成文本的过程中调用外部函数或服务，获取额外数据或执行特定任务。
它解决三个问题：**信息实时性**（训练数据不含最新新闻/股价）、
**数据局限性**（无法覆盖医疗、法律等所有领域）、**功能扩展性**（不可能内置所有能力）。

**模型不会自己执行函数**——它只返回「要调用的函数名 + 参数 JSON」，由开发者在应用侧执行。
完整流程六步：① 定义函数 → ② 把函数定义作为 `tools` 传给模型 →
③ 模型生成函数调用 JSON（函数名 + 参数）→ ④ 后端按 JSON 调用真实函数 →
⑤ 把函数结果作为 `role="tool"` 的消息回填（带上对应的 `tool_call_id`）→
⑥ 模型综合原始查询与函数结果生成最终文本。

工程要点：多函数场景用 `tool_choice="auto"` 让模型自选，靠循环回填实现链式调用（如先查航班号再查票价），
必须设最大轮次上限防死循环；数据库类工具要收敛在白名单函数里并用参数化查询，避免让模型自由生成 SQL。

</details>

**Q5：AI Agent 与 Function Call、工作流（Flow）之间是什么关系？**

<details>
<summary>参考答案</summary>

三者是「能力 → 机制 → 形态」的递进关系：

- **Function Call 是底层能力**：让模型能输出结构化的「函数名 + 参数」，是模型与外部世界交互的接口。
- **AI Agent 是使用该能力的自主系统**：Agent = **LLM + 记忆 + 任务规划 + 工具使用**，
 它在「思考 → 调用工具 → 观察结果」的循环中自主决定下一步，直到达成目标。
 Function Call 常被用作 Agent 的工具调用机制，比早期「让模型输出 Thought/Action 文本再正则解析」更稳定。
- **工作流（Flow）是固定编排**：流程由工程师预先写死（哪一步调什么、什么条件走哪个分支），
 模型只在个别节点上完成理解任务。

对比：工作流**可预测、可测试、成本低**，但只能解决**有限域**任务；
Agent **能解决无限域任务**、更灵活，但不确定性更高、token 成本更大。
实践建议：**流程稳定的部分用 Flow，需要动态决策的环节用 Agent**——
即「用工作流包围 Agent」，而不是让 Agent 承担一切。

</details>

## 6. 自测题

**1. 请默写语言模型的链式法则，并说明 BLEU 与 ROUGE 的方向差异。**

<details>
<summary>参考答案</summary>

链式法则：$P(W_1,\dots,W_n)=\prod_{i=1}^{n}P(W_i\mid W_1,\dots,W_{i-1})$。
它同时支撑两种用法：打分（概率连乘，工程上取 log 相加）与生成（逐词采样）。

BLEU 基于 **n-gram 精确率**（生成文本中有多少 n-gram 出现在参考文本里），主要用于机器翻译，
需要截断计数与简短惩罚；ROUGE 基于 **n-gram 召回率**（参考文本中有多少 n-gram 被生成文本覆盖），
主要用于摘要与问答生成。一句话：**BLEU 看生成得准不准，ROUGE 看覆盖全不全**。

</details>

**2. 一个 7B 模型想在本地 INT4 下推理，显存至少准备多少？显存不足时按什么顺序降级？**

<details>
<summary>参考答案</summary>

INT4 约每参数 0.5 字节，权重约 3.5~4GB；叠加 KV cache、激活值与框架开销（建议留 20%~30%），
实际建议 **8GB 以上**。给出的实测参考是 ChatGLM-6B：INT4 推理最低需 6GB、高效参数微调最低 7GB。

降级顺序：① 降量化等级（Q4_K_M，7B 权重从 FP16 约 14GB 降到约 4GB）→
② 降低 `num_ctx`（KV cache 随上下文长度线性增长）→ ③ 换更小参数规模模型 → ④ 减少并发。
显存 ≈ 权重 + KV cache + 运行开销，三项都要考虑。

</details>

**3. 什么是 Query 改写？至少说出四种改写手法及其适用场景。**

<details>
<summary>参考答案</summary>

Query 改写是 RAG 的第一步，因为用户提问方式与期望答案之间存在差距，
用户问题通常存在**信息不完整**与**噪声问题**两类毛病。四种手法：

① **历史会话改写**——多轮对话中 query 缺少上下文（指代消解），
如「摄像头方面具体改进了什么？」→「华为 meta70 手机的摄像头相比 meta60 有哪些具体改进？」；
② **关键词/缩写词改写**——关键词太短或使用缩写影响语义检索，
如「VR 技术在教育中的应用」→「虚拟现实（Virtual Reality）技术在教育中的应用有哪些？」；
③ **伪答案改写**——加入假设性答案增强语义丰富度；
④ **去冗余/关键词提取改写**——去掉无关背景与语气词，特别适合 BM25 类关键词检索；
另有**子查询改写**针对对比类查询（「C++ 和 Go 哪个更适合系统编程」拆成两个独立查询）。

工程要点：改写质量依赖 prompt 与模型能力，可能失败，因此建议**多次改写或多查询并行**，
再用**重排序**保证精度——即召回阶段宁多勿漏，精排阶段收口。

</details>

**4. Milvus 的 IVF_FLAT 中，`nlist` 与 `nprobe` 分别是什么？如何调？**

<details>
<summary>参考答案</summary>

`nlist` 是**建索引时**划分的簇数量，控制聚类粒度；`nprobe` 是**查询时**访问的簇数量，
控制搜索范围。二者不是同一阶段的参数，不能混用。

调参方向：`nprobe` 增大 → 搜索更多簇、返回更多候选、**精确度提高但查询时间增加**；
减小 → 速度快但可能牺牲精度。

调参流程：先固定 `nlist`（如 128），在测试集上逐步提高 `nprobe`，观察召回率与延迟曲线，
在延迟预算内取召回最高点。一般 `nprobe` 从 `nlist` 的 1%~10% 起调。
相关概念：IVF_FLAT 三步机制是「聚类 → 倒排索引 → 查询时只搜候选簇」，
因此把 $O(n)$ 的暴力搜索降到只搜少数簇。

</details>

**5. 设计一个企业知识库问答系统，你会怎么做？**

<details>
<summary>参考答案</summary>

按「目标 → 流程 → 关键取舍 → 评估」四段回答：

**目标**：让员工用自然语言问到企业内部文档（PDF/Word/PPT/图片扫描件）中的答案，
要求**有依据、可溯源、知识可更新、数据不出域**。

**整体流程**：
① 文档解析——多格式加载器 + OCR（扫描件/图表用 PaddleOCR），注入 `source`/`file_path`/`timestamp` 元数据；
② 分层切块——父块约 1200 字 / 子块约 300 字，子块带 `parent_id` 与 `parent_content`；
③ 向量化入库——BGE-M3 同时产出稠密与稀疏向量，入 Milvus（`IVF_FLAT` + `SPARSE_INVERTED_INDEX`）；
④ 查询处理——意图分类（小 BERT 路由）→ Query 改写（历史会话、缩写、子查询）；
⑤ 混合检索 + 重排序（RRFRanker 或 WeightedRanker）→ 取 `candidate_m` 个父块作上下文；
⑥ 生成——Prompt 约束「只依据作答、须说明来源、不足则给兜底话术」；
⑦ 缓存——Redis 以 `answer:{query}` 缓存结果并设 TTL。

**关键取舍**：
- 切片粒度 → 用父子分层化解；
- 召回宽度 vs 上下文长度 → `retrieval_k` 大、`candidate_m` 小；
- 延迟 vs 精度 → 用小模型做路由，把大模型只用在生成；
- 成本 → Redis 缓存 + 按需检索（通用知识不走检索）；
- 安全 → 权限过滤（`source_filter`）、数据私有化部署。

**评估**：用 RAGAS 跑 `faithfulness`/`answer_relevancy`/`context_relevancy`/`context_recall`，
固定评估集、每次只改一个变量、结果落 CSV 对比；
并补充业务指标（人工抽检、回答采纳率、无答案时的兜底转化率）。

</details>
