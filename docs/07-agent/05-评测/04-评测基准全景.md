> **一句话总结**：benchmark 分数是「在特定环境 + 特定工具集 + 特定预算 + 特定判题器下」的成绩，这四个前提任何一个变了分数就不可比——所以榜单数字既不能直接当作生产预期，也不能作为唯一的迭代目标；正确的用法是「用公开基准做回归、用自己的评测集做能力评估」。
> **前置知识**：[01-为什么Agent评测比LLM评测难](01-为什么Agent评测比LLM评测难.md) 的环境契约、[03-评测方法-单元测试与LLM即裁判](03-评测方法-单元测试与LLM即裁判.md) 的判题分层与显著性检验。
> **学完能做到**：
> 1. 说出主流 Agent 基准各自考察什么能力、任务形态、评测方式与已知局限，并判断哪一个与自己的项目对齐。
> 2. 从环境层、工具层、预算层、判题层四个维度诊断「为什么榜单分数不能代表生产可用性」。
> 3. 按分层抽样与契约冻结的规范，为自己的项目建一套可维护的评测集。

### 1.2 逐个基准的考察能力与局限

**SWE-bench** —— 考察什么能力：在只读 issue 描述的情况下定位跨文件缺陷、写出符合仓库风格的补丁。任务形态：仓库快照 + issue 文本 → 补丁。评测方式：`FAIL_TO_PASS`（原先失败、修复后必须通过）与 `PASS_TO_PASS`（不能被破坏）两组测试。已知局限：①**测试可被改动**，被测系统若能看到测试文件就可能直接改测试来「通过」；②环境安装失败率高，成功的样本里混杂了「装不上依赖」的噪声；③正确补丁可能早已 merged 进主干，模型记住补丁内容也能得分（污染）；④只覆盖 Python，且以 bug 修复为主，不覆盖新功能开发与重构。

**SWE-bench Verified** —— 考察什么能力：与 SWE-bench 相同，但聚焦于**人类确认可解且描述充分**的子集。任务形态与评测方式同上。已知局限：规模从 2294 降到 500，统计噪声更大；筛选过程本身引入了「什么样的任务算清晰」的主观判断；其余局限与 SWE-bench 相同（污染与测试可改动仍然存在）。

**WebArena** —— 考察什么能力：在真实感的网页应用里完成多步操作（下单、发帖、改配置、跨站查信息）。任务形态：自然语言指令 + 自托管站点。评测方式：**执行式校验**——运行后读取站点的数据库/后端状态判断意图是否达成，而不是做字符串匹配；论文还提出 functional correctness 指标。已知局限：①四个站点与真实互联网的分布差异大，多数真实站点有验证码、反爬、动态渲染；②依赖自托管环境的稳定性，容器故障会算作任务失败；③任务多为「可脚本化」的操作，对人类直觉依赖的模糊需求覆盖不足。

**OSWorld** —— 考察什么能力：真实 Ubuntu 桌面上的 GUI 操作与多应用协同。任务形态：开放式计算机任务（五类）。评测方式：执行式判分，通过读取文件系统、应用状态与截图判断。已知局限：①单任务耗时长，整套评测的**成本与时间都很高**；②截图判分对视觉细节（分辨率、主题、窗口位置）敏感，容易产生假失败；③虚拟机不稳定（崩溃、卡死）会污染结果；④任务设计难以覆盖真实办公中的模糊约束。

**GAIA** —— 考察什么能力：把网页浏览、文件解析、计算与推理组合成多步流程。任务形态：三级难度的问题，答案唯一且短。评测方式：短答案规范化后准精确匹配。已知局限：①**只约束答案、不约束过程**，模型可以用任意手段（包括猜）得到答案；②答案唯一导致对格式与表述要求严格，容易出现「推理对了但格式差一点」的假失败；③题目公开时间久，存在污染风险，需用新题或改写题复测；④不评估成本与延迟。

**AgentBench** —— 考察什么能力：作为 Agent 的多轮决策与环境交互能力。任务形态：8 个正交环境。评测方式：各环境自带指标（完成率、进度、胜率）。已知局限：①部分环境偏游戏化（卡牌游戏、谜题），与生产任务的迁移性弱；②各环境指标口径不统一，跨环境直接平均意义有限；③主要是**单 Agent 单工具**交互，对多 Agent 协作与复杂工具链覆盖不足。

**τ-bench** —— 考察什么能力：在多轮对话中既要用工具改对数据库，又要遵守书面政策。任务形态：模拟用户 + 领域 API + 政策文档的三方交互。评测方式：数据库终态比对 + 政策遵从检查。已知局限：领域较窄（零售、航空）；模拟用户的表达多样性有限；政策遵从的判定依赖预定义的规则集。

**BFCL** —— 考察什么能力：Function Calling 的语法、参数与调用决策正确性。任务形态：给定函数签名与用户请求，输出调用。评测方式：AST 结构匹配 + 实际可执行性校验。已知局限：**不涉及多步轨迹**，本质上是结构化输出评测；单轮/少轮为主，无法反映长程决策与错误恢复。

### 1.3 四类 Agent 的能力边界

| 类型 | 核心能力 | 典型基准 | 主要失败模式 | 为什么不能迁移到另一类 |
| --- | --- | --- | --- | --- |
| 编码 Agent | 代码理解、跨文件编辑、遵循仓库约定、跑测试 | SWE-bench / Verified | 环境装不上依赖；改动破坏既有行为；只改测试 | 代码任务有**可执行的验证器**，其他领域没有；浏览器/桌面任务的核心难点（视觉定位、页面漂移）在代码里不存在 |
| 浏览器 Agent | 视觉/结构定位、表单填写、跨页状态跟踪 | WebArena / Mind2Web / WebVoyager | 页面改版导致选择器失效；长流程中途丢失目标 | 依赖 DOM/视觉，无法处理命令行的文件系统操作；对无界面的 API 任务收益为零 |
| 桌面操作 Agent | GUI 操作、多应用协同、窗口管理 | OSWorld / AndroidWorld | 截图误判；单步失败即整链崩溃 | 步骤成本极高（每次点击都要截图推理），不适合高吞吐的文本/代码任务 |
| 通用助手 | 多工具编排、信息整合、长程规划 | GAIA / τ-bench / AgentBench | 中途放弃；把工具结果误用；忽略成本 | 通用性以「每项都不精」为代价，专项任务的准确率远低于专用 Agent |

结论：**「Agent 能力」不是一个标量。** 一个在 SWE-bench 上 70% 的模型，在 WebArena 上可能只有 20%——不是因为它「更笨」，而是因为两类任务调用的能力几乎不重叠。

## 2. 关键机制

### 2.1 benchmark 分数的四层前提

```text
分数 = f(模型能力, 环境层, 工具层, 预算层, 判题层)

环境层：镜像版本 / 依赖与数据快照 / 网络可达性 / 沙箱重置策略
工具层：可用工具集与版本（有无浏览器、有无 shell、shell 权限范围、有无代码执行）
预算层：max_steps / 超时 / 是否允许重试 / 是否允许多次采样取最优
判题层：判题器实现与版本 / 判题器是否对被测系统可见 / 部分完成的计分方式
```

逐项解释为什么它们都会让分数不可比：

| 层 | 变化示例 | 对分数的影响方向 |
| --- | --- | --- |
| 环境层 | 依赖版本升级让某些任务自动就能通过 | 分数上升，但能力没变 |
| 环境层 | 网络被限制导致搜索类任务失败 | 分数下降，像是能力退化 |
| 工具层 | 从「只能读文件」放开到「能执行代码」 | 分数大幅上升，掩盖了模型本身的推理能力 |
| 工具层 | shell 权限从只读改成可写 | 分数上升，但引入了越权风险（判题层未必能发现） |
| 预算层 | `max_steps` 从 30 提到 100 | 分数上升，成本与延迟同时上升 |
| 预算层 | 允许 k 次采样取最优 | 分数变成 `pass@k`，不能与单次结果比较 |
| 判题层 | 判题器从严格匹配改成语义等价 | 分数上升，可能掩盖格式遵从问题 |
| 判题层 | 判题器/测试文件对被测系统可见 | 分数被 reward hacking 抬高 |

### 2.2 环境差异的具体清单

在对比两个系统（或与榜单对比）之前，逐项核对：

```text
□ 镜像与依赖：基础镜像 ID、语言/库版本、系统包
□ 数据快照：数据库/文件系统的快照时间；网页是否提供了冻结副本
□ 网络可达性：能否访问公网、哪些域名被允许、是否有速率限制
□ 工具集：工具名单与版本；是否含浏览器、shell、代码解释器
□ 工具权限：读/写范围、是否允许网络写操作、是否有行数与超时上限
□ 步数与超时：max_steps、单步超时、整任务超时、是否允许重试
□ 采样策略：temperature、是否多次采样取最优、k 值
□ 环境重置：每个 case 前是否 reset；容器是否一次性创建销毁
□ 判题器：版本、是否可见、部分完成如何计分、失败归类规则
□ 成本口径：是否计入工具费、是否计入失败重试、是否计入环境开销
```

任何一项未对齐，两个分数之间的差值就包含了该项的贡献，无法归因给模型能力。

### 2.3 成本被忽略：一个具体的经济性计算

榜单几乎从不报成本，导致「贵 4 倍换 3 个点」这类决策被隐藏。

```text
系统 A：成功率 68%，单任务成本 $0.64  → 每次成功成本 = 0.64 / 0.68 ≈ $0.94
系统 B：成功率 71%，单任务成本 $2.91  → 每次成功成本 = 2.91 / 0.71 ≈ $4.10

按 10 万次任务/年估算：
  A 年成本 = 100000 × 0.64 ≈ $64,000
  B 年成本 = 100000 × 2.91 ≈ $291,000
  差额     ≈ $227,000 / 年

若要证明 B 值得，必须论证那 3 个百分点的成功率对应 ≥ $227,000 的年收益，
即「每提升 1 个点至少值 $75,667」。多数业务达不到这个门槛。
```

再叠加延迟：B 的单任务耗时如果是 A 的 3 倍，P95 会直接决定用户体验上限。**因此「分数不可比」之外还有第二个陷阱：分数可比了，经济性依然可能相反。**

### 2.4 如何为自己的项目选基准或自建评测集

```text
① 从生产日志抽样真实任务，标注类别与频次，得到「任务分布」
   —— 评测集必须复现生产分布，而不是复用论文里的任务分布
② 做能力对齐判断：现有 benchmark 在三个维度上是否覆盖我的任务？
   工具集对齐 / 环境形态对齐（CLI、浏览器、GUI）/ 判题方式对齐
③ 若有覆盖：用 benchmark 做「回归测试」（防退化），用自建集做「能力评估」（看真实水平）
   若没有覆盖：直接自建，不要强行套一个不对齐的榜单
④ 自建集构建规范：
   - 分层抽样：按类别与难度分层，每层 ≥30 个任务（少于 30 时置信区间宽到无法下结论）
   - 契约冻结：所有任务共享同一套镜像/快照/工具集/超时/预算
   - 每条任务写可自动判定的终态断言；无法自动判定的维度改用 Judge 并单独标注
   - 留出 held-out 子集不对外公开、不用于调 prompt
⑤ 评测集维护：环境变化会让任务「腐烂」，定期复跑并标记失效任务
⑥ 成本预算：先估算整套评测的成本与时长，再决定规模（用抽样子集做快速迭代）
```

### 2.5 基准腐烂（benchmark rot）

基准不是一次写就永远有效的：依赖升级、接口下线、网页改版、数据源变更都会让原本可解的任务变为不可解（或反之）。表现与应对：

| 现象 | 机制 | 应对 |
| --- | --- | --- |
| 同一模型半年后分数下降 | 依赖版本变化导致部分任务环境装不上 | 锁定镜像与依赖版本（容器化）；记录每个任务的最后验证时间 |
| 任务通过率突然集体上升 | 某依赖被预装、某接口开始返回缓存 | 定期做「空 Agent 基线」（不调用模型直接跑），检查是否有任务被自动通过 |
| 判题器与新环境不兼容 | 断言依赖的输出格式变了 | 判题器与评测集版本一起管理；CI 里跑自检 |
| 榜单分数无法复现 | 论文未公开环境细节 | 自建评测集时把环境契约写入元数据（见下方代码） |

一个实用做法是维护**空基线（null-agent baseline）**：让一个什么都不做的 Agent 跑完整套评测，记录它的成功率。任何非零的空基线都意味着有任务「不用做就能过」。

## 3. 可运行示例

### 3.1 依赖说明

只依赖 Python 标准库（`random`、`collections`）。Python 3.8+ 可直接运行。

### 3.2 自建评测集健全性检查 + 分数可比性诊断

```python
"""评测集健全性检查 + 分数可比性诊断。

依赖：仅标准库。
"""

import random
from collections import Counter

MIN_PER_CATEGORY = 30          # 每类任务数下限
MAX_DIFFICULTY_SHARE = 0.6     # 单一难度占比上限
BUDGET_USD = 50.0              # 整套评测的成本预算
BUDGET_SECONDS = 3600.0        # 整套评测的时长预算
ASSUMED_SUCCESS_RATE = 0.62    # 用于估算「每次成功成本」
DECLARED_SNAPSHOT = "snap-2024-05"
DECLARED_TOOLS = "default"


def build_tasks() -> list:
    """构造 120 条任务元数据，故意包含失衡与环境契约不一致。"""
    rng = random.Random(11)
    plan = [("config", 50), ("search", 18), ("ops", 14), ("safety", 38)]
    difficulties = ["easy"] * 78 + ["medium"] * 30 + ["hard"] * 12
    rng.shuffle(difficulties)

    tasks, i = [], 0
    for category, n in plan:
        for _ in range(n):
            tasks.append({
                "task_id": "t-%03d" % i,
                "category": category,
                "difficulty": difficulties[i],
                # 每 15 条留 1 条缺终态断言（需人工或 Judge 判分）
                "has_terminal_assert": i % 15 != 0,
                # 少量任务用了旧快照 / 扩展工具集 —— 契约不一致的元凶
                "env_snapshot_id": "snap-2024-03" if i % 15 == 3 else DECLARED_SNAPSHOT,
                "tools_profile": "extended" if i % 20 == 7 else DECLARED_TOOLS,
                "timeout_s": 120,
                "estimated_cost_usd": round(rng.uniform(0.01, 0.09), 4),
                "estimated_seconds": round(rng.uniform(5, 60), 1),
            })
            i += 1
    return tasks


def check_dataset(tasks: list) -> None:
    total = len(tasks)

    print("=== 1) 分层抽样是否达标（每类 >= %d）===" % MIN_PER_CATEGORY)
    for cat, n in sorted(Counter(t["category"] for t in tasks).items()):
        print("  %-8s n=%-4d %s" % (cat, n, "OK" if n >= MIN_PER_CATEGORY
                                    else "不足，结论不稳"))

    print("\n=== 2) 难度分布是否失衡（单一难度 <= %.0f%%）==="
          % (MAX_DIFFICULTY_SHARE * 100))
    for d in ("easy", "medium", "hard"):
        n = sum(1 for t in tasks if t["difficulty"] == d)
        share = n / total
        flag = "  ← 超过阈值，总体成功率会被该层主导" if share > MAX_DIFFICULTY_SHARE else ""
        print("  %-7s n=%-4d 占比 %5.1f%%%s" % (d, n, share * 100, flag))

    print("\n=== 3) 是否有无法自动判定的任务 ===")
    missing = [t["task_id"] for t in tasks if not t["has_terminal_assert"]]
    print("  缺终态断言 %d 条（%.1f%%）：%s%s"
          % (len(missing), len(missing) / total * 100, missing[:5],
             " ..." if len(missing) > 5 else ""))

    print("\n=== 4) 环境契约是否一致（不一致则分数不可比较）===")
    for key in ("env_snapshot_id", "tools_profile", "timeout_s"):
        counts = Counter(t[key] for t in tasks)
        flag = "OK" if len(counts) == 1 else "不一致 → 分数不可直接比较"
        print("  %-16s %-34s %s" % (key, dict(counts), flag))

    print("\n=== 5) 成本与时长预算 ===")
    cost = sum(t["estimated_cost_usd"] for t in tasks)
    secs = sum(t["estimated_seconds"] for t in tasks)
    print("  预计总成本 $%.2f（预算 $%.2f）  %s"
          % (cost, BUDGET_USD, "OK" if cost <= BUDGET_USD else "超预算，需缩减规模"))
    print("  预计总时长 %.0fs ≈ %.1f min（预算 %.0fs）  %s"
          % (secs, secs / 60, BUDGET_SECONDS,
             "OK" if secs <= BUDGET_SECONDS else "超时长，需并发或减规模"))
    print("  每次成功成本期望 ≈ $%.4f（按成功率 %.0f%% 估算）"
          % (cost / (total * ASSUMED_SUCCESS_RATE), ASSUMED_SUCCESS_RATE * 100))


def diagnose_comparability(run_a: dict, run_b: dict, tasks: list) -> None:
    """两轮历史评测的可比性诊断。"""
    by_id = {t["task_id"]: t for t in tasks}

    print("\n=== 6) 两轮评测的可比性诊断 ===")
    for run in (run_a, run_b):
        bad = [tid for tid in run["ran"]
               if by_id[tid]["env_snapshot_id"] != run["env_snapshot_id"]
               or by_id[tid]["tools_profile"] != run["tools_profile"]]
        print("  %s 声明 %s / %s：跑了 %d 条，其中 %d 条契约与声明不符"
              % (run["date"], run["env_snapshot_id"], run["tools_profile"],
                 len(run["ran"]), len(bad)))

    same = (run_a["env_snapshot_id"] == run_b["env_snapshot_id"]
            and run_a["tools_profile"] == run_b["tools_profile"])
    print("  两轮声明契约%s → %s"
          % ("相同" if same else "不同",
             "分数可以直接比较" if same else "分数不可直接比较"))

    common = sorted(set(run_a["ran"]) & set(run_b["ran"]))
    usable = [tid for tid in common
              if by_id[tid]["env_snapshot_id"] == run_a["env_snapshot_id"]
              and by_id[tid]["tools_profile"] == run_a["tools_profile"]]
    print("  共同任务 %d 条，其中契约一致、可比较的 %d 条" % (len(common), len(usable)))
    if len(usable) < len(common):
        print("  → 只能在 %d 条子集上下结论；其余 %d 条需统一契约后重跑"
              % (len(usable), len(common) - len(usable)))


def main() -> None:
    tasks = build_tasks()
    check_dataset(tasks)

    consistent = [t["task_id"] for t in tasks
                  if t["env_snapshot_id"] == DECLARED_SNAPSHOT
                  and t["tools_profile"] == DECLARED_TOOLS]
    stale = [t["task_id"] for t in tasks if t["env_snapshot_id"] == "snap-2024-03"]
    ran = sorted(consistent + stale)

    run_a = {"date": "2024-05-20", "env_snapshot_id": DECLARED_SNAPSHOT,
             "tools_profile": DECLARED_TOOLS, "ran": ran}
    run_b = {"date": "2024-06-18", "env_snapshot_id": DECLARED_SNAPSHOT,
             "tools_profile": DECLARED_TOOLS, "ran": ran}
    diagnose_comparability(run_a, run_b, tasks)

    print("\n  提示：若第二轮只换模型、契约不变 → 分数可比、差异可归因给模型；")
    print("        若同时升级了镜像或工具集，就必须先冻结契约再重跑。")


if __name__ == "__main__":
    main()
```

这份报告的读法：**前三项检查评测集本身是否可信，第四、五项检查跑得起且跑得对，第六项检查历史分数能不能拿来比较。** 在真实项目里，最常见的错误不是「没有评测」，而是「评测集类别失衡 + 契约不一致」，导致分数看起来在动、其实不可解释。

## 4. 常见坑

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 直接拿榜单分数当生产预期 | 忽略了环境、工具集与预算差异 | 先在自己的任务分布上小规模验证，再做容量与成本规划 |
| 与榜单对比时「我们只有 40%」 | 工具集比榜单更保守（无浏览器/无代码执行）或预算更小 | 在报告里写明工具集、步数上限与超时，并按能力对齐后重新比较 |
| 只看成功率，忽略成本 | 榜单不报成本，团队也沿用这个习惯 | 补报单任务成本与每次成功成本；把成本作为负项进指标组 |
| 把 benchmark 当成迭代目标，分数涨但产品没变好 | Goodhart 化：针对公开测试集过拟合 | benchmark 只做回归门禁；能力评估用自建 held-out 集 |
| 评测集任务半年后集体失效 | 基准腐烂：依赖、接口、网页改版 | 容器化锁定镜像与依赖；记录每个任务的最后验证时间；维护空基线 |
| 自建集类别失衡，总体成功率被简单任务主导 | 从日志抽样时按流量抽样，而流量本身偏向简单任务 | 按类别与难度分层抽样，分层报告；必要时加权 |
| 任务数太少（<30）却下强结论 | 置信区间过宽，差异是噪声 | 每层 ≥30 条；用配对检验（见 [03](03-评测方法-单元测试与LLM即裁判.md)）；报置信区间 |
| 判题器对被测系统可见，分数虚高 | reward hacking：直接改测试/断言 | 判题逻辑放在 Agent 不可见的独立容器；held-out 验证 |
| 把多模态基准分数与纯文本 Agent 比较 | 输入模态、工具集完全不同 | 只与同模态、同工具集的系统比较 |
| 只测能力不测稳定性 | 只报 `pass@k`（多试几次取最优） | 同时报 `pass^k`；自动化场景以 `pass^k` 作为准入指标 |
| 换模型版本后分数变化无法归因 | 同时升级了镜像/工具集/超时 | 一次只改一个变量；用契约一致的任务子集比较 |

## 5. 面试问答

<details>
<summary><strong>Q1：如果我告诉你「某模型 SWE-bench Verified 78%」，你会追问哪些问题才敢用它做生产代码 Agent？</strong></summary>

按「可比性 → 方法学 → 过程 → 系统 → 迁移」追问。①**可比性**：工具集是什么（能否执行代码、能否联网、shell 权限范围）？`max_steps` 与超时是多少？是否允许 k 次采样取最优（若允许，78% 是 `pass@k` 而不是单次成功率）？判题器是否对被测系统可见？②**方法学**：500 个实例里有没有环境安装失败被计为失败的样本？测试文件是否对 Agent 可读（可读就可能改测试）？评测时间是什么时候（训练截止时间是何时，是否存在补丁污染）？③**过程**：有没有统计越权（改了不该改的文件）、无效步数、以及「通过但破坏了既有行为」的比例？④**系统**：单任务成本与 P95 延迟是多少？`pass^k`（k 取业务要求的重试次数）是多少？⑤**迁移**：我的仓库是 Python 吗？我的任务是 bug 修复、功能开发还是重构？如果主要是新功能开发，SWE-bench 的覆盖度很低，需要自建评测集。只有这五组问题基本对齐，78% 才能外推成「值得做 PoC」的信号，而不是「生产可用」的结论。

</details>

<details>
<summary><strong>Q2：怎么为自己公司的业务 Agent 建评测集？给一个可落地的流程。</strong></summary>

①**从生产分布出发**：从真实日志抽样任务（包含失败与边缘案例），标注类别与频次，让评测集的任务分布尽量复现生产分布——而这通常与公开基准的分布不同，这是自建的第一理由。②**能力对齐判断**：在工具集、环境形态（CLI / 浏览器 / GUI）、判题方式三个维度上，看是否存在可复用的公开基准；有覆盖的用它做回归测试，没覆盖的直接自建。③**分层抽样与规模**：按类别与难度分层，每层 ≥30 条（低于此值时置信区间宽到无法下结论）；对高价值但低频的任务可以加权上报。④**契约冻结**：所有任务共享同一套镜像、数据快照、工具集与版本、超时与预算，并把契约写进任务元数据（这是"分数可比"的前提）。⑤**断言设计**：每条任务写可自动判定的终态断言；必须调用工具用序列断言；无法自动判定的维度用 rubric + Judge，并先用金标签集校准 Kappa。⑥**留出 held-out**：划分出不对内公开、不用于调 prompt 的子集，用于最终汇报与上线门禁。⑦**维护机制**：定期复跑检测"腐烂"任务，维护"空基线"（什么都不做的 Agent）来发现"不用做就能过"的任务；随着生产分布变化扩充任务。⑧**成本预算**：先估算整套评测的成本与时长，用抽样子集做日常迭代、全量集做发布前评估。

</details>

<details>
<summary><strong>Q3：为什么 benchmark 分数高不等于生产可用？请从环境、工具、成本三个角度讲。</strong></summary>

①**环境**：benchmark 预先冻结了镜像、依赖、数据快照与网络可达性，任务边界清晰；生产环境是活的——接口会改版、页面会重构、数据有脏值、依赖会升级、网络会抖动。在冻结环境里成功率 70% 的系统，换到有噪声的真实环境里常常显著下降，因为评测从未测量"环境不确定性下的鲁棒性"。②**工具**：benchmark 的工具集是作者精心挑选的、与任务匹配的窄集；生产的工具集要么更宽（更多越权风险与选择困难），要么更窄（缺少 key 工具）。此外评测里工具总是"可用且稳定"的，生产里工具会限流、超时、返回 5xx——错误恢复能力在榜单上几乎从不被考核。③**成本**：榜单不报成本，而成本决定能不能规模化。一个成功率 71%、单任务 $2.91 的系统，其"每次成功成本"约 $4.10；相比成功率 68%、单任务 $0.64（每次成功 $0.94）的系统，按 10 万次/年算要多花二十多万美元——除非那 3 个百分点对应极高价值任务，否则不可选。再加上延迟：Agent 的延迟是逐轮累加的，步数上限往往同时是成本上限与 P95 延迟的决定因素，而榜单几乎从不报 P95。三个角度合起来说明：**benchmark 测的是"在受控条件下的能力上限"，生产要的是"在不受控条件下的成本可控的下限"。**

</details>

## 6. 自测题

<details>
<summary>参考答案</summary>

**1. 系统 A 成功率 68%、单任务成本 $0.64；系统 B 成功率 71%、单任务成本 $2.91。请比较两者的经济性并给出建议。**

`每次成功成本 = 单任务成本 / 成功率`。A：`0.64 / 0.68 ≈ $0.94`；B：`2.91 / 0.71 ≈ $4.10`，是 A 的约 4.4 倍。按 10 万次任务估算年成本：A ≈ `100000 × 0.64 = $64,000`；B ≈ `100000 × 2.91 = $291,000`；差额约 **$227,000/年**。也就是说，若采用 B，必须论证那 3 个百分点的成功率每年能带来超过 22.7 万美元的收益（等价于每提升 1 个点至少值 $75,667）。建议：除非这些任务本身是高价值场景（例如每单价值极高、失败成本远大于 $2.27/次的差价），否则选 A；若确实需要 B 的成功率，优先考虑「分层路由」——用 A 处理大多数任务，只把高价值或高难度任务路由给 B，从而把成本花在刀刃上。

</details>

<details>
<summary>参考答案</summary>

**2. 为什么环境契约（镜像/快照/工具集/超时/预算）不统一时，两个 benchmark 分数不可比较？请举一个具体例子。**

因为分数是 `f(模型能力, 环境层, 工具层, 预算层, 判题层)` 的函数值，契约不一致时两个分数的差异包含了契约差异的贡献，无法归因给模型。具体例子：系统 X 在「只读文件 + 无代码执行」的工具集下测得 55%，系统 Y 在「可写文件 + 可执行代码 + 联网」的工具集下测得 72%。这 17 个点里可能绝大部分来自工具集放宽——Y 可以直接写脚本批量处理，而 X 只能逐步手工调用。再比如 `max_steps` 从 30 提到 100：同一个模型在需要 60 步的长程任务上会从「失败」变成「成功」，分数上升但模型能力没变。所以发现分数差异时的第一件事，不是归因给模型，而是核对环境契约清单（镜像与依赖、数据快照、网络可达性、工具集与版本、工具权限、步数与超时、采样策略、环境重置、判题器版本、成本口径），并在契约一致的任务子集上重新比较。

</details>

<details>
<summary>参考答案</summary>

**3. 什么是「基准腐烂」（benchmark rot）？怎么检测和缓解？**

基准腐烂指原本有效的评测任务随时间失去有效性：依赖升级导致任务环境装不上、接口下线、网页改版、数据源变更，于是同一模型的分数会无端漂移，且不可复现。**检测手段**：①定期复跑历史版本（同一模型 + 同一配置），若分数发生变化而模型未改，说明是环境漂移；②维护**空基线（null-agent baseline）**——让一个什么都不做的 Agent 跑完整套评测，任何非零的成功率都说明存在「不用做就能通过」的任务（例如某条断言在初始状态下就为真）；③记录每个任务的最后验证时间与环境版本，超期任务进入复核队列。**缓解手段**：①容器化并锁定镜像与依赖版本，把环境快照 ID 写进任务元数据；②对网页类任务保存冻结副本（DOM 快照或离线站点），而不是依赖实时互联网；③把判题器与评测集一起做版本管理，在 CI 里跑评测集自检；④环境变化无法避免时，及时标记失效任务并重跑基线，避免把环境漂移误读为模型能力变化。

</details>

<details>
<summary>参考答案</summary>

**4. 出题：如果你要评测一个「帮用户改云服务器配置」的内部 Agent，你会选公开基准还是自建？请给出理由与前三个动作。**

**选手自建（可以借鉴但无法直接使用公开基准）。** 理由：①**工具集不对齐**——SWE-bench 面向代码仓库与测试，WebArena 面向网页，OSWorld 面向桌面 GUI，而云配置任务的核心是调用内部 API/CLI、理解企业内部权限模型与变更窗口；②**环境无法复用**——真实云账号、权限体系、变更审批流都是内部特有的，公开基准的环境是模拟的；③**后果严重性不同**——配置错误可能导致生产故障，因此过程层（越权、副作用、变更窗口遵从）与安全层指标比公开基准重要得多，而公开基准基本不测这些。**前三个动作**：①从变更系统的审计日志抽样真实工单，标注类别（扩容、改安全组、调参、回滚）与频次，得到任务分布；②为每条任务写终态断言（配置值必须等于 X、不得改动白名单外的资源、必须在变更窗口内执行），并把「不得改动」作为独立断言通道；③搭建一次性沙箱环境（每个 case 前 reset、容器一次性销毁），冻结 API 版本与工具集版本，然后先在 30-50 条任务上跑通并计算「空基线」（什么都不做时的通过率必须为 0）。

</details>
