> **一句话总结**：Agent 评测的失败从来不是"失败"两个字能描述的——**同一个失败要同时被贴上多个标签**（`missing_evidence` + `tool_error` + `goal_not_completed`），再由稳定规则选出主归因；而"改进"也不能靠两个百分比相减来宣布，配对设计要用 **McNemar exact test**，置信区间必须**以 `taskId` 为聚类单位**重采样，否则同一任务的多次重复会被当成独立样本，把噪声算成信号。
> **前置知识**：[01 篇](01-项目复盘-AgentEvalLab.md) 的评测器判定顺序与证据信任链、[02 篇](02-用Manifest保证评测可复现.md) 的 `taskId + repeatId + seed` 配对主键、二项分布与 Bootstrap 重采样的基础。
> **学完能做到**：
> 1. 用自己的话说清九种 `violation` 的判定逻辑，并解释为什么违规的**追加顺序**就是归因优先级。
> 2. 构造 2×2 配对表、手算并用代码验证 McNemar exact p-value，判断"62% → 71%"这类提升是否显著。
> 3. 实现以 `taskId` 聚类的 Bootstrap 置信区间，并演示"重采样单位选错会得出相反上线结论"。

## 1. 失败分类学：九种标签与判定优先级

### 1.1 标签表

评测器的 `FailureType` 是一个九值枚举，其中 `none` 表示通过，其余八个是违规标签：

| 标签 | 判定条件 | 典型现场 |
| --- | --- | --- |
| `missing_trajectory` | `events.length === 0` | 运行器返回了空轨迹；采集管道断了 |
| `zero_step_termination` | 没有任何 `tool_call` 事件 | 模型直接回答；或工具白名单为空导致全部被拦 |
| `empty_final_answer` | 没有 `final` 事件，或 `final.text.trim()` 为空 | Agent 做完动作忘了输出结论；流式输出被截断 |
| `invalid_evidence_source` | 声明的证据无法绑定到成功 `tool_result` 的产出，或值/哈希不一致 | 模型自报"已确认"；证据来源事件不存在；值被改写 |
| `missing_evidence` | 任务要求的 claim 不在已验证证据集里，**或**未被最终回答引用 | 只抓到一部分数据；证据验证了但没写进结论 |
| `tool_error` | 存在失败的 `tool_result` **且** `status === "failed"` | 工具连续失败，运行器仍返回 failed |
| `blocked` | `status === "blocked"` | 登录墙、验证码、权限不足、依赖不可用 |
| `goal_not_completed` | `status === "failed"` | 兜底标签：运行状态本身就没完成 |

### 1.2 判定顺序 = 归因优先级

`evaluateRun` 用"顺序追加、首个即主因"的方式决定 `primaryFailure`，这个顺序在代码里是**写死**的：

```text
1. missing_trajectory   2. zero_step_termination   3. empty_final_answer
4. invalid_evidence_source   5. missing_evidence（缺验证 / 缺引用，同 code 合并）
6. tool_error   7. blocked   8. goal_not_completed
```

它隐含一条判据链：**从"根本没有产生可判定的东西"到"产生了但没做完"，最后到"做完了但没做成"。** 越靠前越接近"事实性问题"（轨迹空、没动作、没输出），越靠后越接近"状态性问题"（运行器说失败）。

为什么顺序必须写死而不能用"最严重"排序？因为"严重"是主观的、随上下文变化的：对浏览器 Agent，"被登录墙挡住"是正常终止（`blocked`）；对内部运维 Agent，同一现象是严重故障。一旦主归因依赖主观权重，跨版本对比就失真——**同一现象在两次评测里可能被归到不同标签，成功率变化的原因再也追不回来。**

### 1.3 三组容易混淆的标签

**`missing_evidence` vs `invalid_evidence_source`。** 前者是"缺"，后者是"假"。`missing_evidence` 表示任务要求的 claim 压根没出现在有效证据里；`invalid_evidence_source` 表示 **Agent 声明了自己有证据，但那条声明站不住**（来源事件不存在、来源是失败的 `tool_result`、`value` 或 `contentHash` 与来源不一致）。两者的工程含义完全不同：前者多半是 Agent 能力/流程问题，后者涉及**数据可信度**，优先级更高——因为它意味着"这个系统会自报成功"。

**`tool_error` vs `blocked`。** `tool_error` 的触发条件是"有失败的工具结果 **且** 整体状态是 failed"。注意这个 `且`：如果工具失败了三次但第四次成功了、整体 completed，那么 `tool_error` **不会**触发——因为"错误后未恢复"这个描述不成立。`blocked` 只看 `status`，不看工具事件，它表达的是"Agent 明确判断自己被挡住了"。两者可以同时出现，但如果 Agent 在被挡住时把状态写成 `completed`，那它会落进 `zero_step_termination` 或 `missing_evidence`，而不是 `blocked`——**隐瞒阻断会以别的标签暴露出来**。

**`zero_step_termination` vs `empty_final_answer`。** 前者是"没做事"，后者是"没说话"。一条轨迹可以同时命中两者，此时主归因是 `zero_step_termination`（顺序更靠前）。这个区分很实用：只有 `empty_final_answer` 说明工具链路是通的、只是输出环节丢了；两个都有说明整条链路都没启动。

### 1.4 一条轨迹能同时命中几个标签

这是 Agent 评测与 LLM 评测在数据结构上的关键差异。一个典型的"看起来完成了"的失败轨迹：

```text
tool_call   step=1  search
tool_result step=1  success=false          ← 工具失败
tool_call   step=2  search
tool_result step=2  success=true  evidence=[query]
verification step=1 success=true  evidence=[query]
final       step=2  text="搜索完成"  citations=["query"]
status: failed
任务要求证据: ["query", "count"]
```

判定结果：

| 标签 | 是否命中 | 原因 |
| --- | :-: | --- |
| `missing_evidence` | ✓ | `count` 从未被验证，且未被引用 |
| `tool_error` | ✓ | 有失败工具结果，且 `status === "failed"` |
| `goal_not_completed` | ✓ | `status === "failed"` |
| `zero_step_termination` | ✗ | 有 `tool_call` |
| `empty_final_answer` | ✗ | `final.text` 非空 |
| `invalid_evidence_source` | ✗ | `query` 能绑定到成功工具产出的同值证据 |
| `missing_trajectory` / `blocked` | ✗ | 有事件；`status` 不是 blocked |

三条标签，`primaryFailure = missing_evidence`。**如果数据结构只允许一个失败原因，我们就丢掉了"工具失败过"这条最有价值的改进线索。**

## 2. 证据式判定：为什么"状态字符串对了"不算通过

### 2.1 三种"看起来成功"

| 反例 | 表面证据 | 为什么不算通过 | 对应标签 |
| --- | --- | --- | --- |
| 模型直接输出"已完成搜索，共 42 条" | `final.text` 含关键词、`status=completed` | 没有任何 `tool_call`，42 是编的 | `zero_step_termination` |
| 页面加载成功，模型说"页面正常" | 工具返回 200、`status=completed` | 用户要的信息没被提取，`requiredEvidence` 里没有任何 claim 被验证 | `missing_evidence` |
| 遇到登录墙，模型声称"任务完成" | 有一条 `verification` 事件自报 `blocker=登录墙` | 该声明无法绑定到成功 `tool_result` 的产出 | `invalid_evidence_source` |

第三种最隐蔽：它**同时**有一条看起来合法的 `verification` 事件和一句完整的话。如果判定逻辑是"检查最终回答里有没有'完成'且有没有 verification 事件"，它就会通过。

### 2.2 证据信任链

项目把"证据可信"拆成三段必须同时成立的检查：

```text
第一段：来源必须真实 —— verification 声明的每条 EvidenceRecord 必须能在
        「成功的 tool_result 事件」的产出表里找到，key 是 (sourceEventId, claimId)，
        且要求 record.sourceEventId === 该事件的 eventId
第二段：内容必须一致 —— 来源表里的 value / contentHash 必须等于声明里的值
第三段：必须被引用 —— final 事件的 citations 必须包含任务要求的每个 claim
```

第一段的实现有个容易漏掉的细节——构建来源表时要求 `sourceEventId` **自指**：

```ts
for (const event of run.events) {
  if (event.type !== "tool_result" || event.success !== true) continue;   // 失败工具不产出可信证据
  for (const record of event.evidence ?? []) {
    if (record.sourceEventId !== event.eventId) continue;                 // 必须由本事件产出
    sourceEvidence.set(`${event.eventId}::${record.claimId}`, {
      value: record.value,
      contentHash: record.contentHash,
    });
  }
}
```

没有这道自指检查，一个 `tool_result` 就可以"代持"任意其他事件的证据，来源图立刻失去意义。

### 2.3 五种伪造与对应的拦截点

| 伪造手法 | 拦截点 | 结果标签 |
| --- | --- | --- |
| 编一个不存在的 `sourceEventId` | 来源表查不到 `(sourceEventId, claimId)` | `invalid_evidence_source` |
| 指向一个 `success: false` 的 `tool_result` | 来源表只收 `success === true` 的事件 | `invalid_evidence_source` |
| 来源事件存在，但改写 `value` | `value` 不一致 | `invalid_evidence_source` |
| 来源事件存在，值对但改 `contentHash` | `contentHash` 不一致 | `invalid_evidence_source` |
| 证据全对，但最终回答不提它 | `final.citations` 缺少该 claim | `missing_evidence` |

注意第五种故意归到 `missing_evidence` 而不是 `invalid_evidence_source`：证据本身是干净的，问题是**结论与证据脱节**。这个区分让"模型偷懒不写引用"和"模型伪造证据"能被分开统计——前者靠 prompt 工程解决，后者要靠架构上的观测通道隔离。

### 2.4 为什么字符串匹配不够

一个自然的质疑是：既然最终状态对了不算数，那"最终回答里出现期望的关键词"总能算数吧？不能，因为**关键词无法表达因果与作用域**："共 **42** 条"与"**我猜**可能有 42 条左右"含同一数字却语义相反；"已写入 2026-03-02"与"**未能**写入 2026-03-02"含同一日期；多任务场景下另一个任务的正确结果出现在这段文字里，匹配器会误判通过。

结构化证据把这些变成**可判定**的：`claimId` 给出键、`value` 给出值、`sourceEventId` 给出因果来源、`citations` 给出作用域。语义质量留给人工或校准后的 judge——项目刻意不接 LLM-as-a-Judge，就是不把"未经校准的语义判断"混进确定性判定。

## 3. 多标签 `violations` 与 `primaryFailure` 归因

### 3.1 同 code 合并，不同 code 追加

`addViolation` 做两件事：

```ts
const addViolation = (code, message, evidenceIds?) => {
  const existingIndex = violations.findIndex((v) => v.code === code);
  if (existingIndex !== -1) {
    // 同 code：message 去重拼接，evidenceIds 求并集
    violations[existingIndex] = {
      code,
      message: existing.message.includes(message) ? existing.message
                                                  : `${existing.message}；${message}`,
      ...(mergedIds.length === 0 ? {} : { evidenceIds: mergedIds }),
    };
    return;
  }
  violations.push({ code, message, ...(evidenceIds === undefined ? {} : { evidenceIds }) });
};
```

所以 `missing_evidence` 只会在列表里出现一次，哪怕它由两个独立检查触发（缺验证、缺引用）：message 变成 `"缺少已验证证据：query、count；最终回答未引用证据：count"`，而 `evidenceIds` 是 `["query", "count"]`（并集去重）。直接后果是：

> **`violations.length` 是"不同类别数"，不是"违规条目数"。**

### 3.2 汇总计数为什么不能相加

条件汇总里 `failures` 的生成方式是**遍历每条结果的每个 violation**：

```ts
for (const result of results) {
  for (const violation of result.violations) {
    failures[violation.code] = (failures[violation.code] ?? 0) + 1;
  }
}
```

于是各标签计数之和 **≥** 失败运行数。举例：6 条运行、2 条通过，剩下 4 条失败：

| 标签 | 计数 |
| --- | ---: |
| `missing_evidence` | 3 |
| `tool_error` | 2 |
| `goal_not_completed` | 4 |
| **合计** | **9** |

9 显然大于 4。报表里写"共有 9 次失败"是错的；正确的是"4 条失败运行，共产生 9 条违规标签"。要拿失败总数，只能用 `runs - passed`。

### 3.3 `primaryFailure` 的兼容策略

`EvaluationResult` 同时带 `failureType` 与 `primaryFailure`，且始终相等；`failureType` 是 v0.1/v0.2 的兼容别名。这个策略有两个值得学的点：

1. **兼容字段不删，但明确标注废弃。** 类型定义上写了 `/** @deprecated 使用 primaryFailure。保留该字段以兼容 v0.1/v0.2 消费方。 */`。旧消费者继续工作，新消费者看到废弃标记。
2. **导入路径严查两者一致。** `if (failureType !== primaryFailure) fail(...)`。这让"兼容"不至于变成"两个字段可以不一致"的漏洞。

同样的严格性还体现在三个自洽性检查上：

```ts
if (passed && (primaryFailure !== "none" || violations.length > 0)) fail(path, "passed=true 时 primaryFailure 必须为 none 且 violations 必须为空");
if (!passed && primaryFailure === "none") fail(`${path}.primaryFailure`, "passed=false 时不能为 none");
if (!passed && violations[0]?.code !== primaryFailure) fail(`${path}.violations[0].code`, "首个 violation 必须与 primaryFailure 一致");
if (JSON.stringify(reasons) !== JSON.stringify(violationReasons)) fail(`${path}.reasons`, "必须与 violations 的 message 按顺序完全一致");
```

这四条合起来保证：**一份能通过校验的输入文件，其 `passed`、`primaryFailure`、`violations`、`reasons` 四者不可能互相矛盾。** 换句话说，导入路径虽然把判定权交给了外部，但把"自洽性"牢牢攥在手里。

### 3.4 归因表怎么用

| 目标 | 用什么字段 | 注意 |
| --- | --- | --- |
| 失败分布图（饼图/柱图） | `primaryFailure` | 各类别之和 = 失败运行数，可以归一化 |
| 定位改进优先级 | `violations` 全量标签 | 计数之和 > 失败数，不要归一化 |
| 具体证据缺失分析 | `violations[].evidenceIds` | 只有部分标签带该字段 |
| 跨版本趋势 | `primaryFailure` | 顺序稳定，可逐版本对比 |
| 单条失败复盘 | `reasons` | 与 `violations` 的 message 顺序一致 |

## 4. McNemar exact test

### 4.1 2×2 配对表

配对设计下，每个样本（一个 `pairKey`）在 A/B 两个条件下各有一个二值结果，于是有四格：

|  | B 通过 | B 失败 |
| --- | --- | --- |
| **A 通过** | `a` = `unchangedPass` | `c` = `passToFail` |
| **A 失败** | `b` = `failToPass` | `d` = `unchangedFail` |

- A 成功率 = `(a + c) / N`
- B 成功率 = `(a + b) / N`
- 提升 `delta` = `(b − c) / N`

**关键洞察：只有 `b` 和 `c` 携带"哪个更好"的信息。** `a` 和 `d` 是两边一致的部分——它们影响样本量，但不影响方向。如果 A 和 B 在每个任务上都一样，那么无论 N 多大，你都没有任何证据说它们不同。

这就是为什么不能把两个比例各算一个置信区间然后看是否重叠：那个做法丢掉了配对结构，把 `a` 和 `d` 也当成"如果不配对就会有差异"的潜在证据，方向性信息被稀释。

### 4.2 exact p-value 的定义

在"两条件完全相同"的原假设下，每个不一致样本翻转方向的概率是 0.5。所以 `X = b` 服从二项分布 `Binom(n = b + c, p = 0.5)`。双侧 exact p-value 取较小的那一尾、乘以 2：

```text
p = min(1, 2 · Σ_{k=0}^{min(b,c)} C(b+c, k) · 0.5^(b+c))
```

三个边界情形：

| 情形 | 结果 | 原因 |
| --- | --- | --- |
| `b + c = 0` | `p = 1` | 完全没有不一致样本，没有任何方向性证据 |
| `b = c` | `p = 1` | 两侧翻转数量相等，方向完全抵消 |
| `b = 0, c = 1` | `p = 1` | 单侧 1 个不一致：任一方向都同样可能，最小可能的两侧 p 就是 1 |

最后一行值得注意：**只有 1 个不一致样本时，无论方向如何都不可能显著。** 这也解释了为什么仓库的 3 条合成任务演示给出 `McNemar exact p: 0.5000`——`fail→pass = 2`、`pass→fail = 0`，不一致样本总共只有 2 个。

### 4.3 代码实现

```python
"""McNemar exact test：小样本走精确组合数，大样本切对数空间防溢出。"""
from __future__ import annotations

import math


def mcnemar_exact_p(fail_to_pass: int, pass_to_fail: int) -> float:
    """双侧 exact p-value：2 * P(X <= min(b, c)), X ~ Binomial(b + c, 0.5)。"""
    if not isinstance(fail_to_pass, int) or not isinstance(pass_to_fail, int):
        raise TypeError("McNemar 计数必须是整数")
    if fail_to_pass < 0 or pass_to_fail < 0:
        raise ValueError("McNemar 计数必须非负")

    discordant, lower = fail_to_pass + pass_to_fail, min(fail_to_pass, pass_to_fail)
    if discordant == 0:
        return 1.0
    if discordant <= 1024:
        # Python 整数是任意精度，组合数不溢出；但 2**n 转 float 在 n≈1024 以上溢出
        tail = sum(math.comb(discordant, k) for k in range(lower + 1)) / float(2 ** discordant)
        return min(1.0, 2.0 * tail)

    # 大样本路径：算最大项的对数，再按相邻项比值累加
    log_largest = (math.lgamma(discordant + 1) - math.lgamma(lower + 1)
                   - math.lgamma(discordant - lower + 1) - discordant * math.log(2.0))
    scaled = ratio = 1.0
    for k in range(lower, 0, -1):
        ratio *= k / (discordant - k + 1)     # term(k-1) / term(k)
        scaled += ratio
        if ratio == 0.0:                      # 相对项已下溢，后续可忽略
            break
    return min(1.0, 2.0 * math.exp(log_largest) * scaled)
```

两条路径必须一致。用 `n=19, lower=5` 交叉验证：

```text
mcnemar_exact_p(14, 5)                              = 0.063568
大样本对数空间路径(n=19, lower=5)                     = 0.063568   ← 逐位一致
```

### 4.4 一张 p-value 速查表

| `(b, c)` | 不一致对 | exact p | α=0.05 下 |
| --- | ---: | ---: | --- |
| `(2, 0)` | 2 | 0.500 | 不显著 |
| `(5, 5)` | 10 | 1.000 | 不显著（方向抵消） |
| `(9, 0)` | 9 | 0.004 | **显著**（极端失衡） |
| `(10, 3)` | 13 | 0.092 | 不显著 |
| `(14, 5)` | 19 | 0.064 | 不显著 |
| `(16, 5)` | 21 | 0.027 | **显著** |
| `(30, 15)` | 45 | 0.036 | **显著** |
| `(108, 80)` | 188 | 0.049 | **显著**（勉强） |

两条反直觉的读法：

1. **`(9, 0)` 比 `(30, 15)` 更显著。** 前者的不一致对只有 9，后者有 45，但前者是"9 次全部朝改进方向翻"，后者是"45 次里 30 对 15"。**证据强度取决于不一致样本的失衡程度，而不只是数量。**
2. **`(14, 5)` 到 `(16, 5)` 只多了 2 个净翻转，p 从 0.064 掉到 0.027。** 在临界点附近，`p` 对样本数极其敏感。所以"p = 0.048，显著！"这种结论必须配合效应量和置信区间一起看，不能只看星号。

### 4.5 显著性需要多少不一致样本

把 `delta` 固定在 `+9pp`（即 `b − c = 0.09 N`），看不同规模下需要多少不一致对：

| N（配对数） | b | c | 不一致对 | exact p | 结论 |
| ---: | ---: | ---: | ---: | ---: | --- |
| 100 | 14 | 5 | 19 | 0.064 | 不显著 |
| 150 | 21 | 7 | 28 | 0.013 | 显著 |
| 200 | 28 | 10 | 38 | 0.005 | 显著 |
| 300 | 42 | 15 | 57 | 0.0005 | 显著 |

但如果**不一致率更低**（大多数任务根本没变化，`c:b ≈ 2:11`，约 13% 不一致）：

| N | b | c | 不一致对 | exact p | 结论 |
| ---: | ---: | ---: | ---: | ---: | --- |
| 100 | 11 | 2 | 13 | 0.022 | **显著** |
| 150 | 17 | 3 | 20 | 0.0026 | 显著 |

两表对照得出的结论非常重要：**McNemar 的检验力取决于不一致对的数量，而不是总配对数。** 100 对数据里只有 13 个不一致对（11:2）就已经显著，而 19 个不一致对（14:5）反而不显著。原因是后面这一组把同样的净提升分散到了更多"双向翻动"里——而双向翻动正是噪声的形状。

工程推论：**想让评测更快给出结论，应该让改动"要么不动、要么一次翻过去"，而不是在所有任务上都产生微小的概率波动。** 这既指导实验设计，也解释了为什么"改一点 prompt 让所有任务都好一点点"通常最难验证。

## 5. 聚类 Bootstrap CI：重采样单位必须是 `taskId`

### 5.1 为什么 i.i.d. Bootstrap 在这里是错的

Bootstrap 的合法性建立在"样本可交换"（exchangeable）的假设上。假设每个观测都是从同一个总体独立抽取的，那么有放回地重采样观测就能模拟"重新做一次实验"。

但在 Agent 评测里，**同一个任务的多次 `repeat`/`seed` 根本不独立**：它们共享同一套页面结构、同一条目标描述、同一种失败模式。一个难任务很可能 5 次重复全失败，一个易任务很可能 5 次全成功——簇内相关性接近 1。

i.i.d. Bootstrap 把"50 个任务 × 2 次重复"当成 100 个独立样本，于是：

```text
有效样本量被虚增约 2 倍
标准误被低估约 √2 倍
置信区间宽度被低估约 30%
```

后果是**假阳性**：一个不显著的提升会被包装成显著的。

### 5.2 算法

```text
1. 按 taskId 把配对折叠成「任务簇」
   每个簇记录：baselinePassed、optimizedPassed、runs（该任务参与了多少对）
2. 重复 iterations 次：
   a. 有放回地抽取 len(taskIds) 个任务（可以重复抽到同一个任务）
   b. 把抽中任务的簇内计数全部累加（整簇进出，不拆分）
   c. 在本次重采样内先池化再作差：optimizedPassed/runs - baselinePassed/runs
3. 对 iterations 个差值排序，取 [α/2, 1-α/2] 分位点
4. 点估计用原始（不重采样）数据算，保证与报告里的 delta 一致
```

第 2c 步是最容易写错的地方：

| 写法 | 含义 | 问题 |
| --- | --- | --- |
| **先池化再作差**（正确） | 重采样内把所有配对合在一起算比率 | 与报告里的池化成功率口径一致 |
| 先算每任务比率再平均 | 每个任务等权 | 各任务重复次数不一致时结果不同，且丢掉了"重复次数"这一信息 |

第 2a 步的"抽够 `len(taskIds)` 个"也是刻意的：重采样样本的规模应与原样本相同，否则方差会被系统性低估或高估。

### 5.3 代码实现

```python
"""以 taskId 为聚类单位的百分位 Bootstrap，以及用于对照的 i.i.d. 版本。"""
from __future__ import annotations

import random
from dataclasses import dataclass
from typing import Sequence


@dataclass(frozen=True)
class Pair:
    task_id: str
    repeat_id: str
    seed: int
    baseline_passed: bool
    optimized_passed: bool

    @property
    def pair_key(self) -> str:
        return f"{self.task_id}::{self.repeat_id}::{self.seed}"


def percentile(sorted_values: Sequence[float], probability: float) -> float:
    """与 agent-eval-lab 一致的百分位口径：floor(p * n)，夹在 [0, n-1]。"""
    return sorted_values[min(len(sorted_values) - 1, max(0, int(probability * len(sorted_values))))]


def bootstrap_delta(pairs: Sequence[Pair], cluster_by_task: bool = True,
                    iterations: int = 2000, confidence_level: float = 0.95,
                    seed: int = 20260819) -> dict[str, float]:
    """cluster_by_task=True 是正确做法；False 是错误做法（i.i.d.，仅作对照）。

    正确做法三步：①按 taskId 折叠成任务簇，簇内保留全部计数；
    ②有放回抽「任务」（抽够原任务数），整簇进出；③每次重采样内先池化再作差。
    """
    if iterations < 100:
        raise ValueError("iterations 必须 >= 100")
    if not 0.0 < confidence_level < 1.0:
        raise ValueError("confidence_level 必须落在 (0, 1)")

    units: dict[str, list[int]] = {}                   # [baseline 通过数, optimized 通过数, 配对数]
    for pair in pairs:
        key = pair.task_id if cluster_by_task else pair.pair_key
        unit = units.setdefault(key, [0, 0, 0])
        unit[0] += int(pair.baseline_passed)
        unit[1] += int(pair.optimized_passed)
        unit[2] += 1
    keys = sorted(units)
    rng = random.Random(seed)

    deltas: list[float] = []
    for _ in range(iterations):
        baseline_pass = optimized_pass = drawn = 0
        for _ in range(len(keys)):                     # 重采样样本量 = 原单元数
            unit = units[keys[rng.randrange(len(keys))]]
            baseline_pass += unit[0]                    # 整簇进出，不拆分
            optimized_pass += unit[1]
            drawn += unit[2]
        deltas.append(optimized_pass / drawn - baseline_pass / drawn)   # 先池化再作差
    deltas.sort()

    alpha = (1.0 - confidence_level) / 2.0
    passed_baseline = sum(1 for pair in pairs if pair.baseline_passed)
    passed_optimized = sum(1 for pair in pairs if pair.optimized_passed)
    return {"estimate": passed_optimized / len(pairs) - passed_baseline / len(pairs),
            "lower": percentile(deltas, alpha), "upper": percentile(deltas, 1.0 - alpha),
            "unit": "task" if cluster_by_task else "pair", "clusters": len(keys)}
```

### 5.4 两种场景、三个结论

构造同一批 100 个配对（50 个任务 × 2 次重复），四格固定为 `a=57, b=14, c=5, d=24`，于是 `baseline = 62%`、`optimized = 71%`、`delta = +9pp`。区别只在于**这 100 个格子怎么分给 50 个任务**：

**场景 1：改进集中在少数任务上（真实 Agent 评测的典型形状）**

```text
28 个任务两条件全过（56 个 unchangedPass）
 1 个任务 r1 通过、r2 两条件全败
 7 个任务两次重复都 fail→pass（14 个 failToPass）
 5 个任务 r1 pass→fail、r2 两条件全败（5 个 passToFail）
 9 个任务两条件全败（18 个 unchangedFail）
```

**场景 2：同样的格子打散到所有任务**

用固定 seed 把 100 个格子随机洗牌后依次分配给任务，破坏簇内相关。

运行结果：

| 场景 | 点估计 | McNemar p | 聚类 CI（单位=task） | i.i.d. CI（单位=pair） | 聚类 CI 是否含 0 |
| --- | ---: | ---: | --- | --- | :-: |
| 场景 1（改进集中） | +9.00% | 0.0636 | `[-0.020, +0.200]`，宽 0.220 | `[+0.010, +0.170]`，宽 0.160 | **含 0** |
| 场景 2（打散） | +9.00% | 0.0636 | `[+0.010, +0.170]`，宽 0.160 | `[+0.010, +0.180]`，宽 0.170 | 不含 0 |

同样的点估计、同样的 p 值，三种不同的解读：

1. **场景 1 是正确的做法**：聚类 CI `[-0.020, +0.200]` 包含 0，同时 McNemar `p = 0.0636 > 0.05`——两个检验**一致地说"证据不足以宣布提升"**。区间宽达 22 个百分点，说明这个实验的规模根本撑不起上线决策。
2. **场景 1 若错用 i.i.d. Bootstrap**：CI 变成 `[+0.010, +0.170]`，**排除 0**，会得出"显著提升"的错误结论。这就是重采样单位选错的代价。
3. **场景 2 里两者接近**：因为簇内相关性被破坏，i.i.d. 假设近似成立，两个 CI 自然收敛。**这恰恰验证了聚类 Bootstrap 的实现是对的——它在不需要聚类时不会强行把区间撑大。**

### 5.5 解读示例：A 版本 62%、B 版本 71%，提升显著吗？

答案分三层：

**第一层：统计上不显著。** `b=14, c=5`，McNemar exact `p = 0.0636`，在 α=0.05 下不显著。聚类 95% CI 为 `[-0.020, +0.200]`，包含 0。两个检验一致：现有证据不足以排除"这 9 个点是噪声"。

**第二层：即使显著，也要看效应量的区间。** 假设把样本扩到 150 对（`b=21, c=7`），`p = 0.0125` 显著了。但此时 CI 仍然宽——因为聚类单位只有 50 个任务时，任何区间都不会窄。**报告应该写"成功率 71%（95% CI [66%, 76%]，n=150 对，k=50 个任务簇）"，而不是只写"提升 9 点，p<0.05"。**

**第三层：工程上不要拿这个数字做决策。** 具体要做的三件事：

| 动作 | 理由 |
| --- | --- |
| 增加任务数，而不是只增加重复次数 | 聚类 CI 的宽度由**任务簇数**决定；把一个任务跑 10 遍几乎不会让区间变窄，换成 10 个新任务才会 |
| 检查 `pass→fail` 的 5 条 | 任何"双向翻动"都是噪声的形状；如果这 5 条集中在同一类任务上，说明改动引入了新的失败模式，而不是提升了平均能力 |
| 降低不一致率 | 若能把 `c:b` 从 5:14 收到 2:11（不一致率从 19% 降到 13%），100 对就能给出 `p = 0.022`——**同样的提升，更少的噪声，更强的证据** |

## 6. 面试问答与自测题

### 6.1 面试问答

<details>
<summary><strong>Q1：为什么一次失败要保留多个 `violations`，而 `primaryFailure` 又只能有一个？如何保证它稳定？</strong></summary>

因为数组和单值服务两类完全不同的消费者。`violations` 服务"分析与改进"：一次运行可能同时"缺少证据"和"工具失败后未恢复"，这两条指向的修复动作完全不同（一个是补数据链路，一个是加错误恢复），压成一个标签就等于丢掉一条线索。`primaryFailure` 服务"聚合与呈现"：失败分布图、跨版本趋势、周报都需要一个单值、稳定、可预期的归因。

稳定性靠**把顺序写死在代码里**，而不是靠动态排序。"最严重"这类主观排序会随上下文变化（"被登录墙挡住"对浏览器 Agent 是正常终止，对运维 Agent 是严重故障），一旦主归因依赖主观权重，同一现象在两次评测里可能落到不同标签，成功率变化的原因就追不回来了。项目的顺序是从"根本没有可判定的东西"（`missing_trajectory`）到"产生了但没做完"（`empty_final_answer`）到"状态性问题"（`goal_not_completed`），并且 `primaryFailure` 严格等于 `violations[0].code`。另外同 code 会被合并（message 拼接、`evidenceIds` 求并集），所以 `violations.length` 是"不同类别数"而不是"违规条目数"。

</details>

<details>
<summary><strong>Q2：为什么两类结果都不能直接用"两个比例的差"来判断，而必须用 McNemar？</strong></summary>

因为实验是**配对设计**：同一个任务在 A 和 B 两个条件下各跑一次，样本天然一一对应。当成两组独立样本去检验两个比例的差，会丢掉两件事：①这对样本共享同一任务的所有特征，差异**只**来自条件差异，方差应按配对方式算（更小）；②方向性信息被稀释——`a`（两边都过）和 `d`（两边都败）在独立样本视角下会被当成"可能本来有差异"的证据，而它们对"A 与 B 是否不同"没有提供任何方向信息。

McNemar 只统计不一致格 `b = fail→pass`、`c = pass→fail`。原假设下每次翻转方向等概率，所以 `b ~ Binom(b+c, 0.5)`，exact p 就是 `min(1, 2·P(X ≤ min(b,c)))`。这既正确利用了配对结构（`a`、`d` 只影响样本量，不影响方向），又对 `b = c` 正确给出 `p = 1`（方向抵消）。工程上还有一层好处：`b` 和 `c` 本身就是最好的诊断指标——`pass→fail` 的数量直接告诉你改动引入了多少新失败。

</details>

<details>
<summary><strong>Q3：为什么 Bootstrap 必须以 `taskId` 为聚类单位？举一个会得出相反结论的具体例子。</strong></summary>

因为 Bootstrap 的合法性建立在样本可交换性上，而同一任务的多轮 `repeat`/`seed` **不独立**：它们共享页面结构、目标描述和失败模式，簇内相关性接近 1。i.i.d. Bootstrap 把"50 个任务 × 2 次重复"当作 100 个独立观测，有效样本量虚增约 2 倍、标准误低估约 √2 倍、区间宽度低估约 30%，后果是假阳性。

具体例子：100 个配对（50 任务 × 2 重复），四格 `a=57, b=14, c=5, d=24`，即 `62% → 71%`、`+9pp`。若改进集中在 7 个任务上（每个任务两次重复都 `fail→pass`，正是簇内相关的形状），聚类 Bootstrap 的 95% CI 是 `[-0.020, +0.200]`（含 0，不显著，与 `p = 0.0636` 一致）；而错用 i.i.d. Bootstrap 得到 `[+0.010, +0.170]`（不含 0，会宣布显著）。**同样的数据、同样的点估计，因为重采样单位选错，得出相反的上线结论。**

正确做法三步：①按 `taskId` 折叠成任务簇，簇内保留全部计数；②有放回抽取**任务**（抽够原任务数），整簇进出；③每次重采样内**先池化计数再作差**（而不是先算每任务比率再平均）。一个验证技巧：把同样的格子随机打散到各任务后再跑聚类 Bootstrap，区间会收敛到与 i.i.d. 接近——说明实现没有在不需要聚类时强行撑大区间。

</details>

### 6.2 自测题

<details>
<summary>参考答案</summary>

**1. 一条轨迹有 `status = "completed"`、`final.text = "任务完成"`、一条 `tool_result(success=false)`、`requiredEvidence = ["price"]` 且该 claim 从未出现。它会命中哪些标签，主归因是什么？**

只命中 `missing_evidence`：`price` 不在已验证证据集里，也不在 `final.citations` 里（两个检查合并成一条）。其余标签都不触发——`tool_error` 要求 `status === "failed"`（这里是 `completed`）；有 `tool_call` 就不是 `zero_step_termination`；`goal_not_completed` 只看 `status === "failed"`；`final.text` 非空所以不是 `empty_final_answer`。

所以 `violations = [missing_evidence]`、`primaryFailure = missing_evidence`、`passed = false`。

**关键教学点是 `status` 与 `passed` 是两条独立的轴**：运行器说"完成"，评测器说"失败"。也正因如此，`tool_error` 在这条轨迹上不会被触发——单看 `success=false` 一个事件就报 `tool_error` 是错的，必须结合整体状态；这个 `且` 条件避免了把"失败了但恢复了"的轨迹误判。

</details>

<details>
<summary>参考答案</summary>

**2. 计算 `(b, c) = (8, 1)` 与 `(b, c) = (20, 10)` 的 McNemar exact p，并解释为什么第一个更显著。**

`(8, 1)`：`n = 9`，`min(b,c) = 1`，`p = 2 · [C(9,0) + C(9,1)] / 2^9 = 20 / 512 = 0.0391` → 显著。
`(20, 10)`：`n = 30`，`min = 10`，`p = 2 · Σ_{k=0}^{10} C(30,k) / 2^30 ≈ 2 × 0.04937 ≈ 0.0987` → 不显著。

第一个更显著，因为**证据强度取决于不一致样本的失衡程度，而不只是数量**。`(8,1)` 是"9 次翻动里 8 次朝同一方向"，高度失衡在原假设（每次翻动方向等概率）下很罕见；`(20,10)` 虽然有 3 倍数据量，但方向和噪声几乎五五开，`20:10` 在 30 次伯努利(0.5) 试验里完全正常。一句话：**McNemar 检验的是"方向是否失衡"，不是"样本是否够多"。** 顺带一个边界：`b = c` 时 `p` 恒为 1，无论 `b` 多大。

</details>

<details>
<summary>参考答案</summary>

**3. 一个团队报告"成功率从 62% 提升到 71%，n=100 对，p<0.05"，你要追问什么？**

四步。①**这 100 对怎么构成？** 100 个任务各跑 1 次，还是 20 个任务各跑 5 次？后者的有效样本量只有 20 个任务簇，而 **Bootstrap CI 的宽度由任务簇数决定，不由配对数决定**——必须追问"聚类 CI 是多少"。②**`b` 和 `c` 各是多少？** 因为 `(b − c)/100 = 0.09`，可能是 `(14, 5)`（`p = 0.064`，其实不显著）、`(12, 3)`（`p = 0.035`）、`(11, 2)`（`p = 0.022`）——**同一点估计对应的 p 可以差三倍**，所以必须看 2×2 表的原始四格。同时 `c = 5` 意味着 5 个原本通过的任务现在失败了，这在生产上是回归。③**是同一个 Manifest 下跑的吗？** 模型 revision、`promptHash`、`codeCommit`、`dataset.hash` 在 A/B 之间是否只有目标变量变了？④**效应量区间与业务门槛。** 若 CI 是 `[+1%, +17%]`，即使显著，下界也只有 1 个百分点——**平均提升 9 点但某一类任务全线退化**，比平均值重要得多。

</details>

<details>
<summary>参考答案</summary>

**4. 为什么"任务级聚类 CI 更宽"应该被接受，而不是想办法把区间压窄？**

因为更宽才是真话。i.i.d. 假设在这个数据生成过程下是**错的**：同一任务的重复确实相关。用错误假设算出更窄的区间不是"更精确"，而是"把偏差包装成精度"——等于给决策者虚假的确定感。

更重要的是，**宽区间本身提供行动信息**：`[-0.020, +0.200]` 宽 22 个百分点，直接告诉你"这个实验的规模撑不起这个决策"，并指出该往哪补——**增加任务簇数**，而不是增加每任务的重复次数。正确的做法不是"把区间弄窄"，而是**在设计阶段就把区间算出来**：先用一小批任务估簇内相关性与不一致率，再反推需要多少任务簇才能让宽度小于业务门槛（比如 CI 宽度 < 10 个百分点）。这就是 power analysis 在 Agent 评测里的对应物。

</details>
