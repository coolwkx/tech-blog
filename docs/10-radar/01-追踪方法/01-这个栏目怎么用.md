# 这个栏目怎么用

> 栏目本身是一套**流程**，不是一堆笔记。本文规定：收什么、多久看一次、凭什么判断值不值得记、什么时候把条目退役。

本栏目追踪 AI / Agent 领域的新技术（例如 Jev、Muse）。每出现一个新技术就写一篇条目笔记，因此流程必须满足两个约束：**单篇成本低**（否则追不动）、**结论可复核**（否则三个月后没人敢信）。

---

## 1. 这个栏目解决什么问题

追踪新技术常见的三种失败方式，以及本栏目的对应设计：

| 失败方式 | 表现 | 本栏目的对策 |
| --- | --- | --- |
| 追不动 | 热点太密，写了两篇就放弃 | 条目固定七节结构，一小时内可成稿；不值得写的线索降级为速记 |
| 写不准 | 把媒体转述当事实，三个月后发现全错 | 强制区分一手 / 二手信源，查不到的一律标「待验证」 |
| 用不上 | 笔记写完就躺在文件夹里 | 每篇必须写「对我们的影响」，并规定沉淀路径（见栏目首页第四节） |

栏目**不**负责：新闻搬运、产品评测、投资判断、模型排行榜。这三类内容如果要做，另开文档。

## 2. 收录标准

### 2.1 硬门槛（四问全过）

| # | 问题 | 判定要点 |
| --- | --- | --- |
| Q1 | 是否改变了能力边界？ | 追问「以前做不到的是什么」。凡回答只能是「更准了 / 更快了」的，看幅度是否达到一个数量级 |
| Q2 | 是否有可验证的机制？ | 至少命中一项：官方文档、论文、开源仓库、可复现的第三方评测 |
| Q3 | 是否能落到我们的 Agent 工程里？ | 必须能映射到 评测 / RAG / 工具调用 / 记忆 / 权限 之一 |
| Q4 | 是否与已有条目形成差异？ | 与索引表逐条比对机制与能力档位，重复则改为更新已有条目 |

### 2.2 判定记录表（每次判断留痕）

对每条候选线索填一行，避免「当时为什么记了它」半年后无人能答：

| 字段 | 说明 | 示例（Jev） |
| --- | --- | --- |
| 线索来源 | 首次看到它的地方 | 科技日报 2026-09-20 报道 |
| Q1 结论 | 通过 / 不通过 + 一句话 | 通过：决策从自回归生成中拆出，延迟降一个量级 |
| Q2 结论 | 通过 / 不通过 + 一手材料清单 | 通过：官方博客 + 文档 + 第三方适配器仓库 + 独立测试 |
| Q3 结论 | 通过 / 不通过 + 映射到的能力 | 通过：映射到工具调用（路由）与评测（置信度校准） |
| Q4 结论 | 新增 / 更新哪条 | 新增 |
| 处置 | 写条目 / 写速记 / 丢弃 | 写条目 |
| 判断人 + 日期 | — | 2026-09-20 |

### 2.3 信息源分级

同一事实在不同来源里权重不同，写作时按下表标注：

| 级别 | 定义 | 举例 | 在条目中的用法 |
| --- | --- | --- | --- |
| A 一手 | 官方博客 / 官方文档 / 论文 / 开源仓库 / 官方定价页 | TypeSafe 官方博客与文档、Meta 安全架构说明、Meta 开发者文档 | 可直接作为事实陈述 |
| B 独立 | 与发布方无关的第三方复现、独立评测、有原始数据的调研机构 | APUS 的独立开源复现、第三方开发者的对比测试、Apptopia 的下载估算 | 可作为事实陈述，但须写明「独立方 + 口径」 |
| C 转述 | 媒体报道、二手总结、社区讨论 | 各类新闻稿与解读文章 | 只能作为线索，用于**定位** A/B 级材料 |
| D 传闻 | 匿名消息、截图、无出处说法 | 「据说」「内部人士」 | 一律不写进正文，必要时写进「待验证问题」 |

**铁律**：条目正文中每一个数字都必须能指回 A 或 B 级来源；C 级来源只在「延伸阅读」和「待验证问题」中出现。

## 3. 一条线索的完整生命周期

这张图回答：一条线索从被看见到被淘汰，要依次做哪些动作，每个动作留下的产物是什么。

```mermaid
flowchart LR
    S1["① 发现<br/>速记箱：一行线索 + 来源 + 日期"] --> S2["② 去重<br/>比对索引表<br/>命中则改为更新已有条目"]
    S2 --> S3["③ 查证<br/>找 A / B 级来源<br/>查不到就标「待验证」"]
    S3 --> S4["④ 定级<br/>五维打分"]
    S4 --> S5["⑤ 成稿<br/>按模板七节写完，行数 250–450"]
    S5 --> S6["⑥ 复核<br/>每季度一次，事实变化就地更新"]
    S6 --> S7["⑦ 退役<br/>证伪 / 被取代 → 移入退役清单"]
```

**读图要点**：

| 观察 | 含义 |
| --- | --- |
| 七个阶段是严格串行的 | 每一步的产物就是下一步的输入，跳步会直接导致条目无法复核 |
| ② 去重决定了后面是「新增」还是「更新」 | 同一个事实在索引表里只允许有一个落点，否则数字会分散在两条记录里 |
| ③ 查证是唯一的可能中止点 | 查不到 A / B 级来源不会让流程停下，但条目会被标为「待验证」，等级被限制 |
| ⑥ 复核是一条长周期回边 | 它不是流程的终点，而是让已发布的条目随事实变化就地处更新 |
| ⑦ 退役保留条目而不删除 | 退役清单让「这个说法后来被证伪」本身变成可查询的记录 |

| 阶段 | 产出 | 时间盒 | 完成标志 |
| --- | --- | --- | --- |
| ① 发现 | 速记一行 | 1 分钟 | 有来源链接和日期 |
| ② 去重 | 是 / 否 | 2 分钟 | 明确「新增」或「更新 XX 条目」 |
| ③ 查证 | 来源清单 | 20–40 分钟 | 至少 2 个 A 级或 1 个 A + 1 个 B 级来源 |
| ④ 定级 | 五维分数 + 综合等级 | 5 分钟 | 能回答「值不值得现在投入」 |
| ⑤ 成稿 | 条目文件 | 40–60 分钟 | 七节齐全，无占位符 |
| ⑥ 复核 | 更新记录 | 每季度 10 分钟 | 关键数字仍成立，或已修正 |
| ⑦ 退役 | 退役说明 | 触发时 10 分钟 | 索引表状态改为「已退役」 |

## 4. 更新节奏

| 周期 | 动作 | 时间盒 | 产出 |
| --- | --- | --- | --- |
| 每日 | 扫线索：模型发布、Agent 产品、协议与标准、安全事件 | 10 分钟 | 速记箱新增 0–3 行 |
| 每周 | 速记箱过一遍四问；过门槛的排期成稿 | 30 分钟 | 0–1 篇新条目，或 0 篇 + 若干丢弃 |
| 每月 | 对照索引表补一次「对我们的影响」是否已落地 | 30 分钟 | 项目侧行动项 |
| 每季度 | 全量复核：逐条检查关键事实、定价、可用地区、是否已被超越 | 1–2 小时 | 更新记录 + 退役清单 |

节奏原则：

1. **宁可少写，不可写虚。** 一周没有值得写的线索是正常结果，不是失败。
2. **热点不等于条目。** 热度只影响「先看哪个」，不影响「值不值得写」。
3. **更新优于新增。** 同一技术的进展优先并入原条目，「更新记录」越长说明条目越有价值。

## 5. 怎么判断「值不值得记」

### 5.1 快速否决清单（命中任一条即不写条目）

| 情形 | 为什么不写 |
| --- | --- |
| 只有官方宣传，没有任何可验证材料 | Q2 不通过，写出来就是复述公关稿 |
| 能力与已有条目重合度 > 70% | Q4 不通过，应并入已有条目 |
| 变化只在 UI、定价、地区开放 | Q1 不通过，是运营事件而非技术事件 |
| 与 Agent 工程完全无关 | Q3 不通过 |
| 需要付费墙后才能验证核心机制，且无替代来源 | 无法查证，先放速记箱 |

### 5.2 「值不值得」的量化口径

三条门槛，**全部满足**才成稿：

| 门槛 | 口径 | 例：Jev | 例：Muse |
| --- | --- | --- | --- |
| 新意门槛 | 与已有条目机制不同的判别点 ≥ 2 个 | 不生成文本、并行单次判定 | 每用户独立执行环境、外置审批 Agent |
| 证据门槛 | A 级来源 ≥ 1 且 A+B ≥ 2 | 官方博客 + 独立复现 + 第三方测试 | 官方安全说明 + 下载数据调研机构 + 平台封禁事件 |
| 落地门槛 | 能写出 ≥ 2 条可执行的项目动作 | 路由层可用置信度阈值；评测需加校准指标 | 权限分层设计；执行环境隔离；敏感操作二次确认 |

### 5.3 灰区处理

处在「有点像但不完全像」的灰区时，用下面这张表决定：

| 灰区情形 | 处置 | 理由 |
| --- | --- | --- |
| 能力真实但成本极高，暂时用不起 | 写成条目，等级降一档 | 成本会随时间下降，机制结论仍有长期价值 |
| 机制清晰但只在单一封闭平台可用 | 写成条目，「对我们的影响」注明不可直接迁移 | 机制可作为设计参考，不必等它开源 |
| 只有复现项目、原始技术未公开 | 写成条目，状态「部分待验证」 | 复现本身是独立证据，但要写明它验证的是接口行为而非原始实现 |
| 一次性的安全事件、无机制披露 | 写成速记 + 并入相关条目的「更新记录」 | 事件价值在于修正已有判断，不足以独立成篇 |

## 6. 如何退役过时条目

条目退役不是删除。**文件保留**，只在索引表改状态并在文末追加退役说明，理由是：错误结论本身是资产，它能告诉我们当初哪个判断环节不可靠。

### 6.1 触发退役的四种情形

| 情形 | 判定依据 | 处置 |
| --- | --- | --- |
| 事实被证伪 | A 级来源推翻条目中的关键陈述 | 正文标注被推翻的段落，追加退役说明 |
| 技术被取代 | 出现同类条目且新条目在五维中至少三维更优 | 保留原条目，索引表标注「被 XXX 取代」 |
| 长期无进展 | 连续 4 个季度无官方更新、无生态讨论 | 状态改「已退役（停滞）」 |
| 已内化为方法论 | 结论已写入对应技术区块或项目选型 | 状态改「已退役（已沉淀）」，并给出沉淀位置链接 |

### 6.2 退役说明的固定格式

追加在条目末尾，位于返回链接之前：

```text
## 退役说明

- 退役日期：YYYY-MM-DD
- 退役原因：事实被证伪 / 被取代 / 长期停滞 / 已沉淀
- 关键变化：一句话说清哪条结论不再成立
- 仍然成立的部分：列出经得起复核的结论，避免整篇作废
- 沉淀位置：链接到承接该结论的文档
```

### 6.3 退役后索引表的写法

| 状态 | 索引表写法 |
| --- | --- |
| 事实被证伪 | `已退役`，一句话结论改为「原结论：……；已证伪，见文末说明」 |
| 被取代 | `已退役`，一句话结论改为「已被 XXX 取代」，并附上取代者的条目链接 |
| 长期停滞 | `已退役`，一句话结论保留，状态注明停滞起始时间 |
| 已沉淀 | `已退役`，一句话结论后附「已沉淀至某篇文档」，并附该文档链接 |

## 7. 栏目自身的复盘指标

每季度回答一次，用来判断流程是否需要调整：

| 指标 | 合格线 | 不合格时的调整 |
| --- | --- | --- |
| 条目成稿率 | 速记中 ≥ 20% 最终成为条目 | 门槛过高，放宽 Q1 的量化要求；或线索质量太差，调整信息源 |
| 条目复核通过率 | ≥ 80% 的文字无需修正 | 查证阶段时间盒不足，把 20 分钟提到 40 分钟 |
| 「对我们的影响」落地率 | ≥ 50% 的条目产生过项目动作 | 条目写法问题，改模板里的该节引导 |
| 退役条目占比 | ≤ 20% | 收录门槛过松，收紧 Q2 与 Q4 |
| 单篇耗时 | ≤ 90 分钟 | 结构过重，砍掉不产生判断的章节 |

## 8. 一页速查

| 问题 | 答案 |
| --- | --- |
| 什么值得收录？ | 四问全过 + 三条门槛全满足 |
| 多久看一次？ | 每日 10 分钟扫，每周 30 分钟判断，每季 1–2 小时复核 |
| 查不到怎么办？ | 写「**待验证**：……」，并说明为什么存疑 |
| 同一技术又更新了？ | 并入原条目的「更新记录」，不新开文件 |
| 什么时候退役？ | 被证伪 / 被取代 / 停滞 4 个季度 / 已沉淀 |
| 退役要删文件吗？ | 不删。改状态 + 追加退役说明 + 保留仍然成立的部分 |
