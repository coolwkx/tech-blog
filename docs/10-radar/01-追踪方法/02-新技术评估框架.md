# 02 · 新技术评估框架

> 把「感觉很厉害」拆成五个可以打分的维度，输出一个能拿来排期的等级。

评估框架解决一个问题：**面对一堆候选技术，先投入哪一个。** 它不预测技术成败，只回答「此刻它对我们有多少可用的价值」。

---

## 1. 五个维度与权重

| # | 维度 | 它回答的问题 | 权重 | 打分依据的主来源 |
| --- | --- | --- | --- | --- |
| D1 | 技术机制 | 它的核心思路是什么，是新增量还是旧方法换包装 | 25% | 论文、官方文档、开源实现 |
| D2 | 能力变化 | 相比现有方案，能力 / 成本 / 延迟变化多大 | 25% | 独立评测、可复算的官方数据 |
| D3 | 成熟度 | 现在能不能用，会不会明天就变 | 20% | 发布阶段、版本节奏、生态活跃度 |
| D4 | 工程可用性 | 接进我们的系统要花多少代价 | 20% | 依赖、部署形态、文档、生态成熟度 |
| D5 | 对我们的影响 | 与本项目的 评测 / RAG / 工具调用 / 记忆 / 权限 的关联强度 | 10% | 项目侧现状对比 |

权重是**默认值，可按当期目标整体平移**，但每次平移必须在评估表里写明理由。D5 权重最低不是因为它不重要，而是因为它最容易高估——「跟我们有关系」往往只是「听起来有关系」。

---

## 2. 打分刻度（统一五档）

所有维度使用同一套 1–5 刻度，避免「这个 8 分那个 3 分」的不可比：

| 分 | 含义 | 判定口径 |
| --- | --- | --- |
| 5 | 显著领先 | 改变能力边界或成本量级；有独立证据；当前即可用 |
| 4 | 明显更好 | 机制或指标有清晰优势，但存在明确限制 |
| 3 | 有价值 | 有可取之处，但优势不压倒现有方案 |
| 2 | 有限 | 只在特定窄场景有用，或证据薄弱 |
| 1 | 暂不可用 | 机制不明、无证据、或工程代价过高 |

---

## 3. D1 技术机制（25%）

### 3.1 看什么

| 检查项 | 高分特征 | 低分特征 |
| --- | --- | --- |
| 是否新增量 | 提出了新的计算范式 / 新的分层 | 把已有组件重新组合并改名 |
| 是否可解释 | 能画出数据流，说清每一步在做什么 | 只能说「用了强化学习」「用了大模型」 |
| 与现有方法的差异 | 差异点在原理层（例如解码方式、训练目标） | 差异只在调参、提示词、工程包装 |
| 边界条件 | 官方主动说明不适用的场景 | 通篇只讲优点 |

### 3.2 打分锚点

| 分 | 描述 |
| --- | --- |
| 5 | 新增一个可复用的层或范式，并能说清它替换掉了原来的哪一步 |
| 4 | 在原范式内提出关键改动，效果与原理的因果链清晰 |
| 3 | 组合式创新，思路成立但缺少独立验证 |
| 2 | 主要是工程优化或封装，原理无新意 |
| 1 | 机制未披露，无法判断 |

---

## 4. D2 能力变化（25%）

### 4.1 看什么

只认三类硬指标，其余（榜单排名、主观体验）不计分：

| 指标类型 | 口径要求 | 注意 |
| --- | --- | --- |
| 效果 | 任务成功率 / 一致率 / 准确率，须给出样本量与任务定义 | 官方自评需降一档，除非数据可复算 |
| 成本 | 单位任务货币成本，须写明计价单位与是否含输出 | 警惕「输出免费」这类非标准定价的可持续性 |
| 延迟 | 中位 + 尾部分位数（p95 / 最慢请求） | 只给均值不足以判断可用性 |

### 4.2 打分锚点

| 分 | 描述 |
| --- | --- |
| 5 | 至少一项硬指标改善一个数量级（10×）且有独立证据 |
| 4 | 改善 2–10×，或在一项指标持平的同时另一项大幅优化 |
| 3 | 改善不足 2×，或改善明显但证据只有官方自评 |
| 2 | 指标持平，优势体现在体验或集成便利 |
| 1 | 无可用数据 |

---

## 5. D3 成熟度（20%）

### 5.1 看什么

| 检查项 | 说明 |
| --- | --- |
| 发布阶段 | 内部试用 / 早期访问（候补） / 公测 / 正式可用 |
| 版本节奏 | 是否有可预期的迭代；迭代是否破坏兼容 |
| 可用范围 | 地区、平台、是否需企业资格 |
| 生态活跃度 | 第三方适配器、社区复现、集成数量及其增长 |
| 供应方稳定性 | 是否有商业模式、是否依赖单一资助方 |

### 5.2 打分锚点

| 分 | 描述 |
| --- | --- |
| 5 | 正式可用、多区域、有稳定版本节奏与活跃生态 |
| 4 | 公开可用但仍在快速迭代，生态初步形成 |
| 3 | 早期访问 / 候补名单，或仅单一地区可用 |
| 2 | 只有演示与文档，无真实可用入口 |
| 1 | 停留在发布声明阶段 |

---

## 6. D4 工程可用性（20%）

### 6.1 看什么

| 检查项 | 低代价特征 | 高代价特征 |
| --- | --- | --- |
| 依赖 | 一个 HTTP 接口或一个 SDK | 需要专用硬件、专用运行时或私有协议 |
| 部署形态 | 云 API 与本地权重都有 | 只有云 API，且数据不能出境 |
| 学习曲线 | 概念少、可类比已有工具 | 需要先理解一套新术语与新模式 |
| 文档与错误处理 | 有 schema、有限流与重试说明 | 文档只有营销页 |
| 可回退性 | 能按请求灰度、可随时切回原方案 | 一旦接入就难以拆出 |

### 6.2 打分锚点

| 分 | 描述 |
| --- | --- |
| 5 | 半天内可做通端到端 demo，且可灰度、可回退 |
| 4 | 一到三天可接入，需要少量适配代码 |
| 3 | 需要一周左右，或需处理地区 / 合规限制 |
| 2 | 需要重构现有调用链，或需要专用环境 |
| 1 | 无法自主接入（无公开入口 / 需商务审批） |

---

## 7. D5 对我们的影响（10%）

### 7.1 关联能力清单

| 能力 | 关联问法 |
| --- | --- |
| Agent 评测 | 是否提供新的可测量指标？是否要求我们新增评测维度？ |
| RAG | 是否改变检索、重排或答案归因的做法？ |
| 工具调用 | 是否改变路由、参数校验、失败重试的方式？ |
| 记忆管理 | 是否改变记忆的写入、检索、遗忘策略？ |
| 权限与安全 | 是否改变凭据管理、审批链路、沙箱设计？ |

### 7.2 打分锚点

| 分 | 描述 |
| --- | --- |
| 5 | 直接影响 ≥ 2 项能力，并已能写出具体改造点 |
| 4 | 影响 1 项能力，改造点明确 |
| 3 | 提供设计参考，但暂不改造 |
| 2 | 只影响认知，不影响实现 |
| 1 | 与项目无关 |

## 8. 综合计算与定级

### 8.1 计算公式

```text
总分 = D1×0.25 + D2×0.25 + D3×0.20 + D4×0.20 + D5×0.10
```

总分落在 1.00–5.00 之间。用可运行代码实现一遍，保证每次算出的分一致：

```python
"""五维加权评分：给定五个维度的分数，输出总分与关注等级。"""

WEIGHTS = {
    "mechanism": 0.25,   # D1 技术机制
    "capability": 0.25,  # D2 能力变化
    "maturity": 0.20,    # D3 成熟度
    "usability": 0.20,   # D4 工程可用性
    "impact": 0.10,      # D5 对我们的影响
}

LEVELS = [
    (4.20, "A 立即跟进"),
    (3.40, "B 排期试点"),
    (2.60, "C 持续观察"),
    (0.00, "D 暂不投入"),
]


def score(scores: dict) -> tuple:
    """scores 的键必须与 WEIGHTS 一致，值为 1-5 的整数。"""
    missing = set(WEIGHTS) - set(scores)
    if missing:
        raise ValueError(f"缺少维度: {sorted(missing)}")
    for name in WEIGHTS:
        if not 1 <= scores[name] <= 5:
            raise ValueError(f"{name} 超出 1-5 范围: {scores[name]}")

    total = sum(scores[name] * weight for name, weight in WEIGHTS.items())
    total = round(total, 2)

    level = LEVELS[-1][1]
    for threshold, name in LEVELS:
        if total >= threshold:
            level = name
            break
    return total, level


if __name__ == "__main__":
    print(score({"mechanism": 5, "capability": 5, "maturity": 3,
                 "usability": 4, "impact": 5}))
```

### 8.2 等级与动作

| 等级 | 总分区间 | 动作 | 时间承诺 |
| --- | --- | --- | --- |
| A 立即跟进 | ≥ 4.20 | 写条目 + 排一个最小验证任务 | 本周内出 demo 结论 |
| B 排期试点 | 3.40–4.19 | 写条目 + 进入下季度试点候选 | 本季度内评估 |
| C 持续观察 | 2.60–3.39 | 写速记，不写条目；每季度复查一次 | 无 |
| D 暂不投入 | < 2.60 | 只留一行速记 | 无 |

### 8.3 一票否决与一票升格

| 规则 | 条件 | 效果 |
| --- | --- | --- |
| 一票否决 | 关键事实无法查证，或数据不可复算 | 最高只能 C 级，无论总分多少 |
| 一票否决 | 需要把生产数据交给不可审计的第三方 | 最高只能 C 级 |
| 一票升格 | 与当期项目目标直接相关，且有 A 级来源 | 提升一级，须在评估表写明理由 |

## 9. 两个已收录条目的评分（示范）

### 9.1 Jev

| 维度 | 分数 | 打分理由 |
| --- | --- | --- |
| D1 技术机制 | 5 | 把判断从自回归生成中拆出：非自回归、单次前向、输出限定在预定义类型内，并附校准概率；训练目标从人类偏好改为概率校准 |
| D2 能力变化 | 5 | 官方口径延迟降低数十至近两百倍、成本降至数百分之一；第三方独立测试确认毫秒级中位延迟与校准方向正确，但指出准确率与前沿大模型大致持平 |
| D3 成熟度 | 3 | 早期访问 + 候补名单，服务集中在单一区域；已有第三方网关与开源适配器，但供应方商业可持续性未被验证 |
| D4 工程可用性 | 4 | 概念少（三类原语 + 一次调用），有官方 Python 适配器可同题对比大模型；限制是暂不支持图像、非英语长文本表现不一致 |
| D5 对我们的影响 | 5 | 同时影响工具调用（置信度路由）与评测（需新增校准指标），并可直接落到护栏与人工复核设计 |
| **综合** | **4.40** | **A 立即跟进** |

计算过程：`5×0.25 + 5×0.25 + 3×0.20 + 4×0.20 + 5×0.10 = 1.25 + 1.25 + 0.60 + 0.80 + 0.50 = 4.40`。

> 记录一笔真实的差异：初次凭直觉给的印象分是 4.55，按公式算是 4.40。**框架的纪律是：以公式为准，同时把差异写下来。** 直觉分偏高通常来自 D3（成熟度）被乐观估计——早期访问 + 单一区域，实际并不支撑 4 分。

### 9.2 Muse

| 维度 | 分数 | 打分理由 |
| --- | --- | --- |
| D1 技术机制 | 4 | 机制增量不在模型，而在外部：每用户独立持久化执行环境 + 与用户资产隔离的安全区 + 外部审批组件 + 凭据代持；模型侧为面向 Agent 训练的原生多模态模型 |
| D2 能力变化 | 3 | 单项能力（浏览、工具调用、订票、发邮件）此前已有产品展示过；变化主要来自权限与执行环境的架构，加上应用层整合带来的完成度 |
| D3 成熟度 | 3 | 已公开上线但仅限两个国家，连接器生态刚起步，上线两周内即出现平台封禁与权限争议 |
| D4 工程可用性 | 2 | 作为消费级产品无法自主接入；其底层模型与架构思路可借鉴，但整套运行时不可复用 |
| D5 对我们的影响 | 4 | 权限分层、凭据代持、敏感操作二次确认、执行环境隔离，都能直接映射到我们的 Agent 安全设计 |
| **综合** | **3.15** | **C 持续观察** |

计算过程：`4×0.25 + 3×0.25 + 3×0.20 + 2×0.20 + 4×0.10 = 1.00 + 0.75 + 0.60 + 0.40 + 0.40 = 3.15`。

> 说明：公式结果 **3.15 / C 级**。但它**已写成条目**——因为 C 级只约束「投入多少工程资源」，不约束「是否值得记录」。D1 与 D5 的机制价值独立于它当前是否可用。这正是不把等级当作收录门槛的原因。

## 10. 使用这套框架的纪律

| 纪律 | 说明 |
| --- | --- |
| 先定分再论证 | 先独立打五个分，再写理由；避免理由反过来拉升分数 |
| 每个分数必须指回来源 | 分数旁标注来源级别（A/B/C），C 级来源不能支撑 4 分以上 |
| 官方自评降一档 | 只有官方数据时，D2 最高 3 分 |
| 总分不一致以公式为准 | 直觉与公式冲突时记录差异，不修改公式去迁就直觉 |
| 每季度重算 | 成熟度与工程可用性会随时间上升，D1/D2 是稳定的 |
| 保留历史评分 | 不覆盖旧分数，追加一行「重算日期 + 变化原因」，这样能看出技术在往哪个方向走 |
