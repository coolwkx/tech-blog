# Jev —— 把 Agent 的判断从「生成」里拆出来：不写字，只给带概率的判定

> **一句话结论**：它用「不给自由度」换掉了一类幻觉——把分类、路由、打分、真伪判断从自回归生成里拆成一次前向的类型化输出；代价是它不给理由、不看图、非英语表现不一致，因此只适合当判断层，不能当大脑。
> **收录日期**：2026-09-20
> **状态**：部分待验证
> **类别**：模型

---

## 1. 它解决什么问题

Agent 跑起来之后，调用量最大的一类动作不是「写一段话」，而是「选一个」：这条消息是投诉还是咨询、这个工具该不该调、这个回答够不够格、这一步要不要交给人复核。这些动作目前都交给生成式大模型完成，而生成式模型有一个结构性问题：**它的输出空间是无限的**。

要求模型返回 `{"action": "search"}`，它可能返回 `{"action": "Search"}`、返回带解释的文字、返回一个不存在的动作名，或者干脆返回一段 JSON 外面裹着的 Markdown 代码块。这类失败与模型的推理能力无关，是解码方式带来的——逐 Token 采样，每一步都有跑偏的机会。

### 问题的具体形态

| 现象 | 旧做法下的表现 | 造成的实际损失 |
| --- | --- | --- |
| 输出不合法 | 用正则或 JSON 解析器兜底，失败就重试 | 重试拉高延迟与成本；高峰时会持续失败 |
| 输出越出枚举 | 提示词里写「只能选 A/B/C」，仍返回 D | 需要写额外的校验与映射代码，且覆盖不全 |
| 置信度不可用 | 让模型自述「你有多少把握」，数值不校准 | 基于它做阈值分流不可靠，只能全部人审 |
| 延迟以秒计 | 每个判断点都是一次完整生成 | 长流程里判断点多，延迟线性累加 |
| 成本随判断点增长 | 输出 Token 单独计价，通常是输入的数倍 | 高频判断场景成本失控 |

### 它的切入点

Jev 的选择是**直接取消输出自由度**：开发者预先声明一个类型（type），模型只能从这个类型允许的取值里产生答案，并且同时给出概率。官方定位是「非结构化状态进，类型化概率决策出」（a frontier-intelligence function call），不是写文本的模型，而是给软件提供一个可以 `if` 的判断接口。

它的名字有两层含义：一是取自心理学家 Daniel Kahneman 的「系统一 / 系统二」——快直觉与慢推理，Jev 自称为 System One 模型，与负责「慢思考」的大模型分工；二是取自经济学家 William Stanley Jevons，暗示杰文斯悖论：判断成本降下来之后，判断的总量会上升。

## 2. 核心机制拆解（配文本图）

```text
   [非结构化状态 state]
   （一段文本、一条日志、一份工单摘要）
                │
                │  同一次调用里携带多个问题
                ▼
   ┌────────────────────────────────────────────┐
   │  问题集合（每个问题是原子的单维度判断）        │
   │   Choice: 从最多 N 个选项里选一个            │
   │   Score : 按评分标准给一个分                 │
   │   Noul  : 判断一条陈述是否为真               │
   └───────────────────┬────────────────────────┘
                       ▼
   ┌────────────────────────────────────────────┐
   │  编码器：把 state 编码一次                    │
   │  （state 只编码一次，供所有问题复用）          │
   └───────────────────┬────────────────────────┘
                       ▼
   ┌────────────────────────────────────────────┐
   │  并行打分：不做自回归解码                     │
   │  单次前向 → 直接取候选位置的 logits           │
   │  KV-Cache 广播 → 同一 state 广播给所有问题    │
   └───────────────────┬────────────────────────┘
                       ▼
   [每个问题各自返回]
   choice / score / noul  +  probabilities  +  confidence
                │
                ▼
   下游代码：按 confidence 走阈值路由
   （高置信 → 自动执行；低置信 → 重判 / 升级给人）
```

### 2.1 输入：它接受什么

一次调用提交**一份状态 + 一组问题**。状态是非结构化文本；每个问题必须是原子的、单维度的判断。官方设计原则是：复杂逻辑拆成多个问题，在业务代码里组合，而不是让模型一口气做完多步推理。

| 原语 | 用途 | 返回字段 |
| --- | --- | --- |
| Choice | 从最多 255 个选项中选一个 | choice、probabilities、confidence |
| Score | 按给定评分标准打分 | score、probabilities、confidence |
| Noul | 判断一条陈述是否为真 | 0–1 的概率值 |

### 2.2 处理：核心计算路径

公开信息显示，它的关键做法是**跳过自回归解码**：不逐 Token 生成文本再解析，而是在一次前向计算中直接对候选位置取 logits 并归一化成概率。这样做的直接结果是输出天然落在声明好的取值集合内——不是靠事后校验，而是靠输出空间本身被限制住。

官方口径称输出是「并行一次生成」而非逐 Token 生成；第三方复现项目进一步描述了「KV-Cache 广播与并发批量评估」的工作方式，即把同一份状态的缓存广播给多个问题，从而在一次批处理里回答多个问题。这一层机制在原始实现中并未完整公开，属于复现方的分析结论。

把它与逐 Token 生成在机制上逐项对照，差异会更清楚：

| 环节 | 自回归生成 | 决策模型（按公开口径） |
| --- | --- | --- |
| 状态编码 | 每生成一个 Token 都要带上完整上下文前向一次 | 状态只编码一次，结果被所有问题复用 |
| 答案产生 | 依次采样，第 N 个 Token 依赖前 N−1 个 | 一次前向直接取候选位置的 logits |
| 多问题处理 | 通常一次请求问一个问题 | 同一状态广播给多个问题，批内并发 |
| 取值合法性 | 靠提示词、语法约束或事后校验 | 由输出空间本身限定 |
| 概率来源 | 需要专门引导模型自述，且不校准 | 由 logits 归一化得到，训练目标即校准 |

这也解释了为什么「快」和「不给理由」是同一件事的两面：一旦取消了逐步解码，就没有产出一个推理链的位置。速度不是优化出来的，而是这个设计选择的副产品。

### 2.3 输出：它承诺什么保证

它承诺的是**类型层面的保证**，而不是正确性保证：

| 它保证 | 它不保证 |
| --- | --- |
| 答案只能是 schema 里定义的值 | 答案在语义上是对的 |
| 每个答案附带概率或置信分数 | 概率在所有任务上都校准良好（已有第三方提出异议） |
| 不产生格式错误、不凭空造选项 | 不产生任何形式的错误判断 |
| 输出可直接被程序消费，无需正则兜底 | 能解释为什么这么判断 |

官方把可靠性主张放在「概率校准」而不是「永远正确」上，这个自我定位是诚实的，也是理解它的关键。

### 2.4 可靠性手段

| 手段 | 作用 |
| --- | --- |
| 受限输出空间 | 从机制上消除格式错误与枚举越界 |
| 训练目标改为校准 | 官方称使用自研的 RLCD（面向校准决策的强化学习），优化「带诚实概率的答案」，而非 RLHF 的人类偏好 |
| 原子的单维度问题 | 降低单次判断的复杂度，减少「一步错步步错」 |
| 置信度外置消费 | 把「信不信」交给业务代码，而不是交给模型 |

> 注意：RLCD 的奖励函数、网络结构、校准方法均未公开，因此第 2.2 与 2.4 节中关于「怎么做到」的部分，只有行为层面的证据，原理层面仍属**待验证**。

## 3. 与已有方案对比

| 方案 | 核心思路 | 优势 | 局限 | 适用场景 |
| --- | --- | --- | --- | --- |
| Jev（决策模型） | 取消文本生成，一次前向输出类型化判定 + 校准概率 | 毫秒级延迟、输出天然合法、概率可用于阈值分流、单位成本低 | 不给理由（强监管场景难用）、不看图、非英语长文本表现不一致、机制未完全公开 | 高频、原子、结果可被程序直接消费的判断节点 |
| ReAct 式循环 | 用同一个生成模型交替产出推理与动作，动作以文本形式表达 | 通用、无需额外模型、能处理开放式任务 | 每步都是完整生成，延迟与成本随步数累加；动作格式错误需要重试 | 步数不定的探索型任务、需要边想边做的场景 |
| LLM router / 意图分类器 | 用小模型或规则把请求分派到不同处理路径 | 实现简单、可解释、路由逻辑可审计 | 规则难覆盖长尾；小模型在语义边界模糊时准确率下降 | 意图类别稳定、类别数量有限的入口分流 |
| Guardrails 框架 | 在模型输出后做规则 / 分类器校验，拦截不合规内容 | 与模型解耦、策略集中管理、可独立更新 | 属于事后拦截，被拦截的请求仍需重新生成；规则维护成本高 | 合规红线、内容安全、输出格式约束 |
| 结构化输出 / JSON 模式 | 仍然逐 Token 自回归生成，但用语法约束把输出限制在 schema 内 | 复用现有大模型、无需新供应商、生态成熟 | 仍是自回归过程，延迟以秒计；概率不被校准；模型仍可能"填对格式、选错值" | 需要模型同时产出解释与结构化字段的场景 |
| LLM-as-judge | 用大模型给另一个模型的输出打分 | 能评价开放式质量、可解释、无需标注 | 成本高、延迟高、分数本身不校准、存在位置与风格偏好 | 离线评测、少量高价值样本的质量把关 |

### 选型结论

**它与现有方案是互补关系，不是替代关系。** 合理的组合是：ReAct 循环继续由大模型驱动，负责「想」和「写」；每个循环里的判断点（要不要调工具、调哪个、结果够不够格、要不要升级给人）交给 Jev 这类决策模型；Guardrails 仍然保留，但职责从「拦格式错误」变成「拦策略违规」；LLM-as-judge 退到离线评测。

**最容易混淆的一对是「结构化输出 / JSON 模式」和它。** 两者都让输出变得可编程，但实现路径完全不同：

| 对比点 | 结构化输出（JSON 模式） | Jev 类决策模型 |
| --- | --- | --- |
| 解码方式 | 逐 Token 自回归 + 语法约束 | 一次前向 + 候选位置取 logits |
| 输出内容的性质 | 可以是任意文本的字段，包含解释 | 只能是预定义类型的取值 |
| 延迟量级 | 秒级 | 毫秒级 |
| 概率 | 不提供，或提供的是不校准的自述置信度 | 提供，且以校准为训练目标 |
| 主要失效模式 | 格式对但选错值；长输出中途跑偏 | 选错值（但不产生格式错误） |
| 成本结构 | 输出 Token 单独计价 | 输出不计费 |

结论：如果某个环节**需要解释**，用结构化输出；如果只需要**一个可被程序消费的判定**，用决策模型。

**不要选它的场景**：需要给出判断理由且理由要可追溯到监管的场景（金融、医疗、法律）；需要看图或多模态输入的场景；以中文等非英语长文本为主的场景（需先自行验证精度与有效长度）。

## 4. 上手成本

| 子项 | 情况 |
| --- | --- |
| 依赖 | 网络依赖为默认形态：通过 API 调用，服务处于早期访问、需申请。若只在本地复现接口范式，则需要本地模型 + GPU 或可接受的 CPU 推理时间（社区复现项目已证明无 GPU 也可跑通） |
| 部署 | 官方为托管 API，服务部署在单一区域；官方另开源了一个 Python 适配器，可用同一套 Choice / Score / Noul 接口去调用 OpenAI 或 Anthropic 兼容的大模型，便于同题对比 |
| 学习曲线 | 低。需要理解的概念只有三个（Choice / Score / Noul）和一条设计原则（问题必须原子化）。有提示词工程经验的开发者，主要的心智转换是「不再写自然语言指令，而是声明类型」 |
| 生态成熟度 | 早期。官方适配器仓库 2026 年 8 月创建、9 月约 179 star；社区出现本地模拟接口的实现与多个第三方校准测试项目；第三方模型网关已上架其模型。整体规模仍小，不足以支撑生产依赖 |

## 5. 对我们的影响（结合本项目：Agent 评测、RAG、工具调用、记忆管理 等）

### 5.1 Agent 评测

| 要改的地方 | 怎么改 | 怎么验证 |
| --- | --- | --- |
| 评测指标缺一项 | 现有评测看「对不对」，需新增**校准指标**：把预测概率分桶，看每桶内的实际正确率是否接近桶中心 | 在自己标注的样本上画可靠性图（reliability diagram），算 ECE（期望校准误差） |
| 置信度目前不可用 | 把「模型自述置信度」从评测里去掉，改为只评测可校准的概率输出 | 对比同一批样本上「自述置信度」与「校准概率」的分桶正确率 |
| 校准可能不是全域的 | 按「置信且正确 / 置信且错误 / 不确定」三类拆分统计，而不是只看总体 ECE | 检查总体 ECE 高时，是否由某一类集中贡献 |

已有第三方工作正是按这个方向做的：有项目用手工标注的 Agent 工具调用样本画可靠性图并计算 ECE，也有项目在模型不可能见过的规则生成样本上做分布外校准测试。**这两个方向可以直接借来做我们的评测补充。**

### 5.2 RAG

无直接影响。RAG 的检索与生成环节不因它改变。间接影响是：RAG 流程中的判断点（这个查询要不要检索、检索结果够不够、要不要转人工）可以考虑下移到决策层，但这属于 5.3 的范畴。

### 5.3 工具调用

| 要改的地方 | 怎么改 | 怎么验证 |
| --- | --- | --- |
| 工具路由 | 把「选哪个工具、传什么动作」从生成模型里拆出来，改为对候选工具集合做一次类型化选择 | 在历史工具调用日志上回放，对比路由准确率与 p95 延迟 |
| 参数校验 | 枚举型参数改为类型化选择，从机制上消除非法取值 | 统计非法参数导致的重试次数是否下降 |
| 失败重试 | 重试策略改为基于置信度：高置信失败才重试，低置信直接降级 | 观察重试率的下降与最终成功率的保持情况 |
| 尾延迟 | 长流程里的判断点从秒级降到毫秒级后，重新测端到端 p95 | 对比改造前后的 p95，而不是只看中位数 |

### 5.4 记忆管理

| 要改的地方 | 怎么改 | 怎么验证 |
| --- | --- | --- |
| 记忆写入的准入 | 「这段对话值不值得写入长期记忆」是一个典型的二值判断，适合下移到决策层 | 用标注好的对话样本测准入判断的准确率与校准度 |
| 冲突消解 | 「新记忆与旧记忆是否矛盾」可作为一次判断 | 构造冲突样本集测判断质量 |

以上两项都依赖「决策模型在中文长文本上的表现」这一**待验证项 V6**，未验证前不改造。

### 5.5 权限与安全

| 要改的地方 | 怎么改 | 怎么验证 |
| --- | --- | --- |
| 人工复核触发 | 用置信度阈值决定是否升级给人审，替代「全量人审」或「随机抽检」 | 在历史样本上画出阈值 vs 漏检率的曲线，取业务可接受点 |
| 护栏分层 | 护栏职责拆两层：格式合法性由受限输出空间保证，策略违规仍由规则 / 分类器拦截 | 统计改造后护栏命中率的变化（格式类命中应趋近于 0） |
| 判断可追溯 | 记录每次判断的输入摘要、选项集合、概率与最终决策 | 抽查能否复现任意一次判断的决策依据 |

**但要正视它的短板**：Jev 不给理由。对于必须留存推理链才能过合规审查的环节，它不能替代 LLM-as-judge，只能用于「判断 + 记录概率」，把解释责任留在下游。

## 6. 待验证问题

### 6.1 关键事实缺口

| 编号 | 待验证内容 | 为什么存疑 | 需要什么材料才能解决 |
