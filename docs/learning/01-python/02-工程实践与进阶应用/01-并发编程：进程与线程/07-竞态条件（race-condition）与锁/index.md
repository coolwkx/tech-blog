# 竞态条件（race condition）与锁

> **学习目标**：能够解释「竞态条件（race condition）与锁」的机制或步骤，并用本节材料验证理解。
>
> **前置知识**：函数与参数（02 篇）、`if __name__ == "__main__"` 与模块（05 篇）、竞态与锁的直觉（`try/finally`，04 篇）。
>
> **所属主题**：并发编程：进程与线程 · 核心概念

## 本次只学这一点

经典场景：**检查-然后-行动（check-then-act）不是原子的**。
```text
初始 balance = 100，两个线程各取 60
t1: 检查 balance(100) >= 60 → 成立
t2: 检查 balance(100) >= 60 → 成立 ← 问题出在这
t1: balance = 100 - 60 = 40
t2: balance = 100 - 60 = 40（用旧值）或 40 - 60 = -20
```
实测结果（稳定复现）：
```text
余额竞态(无锁): -20 (正确结果应为 40)
余额竞态(加锁): 40
```
**修复：把"检查 + 修改"整体放进临界区**。
```text
lock = threading.Lock

def withdraw:
 with lock: # 进入临界区，同一时刻只有一个线程能进来
 if balance[0] >= 60:
 time.sleep(0.001) # 模拟耗时的写操作
 balance[0] -= 60
```
| 写法 | 说明 |
| --- | --- |
| `with lock:` | **推荐**，出异常也会自动释放 |
| `lock.acquire()` / `try ... finally: lock.release()` | 手动版，容易忘记释放 |
| `lock.acquire(blocking=False)` | 不阻塞，拿不到立刻返回 `False` |
| 同一线程重复 `acquire` 同一把 `Lock` | **死锁**（用 `RLock` 可重入） |
| 忘记释放 / 两个锁交叉获取 | 死锁，程序卡住不再响应 |

> 一个必须澄清的点：**GIL 让竞态更难复现，但不让它消失**。本机实测（CPython 3.12）："2 个线程各循环 100 万次 `g_num += 1`"这个经典 demo **跑出了 1000000 的"正确"结果**（8 线程 × 50 万也同样正确），因为 GIL 的切换间隔默认 5ms，而 `+=` 的字节码窗口太小，很难被打断。但这**不是保证** —— 一旦代码里出现真正的多步操作（函数调用、`sleep`、I/O、`dict` 多步更新），竞态立刻复现。所以正确的学习姿势是：用"取款"这类带明确窗口的例子理解竞态，而不是背"100 万次加 1 会少"这个未必成立的结论。
