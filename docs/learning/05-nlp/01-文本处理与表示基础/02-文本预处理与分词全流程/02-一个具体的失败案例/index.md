## 本次只学这一点

朴素流水线 `text.lower.split()` → 查词表。训练集里出现过 `Café` 与 `café`，测试集来的是 `cafe\u0301`：

- `café`（U+00E9，1 个码位）与 `cafe\u0301`（`e` + 组合重音，2 个码位）**肉眼完全一样**，`==` 却返回 `False`；
- 词表里只会存其中一种写法，另一种必然落到 `[UNK]`；
- 同一个词在训练集里被拆成两个稀疏 key，语义各学一半。

这不是假想：macOS 返回的文件名默认是 NFD（分解形式），Windows / Linux 多为 NFC（预组合形式），跨平台抓取的数据天然混着两种写法。所以需要一条**确定性、尽量可逆、对未见词友好**的流水线。
