## 本次只学这一点

把上面的表压成一棵树：按顺序问四个问题，每个问题的答案都会砍掉一部分候选方案。这张图回答的是「按什么顺序问、每个答案分别通向哪个手段」。

```mermaid
flowchart TD
    A["需求进来"] --> Q1{"Q1 要解决的问题里，「事实」会随时间变化吗？"}
    Q1 -->|会| R1["RAG<br/>改库即可，不用重训"]
    Q1 -->|不会| Q2{"Q2 输出是否只需满足固定格式 / 协议<br/>（JSON、标签集）？"}
    Q2 -->|是，且样本 ＜ 500| R2["few-shot Prompt + 约束解码"]
    Q2 -->|否 / 样本足够| Q3{"Q3 换一个更强的基座，能不能直接做对？"}
    Q3 -->|能| R3["换基座 / 接工具调用"]
    Q3 -->|不能| Q4{"Q4 有标注样本量 N 是多少？"}
    Q4 -->|N ＜ 50| R4["ICL / 先把数据扩到 500+"]
    Q4 -->|50 ≤ N ＜ 500| R5["LoRA，只做格式 / 风格对齐"]
    Q4 -->|500 ≤ N ≤ 5,000| R6["LoRA / QLoRA（甜点区）"]
    Q4 -->|5,000 ＜ N ≤ 50,000| R7["先 LoRA 验证，再决定是否全参"]
    Q4 -->|N ＞ 50,000| R8["全参 SFT（+ 数据配比实验）"]
```

**读图要点**：

| 观察 | 含义 |
| --- | --- |
| Q1 问的是「知识会不会变」而不是「任务难不难」 | 事实会变时微调几乎必然滞后，RAG 改库就能生效，所以它必须排在第一位 |
| Q2 在区分「模式问题」与「能力问题」 | 格式是浅层模式，少量样本的 PEFT 就能学会，不值得上全参 |
| 前三个问题都在排除「不该微调」的情况 | 只有 Q1 到 Q3 都答「否」才进入样本量判断，避免默认把微调当成第一手段 |
| Q4 的区间对应一条容量经验曲线 | 数据越少越该用低容量方法（ICL → LoRA → 全参），否则参数量远多于样本，模型只会背下训练集 |
| 整棵树只负责筛选，不负责承诺效果 | 每一步附加的检查（有没有独立评测集、线上调用量撑不撑得起一次性成本）才是能否落地的真正判据 |

每一步都要附加检查：有独立评测集吗？线上调用量撑得起一次性成本吗？
