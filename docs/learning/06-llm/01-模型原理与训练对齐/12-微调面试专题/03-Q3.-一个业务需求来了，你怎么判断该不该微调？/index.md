# Q3. 一个业务需求来了，你怎么判断该不该微调？

> **学习目标**：能够解释「Q3. 一个业务需求来了，你怎么判断该不该微调？」的机制或步骤，并用本节材料验证理解。
>
> **前置知识**：Transformer 基本结构、SFT 流程、LoRA/QLoRA 的原理、显存构成（权重/梯度/优化器状态/激活/KV cache）、常用评测指标。
>
> **所属主题**：-微调面试专题 · 第一组：概念与决策

## 本次只学这一点

<details markdown="1">
<summary markdown="1">参考答案</summary>

**30 秒版**：先做提示词基线，再判断瓶颈在哪。如果「提示词 + few-shot + 检索」已经能达到验收标准，就不微调；如果瓶颈是格式稳定性、领域语言、延迟或成本，才进入微调路线。

**展开版**——一张决策清单：

```
① 需求能否被 3~5 句指令 + 少量示例表达清楚？
    能 → 先做提示词工程，设一个可量化的验收线
② 模型是否缺知识？
    是 → 先上 RAG（成本低、可更新、可溯源）
③ 提示词已经调好，但表现不稳定（格式失败、风格漂移、长尾任务差）
    是 → 微调（通常 LoRA）
④ 是否需要私有部署、低延迟、低成本？
    是 → 微调一个更小的模型，往往比调大模型 + 长上下文更划算
⑤ 是否有 ≥ 500~1000 条高质量标注数据，且能持续维护？
    否 → 先解决数据问题，微调会很痛苦
```

**必须一起算的成本**：

- 数据成本：标注、清洗、审核（往往占总成本的一半以上）；
- 训练成本：GPU 小时；
- **维护成本**：基座升级要重训、数据分布漂移要重训、评测集要持续更新——这一项最容易被忽略，但它是长期成本的主体。

**追问预判**：
- *「什么时候微调是错的答案？」* —— 当需求本质是「知识更新」或「检索问题」时。用微调去背知识，会得到一个小、脆、且一更新就要重训的模型。
- *「小模型微调 vs 大模型提示词，怎么选？」* —— 看延迟与成本约束。数据量足够时，小模型微调后在窄任务上常常追平大模型，而推理成本低一到两个数量级。
