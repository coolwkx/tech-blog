# Q18. 微调的评估指标应该怎么设计？

> **学习目标**：能够解释「Q18. 微调的评估指标应该怎么设计？」的机制或步骤，并用本节材料验证理解。
>
> **前置知识**：Transformer 基本结构、SFT 流程、LoRA/QLoRA 的原理、显存构成（权重/梯度/优化器状态/激活/KV cache）、常用评测指标。
>

## 本次只学这一点

<details markdown="1">
<summary markdown="1">参考答案</summary>

**30 秒版**：四个维度一起看——目标任务指标、通用能力保持、格式合规率、过拟合检查。基线必须是「未微调 + 好提示词 + few-shot」，并且要跑多随机种子报均值 ± 标准差。

**展开版**：

| 维度 | 指标 | 采集方式 |
|---|---|---|
| 目标任务 | Accuracy / macro-F1 / EM / ROUGE-L / 人工通过率 | 留出测试集 |
| 通用能力保持 | 通用基准回归的相对下降率、保持率（几何平均） | 200~500 条遗忘哨兵集，必要时跑全量 |
| 格式合规率 | JSON 可解析率、schema 通过率、必填字段齐全率 | 解析器批量跑，设绝对下限（如 ≥99%） |
| 过拟合 | 训练/验证 loss gap、验证指标峰值后的回落、复述率 | 训练日志 + n-gram 重合统计 |

**基线设计**（四行对比）：

| 组别 | 说明 |
|---|---|
| A. 零样本 | 只给指令 |
| B. few-shot | 好提示词 + 3~5 示例 ← **主基线** |
| C. 微调 | 报告方法、参数量、训练成本 |
| D. 微调 + few-shot | 判断两者互补还是互相覆盖 |

**容易被忽略的两点**：

1. **格式合规率必须单列**。一个 F1 涨了 9 个点但 JSON 解析率从 99% 掉到 78% 的模型，在生产上是严重回归；
2. **要报告成本**。GPU 小时、峰值显存、推理延迟。只报效果的对比实验是不完整的。

**追问预判**：
- *「为什么基线不用『未微调的裸模型』？」* —— 因为那会高估微调收益。决策要回答的是「相对于最便宜的可用方案（提示词工程），微调值不值」。
- *「怎么衡量灾难性遗忘？」* —— 同一套评测配置跑微调前后，计算相对下降率；优先看单基准的最差下降，别只看平均分。
