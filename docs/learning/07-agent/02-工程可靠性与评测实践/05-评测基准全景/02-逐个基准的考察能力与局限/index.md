# 逐个基准的考察能力与局限

> **学习目标**：能够解释「逐个基准的考察能力与局限」的机制或步骤，并用本节材料验证理解。
>
> **前置知识**：[01-为什么Agent评测比LLM评测难](../../../../../07-agent/05-评测/01-为什么Agent评测比LLM评测难.md) 的环境契约、[03-评测方法-单元测试与LLM即裁判](../../../../../07-agent/05-评测/03-评测方法-单元测试与LLM即裁判.md) 的判题分层与显著性检验。
>
> **所属主题**：-评测基准全景 · 核心概念

## 本次只学这一点

**SWE-bench** —— 考察什么能力：在只读 issue 描述的情况下定位跨文件缺陷、写出符合仓库风格的补丁。任务形态：仓库快照 + issue 文本 → 补丁。评测方式：`FAIL_TO_PASS`（原先失败、修复后必须通过）与 `PASS_TO_PASS`（不能被破坏）两组测试。已知局限：①**测试可被改动**，被测系统若能看到测试文件就可能直接改测试来「通过」；②环境安装失败率高，成功的样本里混杂了「装不上依赖」的噪声；③正确补丁可能早已 merged 进主干，模型记住补丁内容也能得分（污染）；④只覆盖 Python，且以 bug 修复为主，不覆盖新功能开发与重构。

**SWE-bench Verified** —— 考察什么能力：与 SWE-bench 相同，但聚焦于**人类确认可解且描述充分**的子集。任务形态与评测方式同上。已知局限：规模从 2294 降到 500，统计噪声更大；筛选过程本身引入了「什么样的任务算清晰」的主观判断；其余局限与 SWE-bench 相同（污染与测试可改动仍然存在）。

**WebArena** —— 考察什么能力：在真实感的网页应用里完成多步操作（下单、发帖、改配置、跨站查信息）。任务形态：自然语言指令 + 自托管站点。评测方式：**执行式校验**——运行后读取站点的数据库/后端状态判断意图是否达成，而不是做字符串匹配；论文还提出 functional correctness 指标。已知局限：①四个站点与真实互联网的分布差异大，多数真实站点有验证码、反爬、动态渲染；②依赖自托管环境的稳定性，容器故障会算作任务失败；③任务多为「可脚本化」的操作，对人类直觉依赖的模糊需求覆盖不足。

**OSWorld** —— 考察什么能力：真实 Ubuntu 桌面上的 GUI 操作与多应用协同。任务形态：开放式计算机任务（五类）。评测方式：执行式判分，通过读取文件系统、应用状态与截图判断。已知局限：①单任务耗时长，整套评测的**成本与时间都很高**；②截图判分对视觉细节（分辨率、主题、窗口位置）敏感，容易产生假失败；③虚拟机不稳定（崩溃、卡死）会污染结果；④任务设计难以覆盖真实办公中的模糊约束。

**GAIA** —— 考察什么能力：把网页浏览、文件解析、计算与推理组合成多步流程。任务形态：三级难度的问题，答案唯一且短。评测方式：短答案规范化后准精确匹配。已知局限：①**只约束答案、不约束过程**，模型可以用任意手段（包括猜）得到答案；②答案唯一导致对格式与表述要求严格，容易出现「推理对了但格式差一点」的假失败；③题目公开时间久，存在污染风险，需用新题或改写题复测；④不评估成本与延迟。

**AgentBench** —— 考察什么能力：作为 Agent 的多轮决策与环境交互能力。任务形态：8 个正交环境。评测方式：各环境自带指标（完成率、进度、胜率）。已知局限：①部分环境偏游戏化（卡牌游戏、谜题），与生产任务的迁移性弱；②各环境指标口径不统一，跨环境直接平均意义有限；③主要是**单 Agent 单工具**交互，对多 Agent 协作与复杂工具链覆盖不足。

**τ-bench** —— 考察什么能力：在多轮对话中既要用工具改对数据库，又要遵守书面政策。任务形态：模拟用户 + 领域 API + 政策文档的三方交互。评测方式：数据库终态比对 + 政策遵从检查。已知局限：领域较窄（零售、航空）；模拟用户的表达多样性有限；政策遵从的判定依赖预定义的规则集。

**BFCL** —— 考察什么能力：Function Calling 的语法、参数与调用决策正确性。任务形态：给定函数签名与用户请求，输出调用。评测方式：AST 结构匹配 + 实际可执行性校验。已知局限：**不涉及多步轨迹**，本质上是结构化输出评测；单轮/少轮为主，无法反映长程决策与错误恢复。
